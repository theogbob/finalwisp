## idle settle (2026-10-25, lead request for base-2)
`wst idle` / regress idle no longer read RSS at a fixed 3 s: they sample once a second until 4 samples (3 s,
longer than the 2 s idle sweep) differ by < 2% of the idle memory (or < 0.1 KiB/conn), at most 30 s (`--settle`).
Records gain settle_s (None = not stable by 30 s; regress adds a row note), kib_per_conn_3s (the old reading) and
the RSS samples. Why: on 2 vCPU boxes the frees finish later (vmtest: 20-129 KiB/conn at 3 s, 4.7 at 33 s).

## idle pairs and resolution floor (2026-10-31, branch idle-pairs; the flow branch's A/A on VPS3, base4fix rcq3)
- `wst regress --suite idle` ran max(6, reps // 2) reps (8 pairs at --reps 16); now max(6, reps): one base and one
  new probe per rep, so --reps 16 = 16 pairs (the idle suite takes ~2x as long: ~13 s per probe, ~7 min at 16).
- Resolution floor: settled RSS moves in 0.1-0.25 MiB steps (and kib_per_conn is rounded to 0.1 KiB = 0.2 MiB at 2000
  conns). The effect is the Hodges-Lehmann estimate of the paired differences new - base of the probe's RSS above its
  start (rss_settled_mib - rss_before_mib, the RSS behind kib_per_conn, MiB; the verdict's HL ratio is the same
  estimator on log ratios, so a minority of large increases still counts). A WIN / LOSS / watch needs |effect| >=
  max(0.25 MiB, the measured step); below it the row is tie, `verdict_raw` keeps the computed verdict and a note says
  why. Measured step = the smallest gap between one build's distinct settled RSS values, taken only for a build with
  >= 3 distinct values, the larger of the two builds (a gap between the builds is never a step). `resolution` on the
  row: effect_mib, floor_mib, step_mib. tie / unclear are not changed; ratio, p and CI stay as computed.
  (regress.IDLE_FLOOR_MIB, rss_step, idle_floor.)
- Why: the A/A (rc1 vs an identical copy, n=8) rescored on rss_settled_mib gave 1.062 "LOSS" (p 0.031); the regress
  row itself said watch 1.064. Through the new rule (same raw data): watch -> tie (effect 0.2 MiB). The other rcq runs:
  rcq2 idle-fin watch 1.078 -> tie (0.2 MiB); rcq idle-fin stays watch 1.095 (0.35 MiB); the base-3 vs RC1 WIN 0.356
  stays WIN (-6.1 MiB); unclear / tie rows unchanged. The copy's rss_before is 0.1-0.2 MiB higher in most A/A pairs
  (the effect subtracts it).
- Tests: bench/tests/test_regress_validity.py IdlePairsAndFloorTests: 16 pairs at --reps 16; a synthetic one-step A/A
  (LOSS before, tie after); real differences keep LOSS / WIN (a constant 0.6 MiB shift with each build constant, a
  zero-heavy 6-of-16 increase, the base-3 vs own-alloc size); the per-variant step. The old code fails 4 of them.

## exact RSS sampling (2026-11-01, branch rss-exact; the flow branch's gold idle check, 60.17)
- sample.group_usage (the session RSS behind every idle row and the ab/regress RSS columns) now sums VmRSS from
  /proc/PID/status, not the /proc/PID/stat rss field. On kernel >= 6.16 the stat field is the approximate per-CPU counter
  read (VmRSS is the exact sum); on gold (72 CPUs) it read 7-18 MiB high at idle and gave RC1 a false idle LOSS
  (exact: b3 -> rc1 WIN 0.92, A/A tie). The resolution floor stays until A/A data on the fixed harness says otherwise.
- Caveat: peak RSS (VmHWM, the "peak MiB" columns) still comes from the approximate counter in the kernel, so on
  many-CPU boxes it can carry the same bias (several MiB). Use cgroup memory.peak (potato scopes) where exact peaks matter.
## What
One entry point `bench/wst <command>` (= `python3 -m wispsuite` in bench/) for every functional gate and
benchmark: compat, ab, regress, matrix, showdown, wispmark, potato, link, idle. Shared library bench/wispsuite/
(proc, sample, stats, wbench, servers, report); one server registry bench/servers.json; one result JSON shape
(`schema wispsuite/1` + `meta` with git rev and binary md5s). Stdlib only; sudo only for `link`.
Works on competitor servers: `--server NAME` / `fw:PATH` / `NAME='cmd --port {port}'`.

## Decisions (2026-10-24, lead OK on Q1-Q5)
- regress runs the A/B cases in-process (one process registry; SIGTERM stops server, target, client); cases,
  thresholds, verdict rules, LOSS re-run, PROBLEM rules, table and exit codes unchanged (checked: stats/table/case
  lists/confirm identical to master's regress.py on 3000 random inputs; A/A --quick side by side).
- wispmark: `--profile current` (wisp-js 0.5.0, INFO; default) and `--profile upstream` (WispMark's 0.4.1 + DEBUG).
  Echo target stays wbench (byte counters, no sudo/iftop); difference documented in bench/README.md.
- compat on other servers = report mode (adversarial.py asserts some finalwisp choices; not edited).
- compat --bin exits 1 on any failure, including cargo test (old gates.py always exited 0 and did not count
  cargo FAILED/panicked lines). `--matrix` adds adversarial + wisp-js on --no-splice/--balance/--no-tfo/--graceful-close/--dns-own (70.09).
- One-offs moved to bench/legacy/ (README maps old -> new); probes to bench/probes/ (64-bit WS length fix).

## Behaviour changes vs the old scripts
- ab: waits for the server port (local runs) and still keeps >= 0.5 s before the client starts; a server that
  never listens gives an error record instead of a wbench failure; strays checked by listener and command line.
- every server/target/client stopped as a whole process group and waited for (no SIGKILL-and-forget).
- no -1 placeholders in medians; showdown/wispmark/matrix JSON gain `schema`/`kind`/`meta`.
- gates now also run wisp-js over UDP (wispjs_udp.mjs), which the old gate runner skipped.
- compat --bin: a SKIP (membudget without scopes) fails the gate unless --allow-skip; it prints where cargo test ran
  (that source is not checked against --bin).
- compat --bin --fuzz-replay (opt-in, 70.01): builds the cargo-fuzz targets of --cargo DIR/fuzz and replays every
  committed regression corpus server/fuzz/regress/<target> once (-runs=0, in bwrap --unshare-net, ~1 min after the
  build). Inputs found by a fuzz campaign are added there with `-set_cover_merge=1` (docs/summaries/70.01).
- compat --bin step `dns-own` (70.09, tests/compat/dns_own.py, ports B+40..49): finalwisp --dns-server against a
  Python fake DNS server (UDP+TCP, IPv4+IPv6): A, A SERVFAIL + AAAA, TC->TCP, NXDOMAIN/NODATA (+ negative cache),
  SERVFAIL, timeout, garbage / wrong ID / wrong question / other source port, CNAME chain, FORMERR on EDNS, a
  refused first server, an IPv6 nameserver, cancellation (~10 s).
- compat --bin opt-in `--proxy` (40.02, tests/compat/proxy.py, ports B+90..99; docker + nginx:1.27-alpine + caddy:2.8-alpine,
  missing = SKIP): finalwisp ws:// behind nginx and Caddy with the 40.01 configs (TLS at the proxy): wisp-js (2x64 MiB
  download), 32 MiB upload whose target stalls 6 s, a connection idle 125 s; the same direct as the reference.
- compat --bin step `drain` (60.12, tests/compat/drain.py, ports B+80..89): SIGTERM/SIGINT graceful shutdown: idle
  connection -> WS 1001, new connections refused, live stream served until it ends (exit 0), --drain-timeout -> 1001
  to all, second signal / --drain-timeout 0 -> exit at once, 8 connections queued while stopped -> 101 + 1001 (no RST),
  wss -> 1001 + close_notify.
- stop = the whole session, not only the process group (GNU `timeout` in run_tls.sh makes its own group); SIGHUP
  handled like SIGTERM; signals blocked only between fork and registration, never in the children.
- wbench: an explicit --wbench / $WBENCH is used as given (no silent fallback to another binary).
- potato checks --cpu/--pin against the CPUs this process may use (a sandbox without CPU 0 made
  `taskset -c 0` fail and every target die silently in the old script).
- regress --port-base P (optional) moves every port to P..P+7; default ports unchanged.
- regress potato (bench-cpu, lead decision 2026-10-24): server on the 2nd-lowest and peers on the lowest CPU of
  sched_getaffinity (was fixed 1 / 0); fewer than 2 allowed CPUs = PROBLEM, not run (was: unpinned on 1-CPU boxes).
  On a normal box with all CPUs allowed this is the same 1 / 0 as before. `wst potato --cpu` defaults to the
  2nd-lowest allowed CPU too.
- The thin wrappers (ab.py, regress.py, ...) stay until Phase C C3 is merged, then go. No sudo/iftop WispMark mode
  (decision): our echo-side count reads ~1-5% higher than WispMark's iftop number (bench/README.md).

## Host power state (2026-10-24, lead request)
Every result's meta has `power` {start, end, changed}: `powerprofilesctl get`, cpufreq policy0
energy_performance_preference + scaling_governor, AC online (power_supply type Mains; null if none), battery
status (informational). regress prints both samples in the summary header and adds a PROBLEM when profile, EPP,
governor or AC changed mid-run. Reason: a laptop regress had wss 2x higher for both builds than a run 30 min later.

## connchurn + burstidle (2026-10-25, lead request before the base-1.2 A/B)
- wbench `--test connchurn` (bench/src/connchurn.rs): conns x streams loops of new WebSocket connection ->
  CONNECT -> 64 B echo -> close; the closing half (server close frame, TLS close_notify, TCP FIN) runs in a
  closer task (<= 16 per loop) so the server closes TCP first (its TIME_WAIT, not the client's ports) and
  finalwisp's 100 ms kTLS linger tick is not measured. Why: churn reuses connections, so the glibc 16 KiB
  mmap threshold's per-new-connection rbuf mmap/munmap was never measured.
- `burstidle` in wispsuite/ab.py: 3 x (5 s download, 3 s idle) per server process; regress lo + tls lists
  gained `connchurn 10x10`, `burstidle 10x10`, `connchurn-tls 10x10`.
- Smoke (laptop, shared, 1 rep): connchurn 10x10 fw-base1.1 34.8k conns/s p50 2.7 ms p99 6.3 ms vs epoxy 12.3k;
  connchurn-tls fw-base1.1 7.0k; burstidle fw-base1.1 bursts 10957/11359/10915 MiB/s idle CPU 0.3-0.7% vs
  epoxy 4343/3863/3794, idle 0%. A second smoke after the review fixes (power state differed): connchurn 67.4k
  vs epoxy 15.6k conns/s, connchurn-tls 5.2k, burstidle 18714/20557/20935 vs epoxy 10636/10583/10731 MiB/s.
- Review(all) fixes: burstidle fails if the server exits in a burst or idle gap; summary keeps burst CPU%;
  connchurn rejects masked server frames and a CONTINUE without credit, and counts timeouts that end after the window.

## fix2 (2026-10-24)
- regress: a case with host TCP memory pressure (either box) gets verdict `invalid` (computed one kept as
  `verdict_raw` in results.json), so no WIN/LOSS/watch is read from it; header counts "N invalid". A LOSS whose
  re-run is invalid stays LOSS (note "re-run invalid"). Exit code logic unchanged (the pressure PROBLEM fails the run).
- regress (60.15 T08, 2026-10-30): any benchmark error on either side (wbench `errors` > 0 or an `error` record) also
  makes the case `invalid` (reasons in the row's `invalid` list: host TCP memory pressure, tcp_mem max, benchmark
  errors); before, only "more errors in new than base" was a PROBLEM and symmetric errors gave a normal verdict.
- regress idle (60.15 T09): every probe's record (settled/3 s KiB per conn, RSS samples, settle_s, rc; `error` with
  the stderr tail for a failed probe) goes to `raw/idle.jsonl` with `v`, `rep`, `pos`, so idle verdicts can be re-scored.
- compat wispjs-udp (60.15 T07): UDP loss under CPU load is real (kernel drops at a full socket receive buffer, one Udp
  RcvbufErrors per lost datagram), so the echo resends what is missing (up to 5 rounds after 400 ms without a reply,
  20 s deadline; a run with a loss waits 2 s more for late duplicates) and a new line per version checks that every
  lost transmission is covered by the kernel's Udp InErrors + SndbufErrors delta (IPv4 + IPv6; a server that drops
  datagrams itself still fails, checked with an echo that drops every 10th / always id 7; 0 replies fails at once).
  epyc2, 16 CPUs + 14 busy loops: before 6/12 runs failed (missing = RcvbufErrors delta in each), after 0/12 three
  times (8 of 36 runs lost 2-95 datagrams, all resent and accounted). A stream with more replies than sends fails.
- wbench --verify (60.15 T06; usage in bench/README.md): byte integrity at rate. Gold (Xeon 6154, 72 thr), master
  release 1850d055, server default threads, loopback, 16 reps x 5 s per case, verify on/off rotated, run twice
  (pre- and post-review wbench, same result): 0 content errors, 0 count mismatches, 0 missing END in all 96 verify
  runs; per run the client's received bytes == the targets' sent bytes (download, ~2.16 TB per 16 runs) and the
  client's sent bytes == the targets' received bytes (upload). Throughput verify on/off (paired HL, run 2):
  download 10x10 0.959 [0.945, 0.972] (22.7 -> 21.8 GiB/s; run 1 0.962), upload 1x1 1.010 (2706 -> 2753 MiB/s),
  upload 1 KiB x10 0.997 tie (2108 -> 2095). Headroom: the checker runs at ~27 GiB/s per core (fill 73), but in
  download 10x10 each of the 10 client connection tasks already uses ~1 core (client 58-59 CPU s per ~6.3 s run),
  so the per-connection check (~2.2 GiB/s each, ~8% of that core) costs ~4%. Verify never was the limit by
  itself; the published download numbers are now proven correct data, and a verified number reads ~4% lower.
- cross-host RAW `stderr`: only wbench's eprintln! lines (`wbench error:`, `run:`, `target:`, `debug:`), not the
  human summary that ssh -tt merges into stdout.

## wst browser (2026-10-24, lead decision)

subset, transport epoxy: wikipedia, hn, wikipedia-session, ws-echo, cloudflare-25MiB, busy-user. `--full` = all

## Non-inferiority verdict (2026-10-27, 60.12)

  exact signed-rank critical value; coverage 0.91 in a 400-trial simulation at n=16, 3% noise). `tie` now needs the worse-side
  bound within NI_MARGIN = 5% (roadmap 0.95); a non-significant result whose interval allows a > 5% cost is `unclear`
