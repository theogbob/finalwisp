# 20.28 Spliced frame size (64 KiB cap): PARKED (2026-10-24)

Pointers: 60.06 (base-1.1), browser reports in bench/browser/REPORT-busy-2026-10-24.md, REPORT-splice64-2026-10-24.md,
REPORT-s64a-2026-10-24.md; branches splice64 (a1ceb2b, fixed cap) and splice64a (926bc98, adaptive, MIXED_WINDOW 500 ms).

Question: the splice path sends Wisp DATA frames up to 256 KiB (other servers: 64 KiB). In one browser test (Scramjet,
local mirror, page load during a download) the big frames delayed page responses in the main-thread-bound client.
Variants:
- splice64: every spliced frame <= 65530 B (one splice-in, frame headers between pipe segments in flush).
  Laptop regress vs base-1.1: download 10x10 0.96 LOSS (reproduced), CPU/MiB +18%; download 1x1 1.23 WIN.
- splice64a: 64 KiB frames only for 500 ms after client DATA on the connection. Laptop: 0 LOSS, ratios drift 0.95-0.99.
  In a real browser TLS/h2 download the client sends DATA every ~14 ms (WINDOW_UPDATEs), so it is capped all the time.
Browser evidence over three runs: busy page load -156..-550 ms (run 1, local mirror), small fetch -143 ms p=0.004 (run 2),
nothing beyond the A/A noise (run 3; A/A itself 13/16 p=0.02). Real internet downloads rarely build 256 KiB frames
(base-1.1: 7-25% of bytes in >64K frames, max 68990 B), so the effect lives mostly on very fast local paths.
Decision (user): park. "Not noticeable but hurts perf and CPU usage." Re-open only with a real-browser case on a fast LAN
where big frames measurably delay pages; splice64a is the starting point. Test #22 (frame-size checks) lives on the branches.
