## F1: hs_step re-feeds a bad record after the handshake fails (second fatal alert)
- **Repro:** variant TLS, client sends the 5 bytes `16 03 01 00 00` (an empty handshake record). Others that do the same:
  an unknown content type, a record over 2^14+2048, and decrypt errors.
- **Root cause:** `tls.rs` hs_step, Fail branch: after the error it calls `process_tls_records(&mut buf[off..])` in a
  loop to collect the alert. A *deframe* error does not consume the bad record (rustls `DeframerIter` does not advance,
  `conn/unbuffered.rs:94-99` returns before the state is poisoned). Call 2 pops the queued alert. Call 3 finds the
  queue empty, deframes the same bytes again, and `handle_deframe_error` calls `send_fatal_alert` a second time
  (rustls `common_state.rs:638` `debug_assert!(!self.sent_fatal_alert)`).
- **Impact:** debug or test builds panic (with panic=abort in the release profile this would abort the whole
  server, but the release build has no debug assertions). Release base-1.1: the second alert is queued in rustls,
  never encoded, and the connection closes. The client sees exactly one alert. The loop ends (an Err breaks it).
  Severity: low (correctness/hygiene). It also blocks debug-assertion fuzzing of the TLS path.
- **Regression test:** `tls::tests::bad_record_fails_with_one_alert` (`cargo test -- --ignored bad_record`). It fails
  on base-1.1 in debug (panic) AND in release (`assert!(!conn.wants_write())`). It also covers the case the fix must
  keep: a TLS 1.3 ClientHello without our ALPN, where ServerHello + CCS + the encrypted alert are all queued and all must go out.
- **Proposed fix** (`server/fuzz/F1-proposed-fix.diff`, not applied): drain only what rustls queued, using its own
  queue as the stop condition:
  `while conn.wants_write() { match conn.process_tls_records(&mut buf[off..]).state { Ok(EncodeTlsData(e)) => encode, _ => break } }`.
  With the fix, all 34 tests pass in debug and in release, and clippy adds no new warnings. Review (3 vendors; reviewer B
  was unavailable): reviewer A and reviewer C both confirmed the root cause and rejected my first draft (collect one chunk),
  because it would drop the alert after ServerHello+CCS. The fix above is reviewer A's version.

## Harness lessons (for later fuzzing)
- cargo-fuzz's default `-Cdebug-assertions` also applies to dependencies. Build with `-O` plus profile settings to
  choose per crate.
- In fork mode each job rebinds the sink/listener in the same netns, so set SO_REUSEADDR. Kill fork-mode trees by
  process group (`start_new_session`). `bwrap --die-with-parent` does not cover the parent of bwrap.
- `cargo fuzz coverage` runs batches in parallel. With a fixed-port sink, replay in one process (`-runs=0 corpus`) instead.
