# 70.25 Own allocator for the big per-connection buffers ("option 2"): design spec (2026-10-30)

Status: DEFAULT since round 5 (2026-10-30, decision; cargo default feature `own-alloc`, old path `--no-default-features` / `NOFEAT=1 bench/release.sh`); the ONLY path since 60.18 #11 (after base-4: the `own-alloc` feature, the old path, the 70.11 block cache and the NOFEAT lanes are removed, branch nofeat-rm; release disasm identical to base-4); MAX_CLASS 128 KiB (round 4). See "Implementation notes" and "Round 5" at the end; first written as DESIGN ONLY. Branch slab-spec (worktree a worktree) from master 349e55e.
Start this only if the helper-thread trim (sibling trimthr) is not enough. Pointers: 70.23 (glibc trim, branch glibc-trim),
30.12 section "Phase 2" + "gtrim A/B" (100k idle), 70.22 (Scudo M_PURGE), 70.20 (growth chains), 70.11 (block cache),
70.14 (free_drained), 70.03 + 60.05 H7 (mem.rs pin_mmap_threshold), 20.26 (levels), 70.18 (swapped allocators).
Name: the code calls it the **pool** (server/src/pool.rs), not "slab": worker.rs already has `Slab` (the slot arrays).

## TLDR
| | |
|---|---|
| Problem | At 100k idle connections on a 65530-map host, glibc base-3 keeps 26-59 KiB/conn: past M_MMAP_MAX (32765 there) the 16 KiB+ buffers go to arenas, and free() does not return arena memory. malloc_trim fixes memory (0.8-1.0 KiB/conn) but one call at 100k takes 148-339 ms and the clients on that worker see it. |
| Pick | **Design B: route 16 KiB..1280 KiB allocations of worker threads, inside the existing `mem::Counting` global allocator, to a per-worker pool**: 26 page-multiple size classes (4 per doubling), 4 MiB chunks (one mapping each, 4 MiB aligned, header page), per-chunk free/dirty bitmaps, release with madvise(MADV_DONTNEED) in bounded batches at the end of a turn and at the idle sweep, empty chunks munmapped. Everything else (small sizes, > 1280 KiB, non-worker threads, pool failure) stays on glibc. |
| Why B | No worker.rs call-site changes (all buffers incl. frag, HashMaps, udp_buf are covered); the 70.11 cache and its rules map onto the pool's dirty set; ownership by address (a 4 MiB membership bitmap); no userspace lock or shared mutex; failure falls back to glibc (no new abort). |
| Mapping bound | chunks = pool bytes / ~4 MiB: ~1.9k at the measured 100k peak (7.5 GB) vs 32765 glibc mmaps + arenas today. VSZ <= live x 1.25 + workers x (classes in use) x 4 MiB, empty chunks unmapped after idle. |
| Size | ~550 production lines (range 450-700: the realloc/retire/failure protocol is what grows) + ~300 test lines. Deletes the 70.11 cache (~180 lines in mem.rs). Keeps pin_mmap_threshold (still guards > 1280 KiB and non-worker threads). Removes the need for trim against the M_MMAP_MAX spill; a cheap trim may still be wanted for the small-chunk residue (R5). |
| Accept | 100k idle on a 65530 host: no client stall > ~10 ms over the base-3 floor; memory <= ~1 KiB/conn RSS and cg is the target, but **B alone is expected at ~1.3-1.6** (glibc's own residue below the cap, R5): reaching <= 1 likely needs B + a (then cheap) trim or 4-12 KiB classes; CPU tie or win vs base-3 everywhere (VPS + big box); gates + fuzz clean; map-limit and RLIMIT_AS cases do not abort. |
| Main risks | burst CPU (copies instead of mremap, more page faults: 70.20; pend's quarter-step growth at L1+ copies ~4x its final size), TLB-shootdown / mmap_lock cost of release on 128-256 thread boxes, small (< 16 KiB) arena residue, allocator soundness (process-wide blast radius). |
| Confidence | medium (design is standard: mimalloc-style segments + jemalloc-style classes; the CPU effect is unknown until the A/B). |

Human version: instead of asking glibc to clean up (slow, and it stalls a worker for a third of a second at 100k
connections), finalwisp hands out its own big buffers from a few large memory blocks per worker thread. Every buffer
is page aligned, so when it is freed the pages can go back to the kernel one buffer at a time, a little per loop turn,
with no lock. glibc keeps doing everything small. Nothing else in the server has to change.

## SPEC
- Restatement: give finalwisp its own allocator for the big per-connection buffers (>= 16 KiB: rbuf, obuf, bulk, pend,
  frame/fragment buffers, anything that grows past the 16 KiB mmap threshold) so they never land in glibc arenas and
  idle memory goes back to the kernel without malloc_trim, with no client-visible stall and no CPU loss vs base-3.
- Inputs: GlobalAlloc calls (Layout size/align, old layout + new size for realloc) from any thread; per-worker level
  changes (20.26) and idle sweeps (IDLE_SWEEP_MS 2 s); WORKER_BUDGET; host page size; mmap/madvise/munmap results.
- Outputs: pointers with the GlobalAlloc contract (aligned, >= size, zeroed for alloc_zeroed); heap_bytes() with the same
  meaning as today (live requested bytes + bytes held for reuse); new metrics (pool_*); null only when glibc also fails.
- Edge cases: realloc across classes / pool <-> glibc; alloc_zeroed on a reused block; a free on a non-owner thread;
  a pointer from glibc with a pool-range size; mmap ENOMEM (RLIMIT_AS, map count, overcommit=2); madvise/munmap failure
  (munmap can need a VMA split at the map limit); level 2+ (cache_pause); a burst of 8k+ idle frees in one sweep;
  page size != 4096 (some aarch64); user address >= 2^47 (la57); THP=always; worker thread exit (never: run() -> !,
  panic = "abort").
- Constraints: win or tie everywhere (laptop and VPS); no per-host tuning, no sysctls, no env knobs; free when off
  (here: always on, so it must tie); boring correct code, no dependency (libc only); hot path cost <= the 70.11 cache's;
  no shared mutex; release work bounded per loop turn (target <= ~2 ms); the mapping count stays far below 65530 at
  100k+ connections; VSZ RLIMIT_AS-friendly (no big up-front reservation: Scudo's 188 GB is an anti-goal, 70.22).
- Simplest path (ladder): (1) trimthr's helper-thread trim, if it removes the stall: then do NOT build this.
  (2) glibc knobs cannot: M_MMAP_MAX is bounded by max_map_count (70.03, V2 in 70.23), arena frees need a trim.
  (3) swapped allocators were measured and lost: musl (CPU, 30.12), Scudo (CPU 1-4%, 30.12), je/mi/sn (memory, 70.18).
  (4) the smallest in-tree fix = change only the backend of the sizes that cause it (16 KiB+ on workers), behind the
  allocator we already own (mem::Counting). That is design B.
- Assumptions (flag for correction): per-connection buffers never cross threads, but some >= 16 KiB blocks can (Inbox.fds,
  2.7), so the remote-free path is mandatory; x86_64 Linux, 4 KiB pages, 47-bit
  user addresses (release builds are x86_64); callers pass the allocation's layout to dealloc/realloc (GlobalAlloc
  contract); MADV_DONTNEED zero-fills private anonymous pages on the next touch; no MSG_ZEROCOPY / vmsplice / io_uring
  fixed buffers in the tree (grep: none).
- Possible drift paths: the 100k residue turns out to be small-chunk arena memory (R5): scope grows to 4/8/12 KiB classes
  or a (then cheap) trim; burst CPU loses (R1): raise or lower MAX_CLASS / keep glibc mremap for the top classes;
  release cost on 256-thread boxes (R2): batching/munmap rules change; someone wants fallible growth: design A
  (explicit Buf) on the same pool core; trimthr is enough: shelve this doc.
- Confidence: medium.

## 1. Designs compared
All three need the same "pool core" (classes, chunks, release). They differ in how allocations reach it.

| | A: explicit `Buf` type | **B: route inside mem::Counting (pick)** | C: extend the 70.11 cache to own all big blocks |
|---|---|---|---|
| What | replace `Vec<u8>` in Client/Target (rbuf, obuf, bulk, pend, frag, hs.out, udp_buf) with a pool-backed Buf; ws::push_frame / http::simple take it | Counting::alloc/realloc/dealloc send 16 KiB..1280 KiB, align <= 4096, on pool threads (workers) to the pool; the rest to System as now | keep glibc blocks, cache more of them (all sizes, more slots) |
| Covers | only the converted buffers (frag, HashMap growth, future Vecs: no) | every >= 16 KiB Rust allocation on a worker | n/a |
| Call-site churn | ~100-150 edits in worker.rs + ws.rs/http.rs/tls.rs; a Vec API subset to re-implement (reserve, reserve_exact, extend_from_slice, resize, truncate, drain(..n), shrink_to, set_len, spare capacity) | none in worker.rs (2 calls: pool_release at the turn end, wake while pending); main.rs pool_on replaces cache_on | small |
| Ownership | the Buf knows it is a pool block; Buf must be Send (Worker moves to its thread) with an invariant | membership bitmap (address -> is pool chunk) + chunk header (owner, class) | n/a |
| Failure | can be fallible (Err -> close the client), but every site must handle it | falls back to System (glibc, today's behaviour); null only if glibc fails too | n/a |
| Fixes 100k? | yes for the converted buffers | yes | **no**: the blocks still come from glibc; a freed one still lands in an arena past M_MMAP_MAX. Variant "cache blocks are our own per-block mmaps" = one mapping per block = 160k+ mappings at 100k busy conns (> 65530; VMA merging is not guaranteed). Rejected. |
| Other | `Vec<u8, A>` (allocator_api) would avoid the API work but is a nightly feature; rust-version 1.88 says stable only (60.04 F10): rejected | the 70.11 cache semantics move into the pool (dirty set) | |
| Size | pool core ~350 + Buf ~200 + call sites | pool core ~350 + routing ~100 | |

Pick **B**: same core, least churn in the hot path, covers everything, no new abort path, keeps the code that tuned the
cache (levels, sweeps) as rules instead of a second cache. A stays the fallback if fallible growth is ever wanted.

## 2. Design B in detail

### 2.1 Routing (mem::Counting)
- Pool thread = a worker that called `pool_on()` (main.rs:457, where cache_on is called now, inside the spawned thread;
  not in Worker::new, which runs on main). Thread-local state, const init, no destructor (as MY_SLOT / CACHE today), and
  the allocator paths never allocate (fixed arrays and intrusive lists in chunk headers only: a Vec in the TLS state would
  re-enter GlobalAlloc once it passed 16 KiB). pool_on fails closed (pool stays off for that thread) if the page size is not
  4096, or the pool id space (u16; MAX_POOLS 1024) is full.
- alloc(l): `pool_ok(l) = 16 KiB <= l.size() <= MAX_CLASS (1280 KiB) && l.align() <= 4096 && pool thread`. If ok and the
  pool returns a block: use it. Else System.alloc (today's path). alloc_zeroed: same; a clean (fresh or released) block
  needs no memset (zero-fill on touch); a dirty reused block gets write_bytes(0, size) (as the 70.11 cache does).
- dealloc(p, l): if `l.size()` is in the pool range and `is_pool(p)` (bitmap): pool free (owner) or remote free (2.7).
  Else System.dealloc. (Sizes outside the range never reach the bitmap check: one compare on the common path.)
- **Soundness invariant** (review, all three seats): every live pool block's current layout is in the pool domain
  (16 KiB..MAX_CLASS, align <= 4096) and maps to its chunk's class. dealloc/realloc read the class from the chunk header,
  never from the layout (debug-assert that the layout rounds to it). A pool pointer is never passed to System.realloc/free.
- realloc(p, l, new), by origin (membership bitmap, not thread identity):
  1. pool -> same class: return p (account the delta).
  2. pool -> other class, > MAX_CLASS, < 16 KiB or the thread is not the owner: allocate the new block (pool or System),
     copy min(old, new), free the old (owner free or remote free). Shrink moves too (shrink_to's purpose is to free memory;
     note: pend.shrink_to at L2/L3 targets keep/4 = 16384, exactly the pool's lower bound, worker.rs:3445).
  3. System -> in range, pool thread: pool block + copy + System.dealloc. This rule decides the idle result: every client's
     rbuf starts as vec![0u8; 4096] and obuf small, both glibc; 70.11's cache falls through to System.realloc on a miss
     (mem.rs realloc), the pool must not.
  4. System -> anything else (e.g. main-thread Slab arrays of 1 MiB growing past it): System.realloc (mremap) as today.
  5. A move whose pool allocation fails tries System; only if that fails too it returns null with the old block and the
     accounting unchanged (Rust then aborts, as today).
- Accidental clients (inherent to routing in Counting, review): any >= 16 KiB allocation on a worker enters the pool:
  HashMap tables (DNS cache), Inbox.fds pushed by this worker, Vecs grown on the worker. They bring patterns the buffer
  paths do not have (HashMap shrink): one test each.
- Growth semantics: inside the pool growth COPIES (no mremap): a doubling chain to 1280 KiB copies < 1.25 MiB per buffer
  lifetime (geometric sum). Above MAX_CLASS the block moves once to glibc (one copy <= 1280 KiB), then grows by mremap as
  today. This is the main CPU question (R1).

### 2.2 Size classes
**Historical numbers (60.16, marked 2026-10-30):** the design below says 26 classes to 1280 KiB. The code has **13 classes,
16 .. 128 KiB** (pool.rs CLASSES / MAX_CLASS; round 2: 18 classes to 320 KiB; round 4, 2a56a5b: 128 KiB). Larger buffers go
to glibc. Read the TLDR "Pick" row the same way.
4 per doubling, page multiples, 16 KiB .. 1280 KiB (26 classes): 16 20 24 28 32 40 48 56 64 80 96 112 128 160 192 224 256
320 384 448 512 640 768 896 1024 1280 KiB. class_of(size) in O(1) (leading_zeros + 2 bits, as jemalloc's size2index).
Measured chains (70.20, 70.11) and where they land (virtual waste = class - request; resident waste only on a reused dirty block):
| buffer | sizes | class (waste) |
|---|---|---|
| rbuf | 16384, 32768, 65536, 131072, 262144 (RBUF_MIN doubling to rbuf_max) | exact (0%) |
| obuf / bulk | 65539 -> 131078 -> 262156 -> 524312 -> 1048624 (reserve(room + CHUNK) doubling) | 80/160/320/640/1280 K (20%); 2097248 (L0) -> glibc |
| pend (L0) | first unsent length x 2^k, ~16K -> ~1 MiB in echo bursts | any class (<= 25%); > 1280 K -> glibc |
| pend (L1+) | reserve_exact by a quarter | any class |
| udp_buf | 8 x 65530 = 524240 | 512 K (0%) |
| big frames / frag | up to MAX_FRAME 16 MiB | <= 1280 K in pool, above glibc |
Resident memory of a fresh block = pages touched (Vec writes only up to len), same as glibc's page-rounded mmapped chunk
(65539 -> 17 pages either way). Optional later (not part of this change): CHUNK = 65527 makes room + CHUNK = 65536 for the
first obuf (UDP_SLOT = CHUNK still >= 65527, the IPv6 max): the obuf chain would then fit exact classes. Needs its own A/B.
MAX_CLASS 1280 KiB covers the obuf/bulk chain to 1 MiB and most of pend. Above it glibc serves (mmapped chunks, pinned
threshold): their count is <= heap / 1.25 MiB, so the M_MMAP_MAX spill needs > 40 GiB of such buffers live.

### 2.3 Chunks, regions, VSZ and mapping count
- Chunk = 4 MiB, 4 MiB aligned (mmap 8 MiB PROT_READ|WRITE, MAP_PRIVATE|ANONYMOUS|NORESERVE, munmap the unaligned head
  and tail: 3 syscalls per chunk, ~once per 4 MiB of growth) + madvise(MADV_NOHUGEPAGE) once (THP=always would fault 2 MiB
  pages into an aligned chunk and split them at every block release). One owner (worker) and one class per chunk.
- Page 0 = header (~300 bytes used): magic, owner pool id (u16), class (u8), nblocks, bump (blocks never handed out),
  live (owner-only), free and dirty bitmaps (<= 255 blocks: 4 u64 each), list links, remote-free stack (AtomicPtr).
  Blocks start at page 1. Blocks per chunk: 255 (16 K) .. 3 (1024 K / 1280 K); fill 75-100% (table in the worker data).
- Membership: static bitmap of 4 MiB granules over 2^47 bytes = 2^25 bits = 4 MiB BSS (VSZ; RSS only the touched words:
  1-2 pages). Bit set (Release) by the owner after mmap, cleared before munmap. A chunk mapped at >= 2^47 is unmapped and
  the allocation falls back (la57). is_pool(p) = one load; the header is read only when the bit is set (a glibc pointer
  can sit next to unmapped or PROT_NONE arena space, so masking alone is not safe).
- Mapping count: <= one VMA per chunk (adjacent chunks with equal flags may merge, so /proc/self/maps can show fewer;
  MADV_DONTNEED and the whole-chunk NOHUGEPAGE never split; the alignment trim needs one extra mapping for a moment).
  Expected at 100k conns at the measured base-3 peak (VmHWM 5.0-7.5 GB, 30.12): ~1.2k-1.9k chunks; upper bound
  ~1.67 x live / 4 MiB + partial chunks. Not a function of the connection count: idle = a few chunks per worker. 65530 mappings would need ~256 GiB
  of pool memory. glibc keeps its own mmaps (> 1280 K, non-worker threads) under the 70.03 half-limit rule.
- VSZ (review: chunk fill counts too): <= live requested x 1.25 (class rounding) / 0.75 (worst chunk fill, the
  1024 KiB class: 3 blocks + header in 4 MiB) = ~1.67 x live, + per worker one partly used chunk per class in use (worst
  case 26 x 4 MiB = 104 MiB per worker; 256 workers all classes 26 GiB; typical a few classes = 10-30 MiB per worker) + the
  4 MiB bitmap. The header page costs a block only in the 1024 KiB class (3 instead of 4; 256 K: 15 of 16; 512 K: 7 of
  8). Lever if it matters: put the header page just below the aligned base (mapping [base - 4 KiB, base + 4 MiB)), at the
  price of non-adjacent chunks; or an owner byte-map per granule (32 MiB VSZ) instead of headers. Header page chosen: one
  structure, O(1), no extra VSZ. Same order as glibc's own arena reservations (64 MiB HEAP_MAX per arena). Empty chunks are unmapped after
  idle (2.5), so VSZ falls back. No up-front reservation. MADV_DONTNEED does not lower VSZ; only munmap does. Under RLIMIT_AS or overcommit=2 (MAP_NORESERVE ignored: commit
  = VSZ) a chunk mmap fails -> System fallback (2.9).

### 2.4 Allocation and free (owner thread, no atomics except the bitmap/remote paths)
Per class: `cur` chunk, a list of chunks with dirty free blocks, a list of chunks with clean free blocks, counters
(dirty bytes, low-water). Block states: live | dirty free (pages resident, counted) | clean free (released or never
touched, not counted).
- alloc order: dirty free block (warm, no fault: this is the 70.11 cache hit) -> clean free block -> bump in `cur` -> new chunk.
  Finding a block = find-first-set over <= 4 words of the chunk's bitmap.
- free: set free + dirty bits, live -= 1, chunk onto the class's dirty list if not on it. No syscall.
- Hot-path cost: TLS access + class_of + one bitmap scan + header writes. 70.11's cache_take scans up to 256 slots and
  calls malloc_usable_size on put; this is not slower.

### 2.5 Release policy (per worker, no userspace lock, bounded)
The dirty set is the old block cache. Its rules carry over (70.11, 60.09 M2/M4b):
- cap = min(16 MiB, worker budget / 16) (budget off: 16 MiB); at level 2+ (cache_pause) L2_BYTES = 1 MiB.
- End of every loop turn (`mem::pool_release()` in Worker::run, after reap_dead and the sweep): if dirty bytes > cap,
  release the excess: walk the class dirty lists (oldest first), turn each run of contiguous dirty blocks in a chunk into
  ONE madvise(MADV_DONTNEED) (the bitmap gives address order and merges for free), mark them clean, account(-bytes).
  Bounded per turn on three axes (review: bytes alone do not bound IPI rounds): <= RELEASE_CALLS (16) madvise calls,
  <= RELEASE_BYTES (8 MiB; one merged call is split at 2 MiB), and an elapsed-time check between calls (stop after
  ~1 ms). Start values; the 100k stall probe may argue them up. The rest continues next turn. Below the cap: nothing
  (steady churn keeps its working set).
- Wake rule (Worker::run, worker.rs:958): epoll timeout 0 while a release backlog exists (as `ready`); never -1 while any
  chunk of this worker is mapped (replaces `cache_held() > 0`): a remote free can arrive at an idle worker and only the
  owner drains it, and the sweep must run to unmap empty chunks. Without timeout 0, the ~0.8 GB that the first sweep
  frees per e5 worker would take 2 s per batch.
- Order at every release: drain the remote stacks into the bitmaps first, then madvise (a remote link word written after
  the advise would break both the list and the zero-fill), then munmap.
- At each idle sweep (after cache_sweep's place in run()): release what the dirty set did not need since the last sweep
  (its low-water mark), or all of it if no dirty block was taken (M4b; a flush lowers the low-water mark too, mem.rs
  cache_free_first). Chunks with live == 0 (remote frees drained: a remote-freed block counts as live until then), no dirty
  blocks, empty at the previous sweep too, are unmapped: clear the membership bit, munmap; on munmap failure set the bit
  again and keep the chunk (no pointer into it exists). <= 4 munmaps per turn: munmap takes mmap_lock for write, and on
  kernels < 6.4 (no per-VMA fault lock) a waiting writer blocks every thread's page faults.
- Level 2+ (cache_pause port): at the transition flush the dirty set down to L2_BYTES (bounded batches, same turn
  onward), cap L2_BYTES while at level 2+, the full cap again below level 2; port the tests at worker.rs:5015-5037 and
  the cache tests in mem.rs.
- Locks: "no lock" is a userspace statement. madvise(DONTNEED) walks under mmap_lock read (+ page-table locks), mmap and
  munmap take it for write; each call flushes TLB entries on the CPUs running our threads (batching varies by kernel).
  The stall can therefore land on another worker; the bounds above and the 100k probe on every worker cover that.
- 100k idle case: the sweep frees ~8k idle clients' buffers per worker at once (~0.8 GB per worker on e5). Blocks
  allocated together are contiguous, so runs are long (~1 call per 2 MiB piece): ~400 calls per worker,
  with the bounds above ~100 turns of <= ~1 ms (page zap ~0.1-0.3 us/page), events served between turns. malloc_trim did all of it in one 148-339 ms
  call under arena locks. (Base-3 below the cap did one munmap per block in the sweep turn: not bounded either.)
- MADV_FREE was considered and rejected: the pages stay in RSS (and memory.current) until the kernel needs them; users and
  wst idle read RSS. DONTNEED is the honest number.

### 2.6 Memory accounting (heap_bytes, levels)
Live pool blocks count at their requested size (as today, so 20.26 level thresholds and Host mode keep their meaning);
dirty free blocks count at the class size until reused or released (as cached blocks count at their usable size in 70.11);
clean blocks and VSZ do not count; each mapped chunk's header page counts 4 KiB (review: ~7.6 MiB at 1.9k chunks,
resident). realloc within a class: account(new - old). No change to USED, LEVEL, the sampler or SLAB_UNTOUCHED.
Seats disagreed on live blocks at class size (reviewer A: closer to the cgroup's view) vs requested size (reviewer C: class size
inflates Host-mode usage ~20% on the 65539 chain). Requested size is kept: a fresh block's resident pages = the pages its
Vec touched, i.e. the requested size rounded to pages, the same as glibc's mmapped chunk today. Cgroup mode reads
memory.current and does not depend on this counter at all.

### 2.7 Cross-thread frees (checked in code, 349e55e; corrected by the review)
No per-connection buffer moves: Client and Target (rbuf, obuf, bulk, pend, frag) live in their worker's `Slab`
(worker.rs) and are allocated, grown and freed only there. But some >= 16 KiB blocks DO cross threads:
- **Inbox.fds** (net.rs:671-720, review): accept balancing (worker.rs ~1173) pushes fds into a PEER's Vec; that Vec
  grows on the pushing worker (a pool block once >= 4096 fds are queued, e.g. a stalled peer in a 10k conn/s burst) and is
  dropped on the receiving worker after drain()'s mem::take. A real worker -> worker remote free (rare).
- Inbox.q (Vec<DnsResp>), DnsResp.addrs: grown on DNS threads (not pool threads: System blocks), freed on workers.
- Worker::new runs on main before the move (main.rs:449-458): its 1 MiB Slab arrays and IoVecs are System blocks; the TLS
  cert set can be dropped on a worker (tls.rs reload). All System, handled by the bitmap miss.
So membership is "this address is a live pool chunk", never "I am a worker". The allocator must be sound for any free: a non-owner dealloc pushes the block onto its chunk header's remote stack (lock-free Treiber push,
link in the block's first word) and sets REMOTE_PENDING[owner] (static [AtomicBool; MAX_POOLS]); the owner checks its flag
once per turn and drains (swap the stack to null: only the owner pops, all at once, so no ABA). The pushing thread
needs no pool TLS of its own (CACHE.try_with style: DNS threads, main, exiting test threads). A non-owner realloc =
alloc on the calling thread + copy + remote free. Metric pool_remote counts them (expected ~0). Alternative (reviewer C): a
per-chunk mutex taken only on remote free and drain; the push-only stack is ~10 lines and needs no lock, so it stays.

### 2.8 splice / kTLS / sendmsg
Pool blocks are plain private anonymous memory. read/write/writev/sendmsg/recvmmsg copy; kTLS sendmsg copies into skbs;
splice uses the client's pipe, never these buffers. So releasing a free block's pages is safe. Rule for later: MSG_ZEROCOPY,
vmsplice or io_uring fixed buffers would need "the kernel is done" before a block is freed (true for any allocator).

### 2.9 Failure behaviour
Today an allocation failure is a null from glibc -> handle_alloc_error -> abort; the buffers use infallible reserve /
reserve_exact / extend (worker.rs:3080, 3334, 3408), so there is no other out-of-memory path (memory pressure is handled
earlier by the levels, 20.26). The pool adds no abort, and it does not remove that one: if the pool AND glibc fail,
Rust aborts as today.
- chunk mmap fails (ENOMEM: RLIMIT_AS, map limit, overcommit=2) -> that allocation goes to System (base-3 behaviour,
  incl. glibc's own mmap -> arena fallback); no new chunk attempt on that worker until the next sweep (no failing mmap per
  alloc); counter pool_fallback.
- madvise fails -> the blocks stay dirty (usable, counted), retried at the next sweep; counter.
- munmap fails (it can need a VMA split, ENOMEM at the map limit) -> keep the chunk as clean and empty; retry next sweep.
- Corruption checks: debug builds assert header magic, owner, and "free of a block whose free bit is set" (double free).

## 5. Risks
- R1 burst CPU: growth copies instead of mremap and fresh blocks fault their pages (70.20: base-3 had fewer faults than
  je/mi because of mremap). Echo 100x10 is the case for doubling (total copy ~ final size); pend at L1+ grows by quarters
  (reserve_exact(max(data, cap / 4)), worker.rs:3408): ~4x its final size in memcpy up to MAX_CLASS (review), so
  the stalling-sink upload is the second case. Levers: MAX_CLASS 320 KiB (covers rbuf and the obuf chain to 262156, the
  idle case; glibc mremap above; review suggests starting there), class headroom.
- R2 release cost on many-thread boxes: each madvise/munmap flushes the TLB on every CPU running our threads. Long runs
  (1 call per chunk), bounded batches, munmap only after a second idle sweep. Measure on a 128-256 thread box.
- R3 VSZ/commit: worst case 26 GiB VSZ at 256 workers using all classes; overcommit=2 hosts charge it. Fallback, not
  abort; but memory reporting tools show it. Lever: 2 MiB chunks (halves it, more chunks).
- R4 soundness: an allocator bug is memory corruption. Mitigation: small code, stress + fuzz with shadow checks, debug
  asserts, the remote path kept trivial, the 70.11 tests ported.
- R5 small-chunk residue: glibc below the cap still kept 4.1-4.4 KiB/conn at 2000 conns and 1.6 at 20k (gold); the
  marginal cost from 2000 to 20k is (20000 x 1.6 - 2000 x 4.1) / 18000 = ~1.3 KiB/conn, so part is per process and part
  per connection. Trim returned it (70.23: 4.7 -> 1.3 below the cap; 30.12: 0.8-1.0 at 100k). The pool does not touch
  < 16 KiB, so B alone likely lands at ~1.3-1.6 KiB/conn at 100k, not <= 1 (seats: reviewer A estimated 3-4 from the 2000-conn
  number, which includes the per-process part; reviewer C expected ~1). Levers: B + V1 trim (cheap then: gold trimcap2, where
  big blocks stayed out of the arenas, had trim_max 3.8-7 ms), or 4/8/12 KiB classes (the 4 KiB first rbuf, handshake
  buffers; resident waste < 1 page per block). This is a user judgment call if B alone measures above 1.
- R6 tooling: valgrind/heaptrack see mmaps, not pool blocks (minor; glibc builds of the tests still work).
- R7 a future thread that allocates big buffers and exits would leak its chunks (as the 70.11 cache documents): pool_on
  only on workers, which never return.
- R8 helper-thread trim is not free either (review, for the trimthr comparison): malloc_trim holds each arena's lock
  for its walk, so off the worker it stalls whichever threads malloc/free in that arena meanwhile (tcache hits excepted).

Deviations / details decided while building (none changes the design):
- Release order: largest class first (more bytes per madvise call), oldest dirty chunk first within a class. 70.11
  freed the oldest blocks; here only the amount follows the low-water rule, not which blocks.
- `owed` (bytes the last sweep decided to release) is paid in bounded batches; a dirty hit lowers it (the block was
  needed after all); bytes a failed madvise left dirty stay owed at the next sweep (review).
- MADV_NOHUGEPAGE failing with anything but EINVAL (ENOMEM: a VMA split at the map limit) -> the chunk is not used
  (review): THP=always would otherwise fault 2 MiB pages into it.
- A half-failed alignment cut unmaps only the still-owned range (review, P1: the head may already be
  another thread's mapping).
- Pool ids are recycled when a thread turns its pool off with no chunk left (tests, fuzz threads); workers never exit.
- metrics: cache_hit / cache_miss keep their keys (pool: dirty hit / clean or fresh); new keys with the feature:
  pool_fallback, pool_remote, pool_madvise, pool_munmap, pool_madvise_fail, pool_munmap_fail, gauges pool_chunks,
  pool_dirty_kib, and pool_release_max_us (process max of the whole turn-end step, elapsed). 60.16 (base-4 tidy):
  pool_release_cpu_max_us beside it = the longest thread CPU time of that step (CLOCK_THREAD_CPUTIME_ID, read only
  when release() does work; the common turn returns before any clock read). It tells syscall work (cpu ~ elapsed)
  from waiting on mmap_lock or preemption (cpu << elapsed), e.g. the 30.14 pre-soak 65 / 255 ms elapsed maxima. The
  two maxima are process-wide and can come from different calls.
- Test-only feature `pooltest` (never in a release; the 70.24 trimtest method): every allocator call timed with a
  ru_nvcsw "blocked" flag, calls attributed in/out of any worker's release, release elapsed + CPU time, chunk-map
  times, FW_PT_MMAP_MAX (forced-arena repro).
- Size: pool.rs 879 lines before the model/tests (719 non-comment) vs the 550 (450-700) estimate: the failure paths,
  comments and the release/sweep bookkeeping grew; + 160 lines model (shared with the fuzz target) + 560 test lines.
  mem.rs +277 (incl. ~100 pooltest), worker.rs +81 (mostly the ported level-2 test), metrics.rs +59. The 70.11 cache
