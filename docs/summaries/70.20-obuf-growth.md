# 70.20 obuf / buffer growth under glibc: the "mmap churn" weak spot re-measured (obuf, 2026-10-29)

Branch obuf-growth from master fb48ca6 = base-3 + docs).
Laptop only, nice -n 19, shared with other jobs and the maintainer's VMs. **Syscall and page-fault counts only, no timing.**
Data: raw data (not published): obdrv.py (strace -f from start, -c or full with sizes, optional -k stacks),
obwin.py (server under `strace -f --seccomp-bpf -ttt` from start; calls counted by timestamp inside a window of the run;
minflt from /proc/PID/stat over the same window), *.jsonl results, st/ raw strace files, bins/ (fw-base3 = release.sh of
fb48ca6, md5 55d175ae = base-3; fw-dbg = throwaway instrumented build, not committed).
Reference allocators (70.18 binaries, like-for-like): je-tuned = allocscout fw-je with
`_RJEM_MALLOC_CONF=background_thread:true,tcache_max:8192,dirty_decay_ms:1000`; mi-tuned = fw-mi with
`MIMALLOC_PURGE_DELAY=0 MIMALLOC_ALLOW_THP=0` (env stands in for the built-in setting, as in 70.18).

## TLDR
- **The 70.18 "2.4-3.2 mmap-family calls per MiB" is not a rate.** It is mostly front-loaded buffer growth (Vec doubling,
  one mremap per step above the 16 KiB mmap threshold) + teardown, divided by the MiB of a 2 s run. Same runs at 2 s vs 6 s:
  echo 10x10 1.08 -> 0.50/MiB, echo 100x10 4 thr 2.79 -> 1.01, echo --mem-budget 128M 2.80 -> 1.12 (total calls almost
  constant). The lead replaced the "< 0.5/MiB in a 2 s run" bar with: steady-window calls/MiB + burst calls per stream +
  minflt, CPU later on a VPS.
- **The biggest grower is pend (upload backlog per stream), not obuf** (strace -k stacks): in an echo burst each stream's pend
  doubles 16 KiB -> ~1 MiB (about 7 mremaps per stream); obuf/bulk/rbuf are per connection. 70.18 blamed obuf without stacks.
- **Level 0, late window (t = 3..6 s of an 8 s echo): all three are low**: base-3 0.015-0.048 calls/MiB, je-tuned
  0.007-0.066, mi-tuned 0.004-0.058 (mmap+munmap+mremap+madvise). At echo 10x10 base-3 is 2-8x je/mi, but at <= 0.05/MiB.
  Page faults per MiB are of the same order (base-3 1.5-13, je 1.4-20, mi 2.3-35). Equality is not shown; the gap is small in
  absolute terms.
- Where base-3 makes clearly more calls (same method, like-for-like):
  - **burst** (first 2 s of a fresh server, teardown excluded): echo 10x10 0.24-0.26/MiB (~5.8 calls per stream) vs je
    0.06-0.08, mi 0.05-0.06; echo 100x10 4 thr 1.25-1.44/MiB (~8 calls per stream) vs je 0.24-0.36, mi 0.13-0.17. But base-3
    takes FEWER page faults there (38-46/MiB vs je 55-59, mi 78-100), consistent with mremap keeping the pages a buffer already
    touched (the others copy into fresh memory; not proven to be the whole reason).
  - **under memory pressure with level changes** (--mem-budget 128M, Host-mode budget, levels 1-3): 0.16-0.25/MiB vs je
    0.01, mi 0.02-0.04: obuf/bulk regrow 64K -> 512K at level 1 and are freed when drained at level 2 (70.14 rule).
- **70.11 backlog item "obuf grows to 512 KiB at L2 although out_high = 64 KiB": not a flow-control bug.** Instrumented build:
  the 512 KiB growth happens at LEVEL 1 (out_high 256 KiB); at level 2 the obuf never grew past 131078 in the runs. Analytic
  ceiling of read_target at L2: about 4 x (room + CHUNK) = 262156 (reachable, rarely; see 5). The frees at level 2 are
  70.14's intended "free drained buffers above keep". Closed.
- **Verdict: no code change.** The extra calls follow growth steps per buffer lifetime (bursts) and level changes (pressure),
  not bytes moved. Every in-tree option found costs memory, accounting, or copies (section 6). CPU effect: NOT measured
  (laptop rule); the direct test is 70.18's arm B (base-3 vs je-tuned) on a VPS with burst/pressure cases, if still wanted.
Confidence: high on the counts, the pend attribution and the 70.11 explanation (instrumented, repeated); medium on the
per-MiB ratios (normalization, see 3); none on CPU.

## 1. What grows above the mmap threshold (strace -k stacks + addr2line, base-3, echo 10x10 and --mem-budget 32M)
| buffer | site | growth | freed |
|---|---|---|---|
| pend (upload backlog per stream) | write_target extend_from_slice (L0, doubling) / reserve_exact by a quarter (L1+) | 16K -> 32K -> ... -> 1-2 MiB at L0 in echo bursts | stream close; idle sweep; flush_pending shrink_to above min(4 MiB, keep) |
| obuf / bulk lane (per client) | read_target `reserve(room + CHUNK)` | 65539 -> 131078 -> 262156 -> 524312 (-> 2 MiB at L0) | close; idle sweep; free_drained (70.14): L1 >= 2 MiB, L2+ > 132 KiB |
| rbuf (per client) | read_client 16K -> rbuf_max 256K | doubling | idle sweep; pressure levels |
Every step above 16 KiB is one mremap (glibc mremap_chunk: no copy, no new page faults); the first allocation of a buffer is an
mmap unless the 70.11 block cache has a block of 16-132 KiB; the free is a munmap unless cached.
Side observation (not this task: credit, 20.30): in an echo 100x10 burst at L0 each stream's pend reaches ~1 MiB (mremap
528384 -> 1052672 x ~700-1000 per 2 s), i.e. ~1 GiB of upload backlog for 1000 streams; consistent with 70.18's burst HWM
1.2-1.6 GiB. That is the memory to look at in bursts, not the syscalls.

## 3. Late window (obwin.py: 8 s run, calls in t = 3..6 s; 2 reps rotated)
Method notes (review): traced set mmap, munmap, mremap, madvise, brk; the ratio counts the first four (same set as 70.18 3.3,
so the allocators' madvise purges count). MiB = the run's mean rate x the window length: an ESTIMATE (traffic is not
stationary, worst under pressure); raw counts are in fair_win.jsonl / win2.jsonl. The window starts after wbench is
launched, not at its first byte. The server runs under strace (seccomp-bpf: only traced calls stop), which perturbs a little.
The pressure runs have no cgroup limit: the budget is Host mode (heap + host TCP memory, mem.rs), so sibling traffic on the
laptop can move levels. A 3 s window holds about one idle-sweep period per worker.
mmap+munmap+mremap+madvise per MiB / minflt per MiB:
| case | base-3 | je-tuned | mi-tuned |
|---|---|---|---|
| echo 10x10, 1 thr, L0 | 0.017, 0.031 / 1.5, 2.8 (+ single run 0.024 / 2.0) | 0.007, 0.007 / 1.4, 1.5 | 0.004, 0.004 / 3.0, 2.3 |
| echo 100x10, 4 thr, L0 | 0.048, 0.015 / 13.3, 4.7 (+ 0.036 / 10.6) | 0.022, 0.066 / 8.0, 20.5 | 0.021, 0.058 / 13.1, 34.5 |
| echo 10x10 --mem-budget 128M (levels 1-3) | 0.248, 0.177 / 3.4, 2.5 (+ 0.158 / 2.4) | 0.011, 0.013 / 1.5, 1.3 | 0.036, 0.021 / 3.6, 2.9 |

## 5. 70.11 backlog: obuf at level 2 (throwaway instrumented build fw-dbg: eprintln on every obuf/bulk capacity change in
read_target, and on every free_drained free, with the level)
- --mem-budget 128M / 32M / 16M / 24M (no strace on the hot path): the server stayed at level 1; obuf and bulk grew
  65539 -> 131078 -> 262156 -> 524312 there; no free_drained frees.
- 48M (levels 1 <-> 2 <-> 3, 14 logged + 4 unlogged changes in 4 s): growth to 524312 only at level 1 (31 obuf, 5 bulk);
  at level 2 only 0 -> 65539 (36) and 65539 -> 131078 (34); at level 3 the same <= 131078; frees at level 2: 26 x 524312,
  14 x 262156 (70.14 rule: drained and > keep 132 KiB).
- Bound (read_target, TCP copy path and bulk lane only): a read happens only with pending < out_high (64 KiB at L2) and
  adds <= room + CHUNK; a sent prefix >= the lane's unsent bytes is compacted first, so len < 2 x unsent < 128 KiB and the
  reserve doubles at most to about 4 x (room + CHUNK + bytes queued before the first read) = 262156 from an empty Vec. It is
  reachable (review: e.g. len 95539, a partial send of 40000 leaves 55539 unsent with ohead 40000 < 55539: no
  compaction, reserve -> 262156), then freed at its next full drain (> keep 132 KiB). Not seen in the instrumented runs.
  524312 is not reachable at L2 on this path; at L1 (out_high 256 KiB) 524312 and even 1048624 are.
  flush_dirty's compaction (ohead >= OBUF_COMPACT 1 MiB) plays no part at these sizes.
  Not covered (not measured): small control frames (CONTINUE, PING/PONG, CLOSE, INFO) appended without the out_high check,
  and read_udp, which checks out_high once per recvmmsg batch of up to UDP_BATCH = 8 datagrams (up to ~512 KiB) and has no
  read-path compaction (review: a slowly draining UDP client's obuf can hold up to 1 MiB of sent prefix before flush_dirty's
  rule compacts it). Backlog candidate, separate from this task.
- "Freed at level 2" means: at the L1 -> L2 set_level drop if drained (only when no upload target is staged), else at its
  next full drain at level 2; a client that never fully drains keeps its capacity.
- So the 2026-10-26 observation (strace with -f and level changes) was level-1 growth freed at level 2. Closed; no change.
  Under pressure the level-change rate drives the cost (sampler hysteresis, 20.26; not this task).

## 6. Options considered and not taken
- Bigger block cache (classes up to 1-2 MiB): helps only when blocks are freed and reused within a worker before the idle
  sweep; in a burst all streams grow at once (nothing to reuse), and at level 2 keeping 512 KiB blocks defeats the level.
- Headroom on growth above CACHE_MAX (realloc to 2 x the request, the Vec's next doubling then fits the mapping): removes
  about 1/3 of the burst mremaps; virtual only (resident memory stays <= the Vec capacity), but 2x commit charge for growing
  buffers (matters under vm.overcommit_memory=2) and a block bigger than its layout. Not worth it without a CPU result.
- Pre-sizing pend at level 0 (first backlog -> 64 KiB): heap_bytes (Host-mode budget input) would count unused capacity.
- Shrink to keep instead of free at level 2: keeps 132 KiB per drained client at the level meant to shed memory.
- Compact before growing when compaction alone makes the reserve fit (review: reviewer A, reviewer B): would make the L2 ceiling
  131078 + small frames (<= keep, inside the block cache range) and halve the worst L0/L1 capacity. But it breaks the
  amortization the current rule (compact only when the sent prefix >= the unsent bytes) guarantees: at L0 with a full
  1 MiB obuf, every 64 KiB read could memmove ~1 MiB (about 15 copies per byte). A bounded form (e.g. compact instead of
  growing only when the prefix >= unsent / 4) trades a known syscall for up to 4 copies per byte; its benefit in the
  measured runs is ~0 (L2 obufs never reached 262156). Backlog, not done.
If a CPU question remains, the direct test is 70.18's arm B (base-3 vs je-tuned, VPS, rotated A/B, burst-heavy cases:
echo 100x10 short runs, potato echo at 32-128M with level changes, connchurn), not an in-tree growth change.

unresolved candidate). Filter set (reviewer A): madvise is in both 70.18's ratio and this one.
