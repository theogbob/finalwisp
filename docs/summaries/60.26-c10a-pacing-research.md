# 60.26 C10a bandwidth caps by kernel TCP pacing: research and pre-spec (2026-11-01, a research branch (not published))

Pointers: 60.02 C10 (first design), 60.20 (wave 2, answer e), 60.18 #14 (decision: both caps early, set once),
60.21/60.22 (as-built patterns: flags, side vectors, one release helper, disasm classes), 20.19 / 20.21 (TCP_NOTSENT_LOWAT
on client sockets, adaptive lowat), 20.26 (memory budget, lazy caps), 20.30 (credit v2), 70.02 (listener keepalive:
the same "set on the listener, inherited" pattern). Prototype: this branch (research only, never merge as is).
Evidence: `research/c10a/` (scripts + raw logs; the wss runs need a throwaway `cert.pem`/`key.pem` there:
`openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes -keyout key.pem -out cert.pem -days 30 -subj /CN=x`).

## Summary
- **Pick:** download cap = `SO_MAX_PACING_RATE` once on each worker's **listener** (accepted sockets inherit it, kernel
  `sock_copy`; verified 6.12 + 7.0): no code per accept, nothing when off. Upload cap per stream = `SO_MAX_PACING_RATE` +
  `TCP_NOTSENT_LOWAT` on the winning target socket in `won` (one branch per CONNECT off; two setsockopt per stream on).
- **Pacing holds** for send, splice, kTLS, kTLS+splice at 1/10/100 Mbit/s: veth (MTU 1500) without fq 1.000-1.004 of
  the cap; under fq 0.989-1.027; loopback (7.0, MTU 64 KiB) 0.987-1.016, one outlier 1.143 (send at 1 Mbit/s: 64 KiB skb
  granularity + the unpaced first 10 segments in a 3 s window). Through finalwisp (ws, wss, splice, `--no-splice`,
  `--balance`, 1-4 streams, upload per stream) 0.92-1.05 at 1 Mbit/s (64 KiB frame quantization) and 0.96-1.02 at
  10/100 Mbit/s.
- **Not covered:** UDP upload (fq-only: not applied), unix-socket clients (no effect: warn), per-IP totals (C10b), the
  first 10 segments of a connection (unpaced burst).
- **Companion settings (measured):** client lowat max(16 KiB, rate/8) (~125 ms of queued payload at the cap: a queue
  bound, not a latency bound) with a download cap (1 Mbit/s interactive RTT
  1226 -> 332 ms wss); target lowat rate/8 with an upload cap (queued per stream ~4 -> ~1.2 MiB); splice off with a
  download cap (wss 4-stream split min/max 0.24-0.43 -> 0.93; nothing starves either way).
- Flags `--download-rate-per-conn RATE`, `--upload-rate-per-stream RATE`, bytes/s, K/M/G binary. OFF disasm: per-byte
  functions OFFSET-ONLY vs base-5.

## Survey: what the other servers do

| epoxy-server (0c11678) | `read_limit` / `write_limit` bytes/s **per Wisp connection** (`server/src/config.rs:177-182`), cargo feature `speed-limit` (off by default, `Cargo.toml:57`) | `async-speed-limit` token bucket, 1 s refill (`handle/wisp/mod.rs:311-319`); `limiter.consume(len).await` per packet (`handle/wisp/wispnet.rs:169`) | per packet; a dependency |
| wisp-server-python (ae940ec) | `--limits --bandwidth` KB/s **per IP** (`cli.py:82`) | fixed-window average, `while over: sleep(0.01)` spin (`ratelimit.py:44-56`; 60.02 PY-NEW-4 anti-pattern) | spin-wait; window reset forgets history |

All four do it in user space per read/packet. None uses kernel pacing; finalwisp would be the only one with no
per-byte work for its caps, and the only one whose cap also holds on its zero-copy (splice) and kTLS paths, which a
user-space bucket only reaches by clipping each splice length (60.02 C10 first design).

## Kernel facts (source, torvalds/linux master unless a tag is named)
1. `sk_setsockopt` `SO_MAX_PACING_RATE` (`net/core/sock.c`): value u32 (0xFFFFFFFF = no limit; a u64 with optlen 8 is
   read since v5.0, the u32 form on every kernel since 3.13); sets `sk_max_pacing_rate`, lowers `sk_pacing_rate` to it
   and moves `sk_pacing_status` NONE -> NEEDED. No capability needed, any socket type accepts it.
2. TCP internal pacing (`net/ipv4/tcp_output.c`): `tcp_update_skb_after_send` advances `tcp_wstamp_ns` by
   `skb->len / sk_pacing_rate` whenever `sk_pacing_status != NONE` (**skb->len = TCP payload**: the unit is payload
   bytes/s, headers not counted), **except the first 10 data segments** (`tp->data_segs_out >= 10`); `tcp_pacing_check`
   holds the next skb on an hrtimer when status is NEEDED (internal pacing, since 4.13, commit 218af599fa63).
   `tcp_update_pacing_rate` (`tcp_input.c`) keeps `min(cc rate, sk_max_pacing_rate)` on every ACK.
3. `sch_fq` (`net/sched/sch_fq.c` `fq_classify`): flips the socket to `SK_PACING_FQ` when `rate_enable` (default), then
   fq enforces the EDT timestamps TCP still computes with payload lengths (so the unit stays payload bytes; measured 0.99-1.008
   under fq). fq with `nopacing` leaves the status NEEDED, so TCP paces itself: every qdisc case is covered.
4. Inheritance: `sk_clone` -> `sock_copy` copies everything after `sk_dontcopy_end`; `sk_pacing_status`,
   `sk_pacing_rate`, `sk_max_pacing_rate` all lie after it (checked in `include/net/sock.h` v5.4, v5.15, master). So a cap
   on the listening socket is on every accepted socket from its first byte. Measured: `getsockopt` on accepted
   sockets returns the listener's value (6.12, 7.0). SYN-ACKs are not paced (fq treats request socks as orphans).
5. UDP: no internal pacing (only TCP reads `sk_pacing_status`); fq paces non-TCP sockets that set a max rate
   (`fq_fastpath_check`). Without fq the option is silently a no-op.
6. Unix sockets: the setsockopt succeeds (measured on 7.0) and does nothing.

## Approaches compared
| | code paths touched | OFF cost | ON cost | failure modes | complexity |
|---|---|---|---|---|---|
| **A. listener-inherited pacing (download) + `won` (upload)** [pick] | startup (`net::listen`), per CONNECT (`won`) | none at accept; 1 predictable branch per connected stream | 0 syscalls per accept; 2 setsockopt per stream | UDP/unix not capped; first-10-segment burst; per-conn not per-IP | ~60 lines |
| B. setsockopt in `adopt` (download) + `won` | accept/adopt, per CONNECT | 1 branch per accept + per stream | 1 more syscall per accept | same as A | ~60 lines |
| C. user-space token bucket on every write / splice length (60.02 C10 first design, = wispurr/epoxy) | `flush`, `send_bulk`, `splice_target`, `write_target`, `flush_upload`, 100 ms timer | branches on per-byte paths (must tie in A/B) | per-write debit + timer wakeups; splice clipped to tokens | timer granularity, starvation fairness, more state per client (side vectors) | M-L |
| D. eBPF EDT / tc classes per IP (operator) | none in finalwisp | none | none in finalwisp | needs CAP_NET_ADMIN/BPF and host config: against "no required privileges / no per-host tuning" | outside |
Pick A: same kernel mechanism as B with no per-accept work at all (the 70.02 keepalive precedent), and it covers
`--balance` hand-offs and trusted-proxy clients automatically (same socket). C is what C10b (per-client upload total,
per-IP) needs anyway; C10a should not pay for it. B stays the fallback if a later feature needs per-client rates
(e.g. tiers): a per-socket setsockopt overrides the inherited value.

## Chosen design
### Flags (C8 file names = the same without dashes; both off by default)
- `--download-rate-per-conn RATE`: max bytes/s the server sends on one client connection (all its streams together,
  Wisp and wsproxy alike).
- `--upload-rate-per-stream RATE`: max bytes/s the server sends to one TCP target (each stream on its own).
- RATE: bytes per second, `parse_size` grammar (plain, K/M/G = 2^10/2^20/2^30), 0 = off, else 16K..4095M (u32,
  0xFFFFFFFF is the kernel's "unlimited"). Floor 16 KiB/s [rt reviewer A]: below it the 16 KiB lowat floor means > 1 s HOL,
  fq's default 10 s horizon can drop EDT-stamped skbs (`horizon_drop`), and a close tail can outlast KTLS_LINGER 10 s.
  Even at 16 KiB/s the close tail can exceed the 10 s kTLS linger: the lowat floor (16 KiB = 1 s) plus `obuf` up to
  `out_high` drain at the cap, so a client closed with a full queue loses the tail when the linger ends (as a slow client
  today). Documented in 40.03; the linger is not raised (it bounds memory held by dead peers) [rt2 reviewer B]. The rate/8
  lowat is ~125 ms of queued payload at the cap: a queue bound, not an RTT or latency bound. Error text names the unit. Startup line: `, pacing: download/conn N B/s, upload/stream N B/s`
  (impl: also print it as Mbit/s for operators).
- Unit choice: bytes/s like every other size flag and like the kernel option; bits/s SI (tc-style `10mbit`) would add a second
  number grammar to the CLI. 10M = 10 MiB/s = 83.9 Mbit/s goes in 40.03 (open question U1).
- Grammar note: `--stream-rate-per-ip` counts streams/s; here the noun before "rate" says what is counted (download
  bytes, upload bytes). Later C10b names fit the same grammar: `--upload-rate-per-conn`, `--download-rate-per-ip`.

### Semantics (what the operator gets)
- Upper bound on TCP payload bytes/s on that socket: stream data + Wisp/WS framing (9 B per <= 64 KiB frame) + TLS record
  overhead (22 B per 16 KiB): the user's stream data gets ~99% of the cap. Not a byte quota: no accounting, no refusal.
- Burst: the first 10 TCP segments of a connection are unpaced (~14.5 KB on a 1500-byte MTU; up to 10 x 64 KiB = 640 KiB on
  loopback to a local reverse proxy, which then forwards it at line rate). Pacing granularity = one skb (MSS x TSO
  autosize; at low rates TCP sends 1-2 MSS per skb).
- Download cap with N streams: the cap is shared; how it is split is finalwisp's own stream scheduling (the same as for a
  slow client link): see Prototype evidence, fairness.
- Download over UDP streams is covered (it leaves on the client TCP socket). UDP upload is **not** capped (fact 5; C10b).
- Behind nginx/Caddy: the cap applies to finalwisp -> proxy (one socket per WebSocket), so it still caps each client.
- Unix-socket listeners (C7, later): no pacing exists there: startup warning "--download-rate-per-conn does not apply to
  unix-socket clients" when both are set.
- Upload cap: the backlog the client may push ahead of the cap stays in the kernel + `pend`, bounded by the Wisp credit
  (PEND_LOW 256 KiB grant threshold) plus the target lowat; the client sees backpressure through CONTINUE.

### Hook sites (by function)
1. `cli.rs`: two `Opts` fields `download_rate: u32`, `upload_rate: u32`; FLAGS entries; USAGE line; `fn rate(flag, v)` on top
   of `parse_size`; tests (`bad_values_are_errors_not_panics` + a parse case + the FLAGS/USAGE cross-check already there).
2. `worker::Config`: `download_rate: u32`, `upload_rate: u32` (Arc<Config>, not per client: no Client/Target growth).
3. `net::listen(addr, keepalive, pacing)`: after the keepalive block and **before `bind`/`listen`** (children already in
   the accept queue would miss a later setting [rt reviewer B]), `if pacing > 0 && !set_pacing(fd, pacing)` -> close and
   `Err("SO_MAX_PACING_RATE on the listener (..): --download-rate-per-conn")` (refuse to start: an explicit cap that cannot
   be set must not run silently uncapped). `net::set_pacing(fd, u32) -> bool`.
3b. Startup self-check [rt reviewer A P1], like `net::buf_lock_supported`: a loopback listener with the cap, connect, accept,
   `getsockopt(SO_MAX_PACING_RATE)` on the accepted fd == cap, else refuse to start ("the kernel does not pass the
   listener's pacing to accepted sockets"). It proves **option inheritance only**, not enforcement on every route (a route
   via an fq device, a vendor qdisc, MPTCP-forced via `mptcpize`: MPTCP rejects the option, `net/mptcp/sockopt.c`) [rt2].
   Its three temp sockets have bounded ownership: one owner (a small struct with `Drop` closing each fd), non-blocking
   connect/accept with a short bound (e.g. 1 s), every exit path closes all three [rt2 reviewer B].
4. `Worker::new`: `net::listen(&cfg.addr, cfg.keepalive, cfg.download_rate)`.
5. `main.rs` (U7): `splice: o.splice && o.download_rate == 0`, and the capabilities line says "splice off (download cap)".
   `notsent_lowat: paced_lowat(o.notsent_lowat, o.download_rate)` = `lowat.min(max(16 KiB, rate/8))` when both
   are non-zero (0 = kernel default stays 0: the operator chose it, no HOL bound; 40.03 says so [rt both]); capabilities
   note `pacing_note`. The 20.21 `adapt_lowat` call (`mod.rs` ~757) is fed `cfg.notsent_lowat`, which is then the derived
   value (Config holds the result), so its restore goes back to the derived value; its lift needs >= LOWAT_FAST 1 GiB/s,
   unreachable under any cap below that (a >= 1 GiB/s cap may lift it like an uncapped client: harmless) [rt].
6. `connect.rs` `won`: after `t.fd = fd;`: `if self.cfg.upload_rate > 0 { net::set_pacing(fd, r) && net::try_notsent_lowat(fd,
   max(16 KiB, r/8)) }`. `net::set_notsent_lowat` returns `()` and drops the setsockopt result, so fail-closed needs a
   checked helper `net::try_notsent_lowat(fd, u32) -> bool` (the client-side call in accept_all keeps the old best-effort
   one) [rt2 reviewer B]. A failure (not expected on a TCP socket: only EFAULT/EINVAL paths) fails the stream closed
   [rt reviewer B]: `fail_target(ti, 0x03)` before `connected`, metric `pace_fail` appended last (a promised cap must not
   silently vanish). The `lazy_cap` alternative [rt reviewer A P2] is **rejected** [rt2 reviewer B]: `lazy_cap` is skipped when the
   memory caps are off (`sock_cap == 0`) and fires at a byte threshold, so the cap would be missing or late; pacing stays
   in `won` (one ON cost line in the A/B records its churn cost, no hook-site decision left). With C6 (upstream proxy)
   the winning fd is the proxy connection: it gets the upload options before the proxy handshake, so the cap also counts
   the CONNECT/SOCKS handshake bytes (negligible; noted for C6) [rt2]. `won` is the only place a TCP target becomes Open (Happy Eyeballs losers never carry data; TFO SYN data is at
   most one MSS and within the 10 unpaced segments anyway). UDP targets (`udp_open`) untouched.
7. No release helper: nothing is taken (no counters, no tables); the setting dies with the socket.
8. Tests to adapt: every `Config { .. }` literal in `worker/tests.rs` (15) and `server/fuzz/worker_hooks.rs` gets the two
   fields (0).

### Costs and disassembly
- OFF: accept path unchanged (no code); `won` one `cmp` on a Config field per connected stream; startup only otherwise.
- ON: 0 syscalls per accept; 2 setsockopt per TCP stream; kernel hrtimer per paced skb (that is the pacing itself).
- Disassembly (prototype vs base-5, plain `cargo build --release` of both, `bench/tools/disasm_norm.py --show`):
  OFFSET-ONLY: `read_target`, `accept_all`, `adopt`, `close_target`, `on_message`, `push_continue`, `resolve`, `run`,
  `try_connect`, `Arc<Config>::drop_slow` (Config field offsets +8: the two u32 moved the bools). LOGIC: `won` (the hook),
  `cli::parse_args`, `main`, and `getenv` (only the prototype's A/B env switches; gone in the real build). No
  per-byte function (`flush`, `send_bulk`, `splice_target`, `write_target`, `flush_upload`, `read_udp`, `udp_send`) differs
  beyond offsets. `disasm-vs-base5.txt` in research/c10a.

## Design review (2026-11-01; `review` three reviewers: reviewer A, reviewer B, 
answered; reviewer C unavailable, 402 out of credits on both rungs). The doc text did not reach them (an unsubstituted
placeholder), so both judged the design from the six questions plus master code and kernel source; their points:
- Both confirm: inheritance through `sk_clone_lock`/`sock_copy` on every TCP child path (SYN cookies, server TFO, IPv6);
  nothing in `tcp_minisocks.c`/`tcp_init_transfer` resets it (v5.15, 6.12, master); internal pacing needs no fq; the
  unit is headerless TCP payload (`oskb->len`), and fq enforces TCP's EDT stamps without re-applying the socket rate.
  Exceptions: MPTCP rejects SO_MAX_PACING_RATE (not finalwisp's sockets; self-check covers `mptcpize`); a live flow that
  first went through fq stays `SK_PACING_FQ` if its route moves to a non-fq device (multi-homed corner, documented).
- Folded in: set the listener option before `listen()` (reviewer B); refuse to start + runtime self-check (reviewer A P1); floor
  16 KiB/s (reviewer A); `--notsent-lowat 0` semantics stated (both); fail the stream if the target setsockopt fails (reviewer B);
  `lazy_cap` alternative for churn (reviewer A); per-conn not per-IP stated as a limitation (both; U5); fq recommended at scale
  (hrtimer per skb otherwise; reviewer A); credit loop latency test (both, see bidir below); `--mem-budget` + many capped
  uploaders test (reviewer A: the target lowat moves backlog from the kernel into `pend`, which `pend_sweep` can shed).
- Splice: reviewer A calls disabling it required (`gather_bounds` holds the lanes behind a <= 256 KiB pipe chunk: HOL at low
  rates), reviewer B calls it safe but not needed for the cap itself. Both consistent with U7; reviewer A's cheaper variant (splice
  length min(SPLICE_PIPE, lowat)) touches `splice_target` per read, so it is not C10a.
- Reviewer B: "per-socket pacing with permitted bursts, not a strict quota": that is the wording used in Semantics.

Second round (lead, reviewer B, on the doc text): design kept; inheritance re-verified in 5.15/6.12/mainline.
Folded in, marked [rt2]: `lazy_cap` rejected, checked lowat helper, U5 reworded as an approximation, U8 remedy shape,
lowat = queue bound, close tail at the minimum rate, self-check scope + temp-socket ownership, C6 handshake bytes.

## Safety analysis
- Abuse: the caps only slow the server's own sends; a client cannot raise them (no client-controlled input reaches the
  option). A capped download makes every client a "slow reader": data waits in the target sockets' receive buffers and in
  `obuf` up to `out_high`, exactly as for a slow link; the memory budget levels (20.26) already bound that. Operators who
  set a low cap on a busy host raise steady-state memory per client (same order as slow clients today); 40.01 note.
- Upload cap: without the target lowat each capped stream kept ~3.4-4.4 MiB queued ahead of the cap (kernel autotuned
  send buffer); with it ~1.1-1.2 MiB at 1 and 10 Mbit/s (most of it the client's own socket buffers and the credit window).
  A client that ignores the Wisp credit hits the existing 20.27 0x49 hold / PEND_HARD shed, as for any slow target.
- 70.02 dead-peer detection: a paced client still ACKs, `peer_gone` stays false; kTLS starve (50.02) needs `outq == 0`, a
  paced socket has data queued: no false starve episodes. 20.21 adaptive lowat: a paced client never reaches LOWAT_FAST
  (harmless; documented in 60.20).
- Leaks: nothing allocated, nothing counted, no cross-worker state; every exit path is the socket's close.
- DoS on the server: pacing costs the server an hrtimer per skb; with many paced sockets that is the kernel's normal paced
  TCP (Google runs all TCP paced via fq). The A/B ON plan below measures it.
- Kernels: 5.15+ supported: internal pacing (4.13) and inheritance hold; < 5.15 only logs (project rule), and the option
  still works there (3.13+ with fq, 4.13+ without).
- Failure is loud where it matters: the listener setsockopt failing refuses to start; a per-stream failure is counted.

  the credit loop RTT grows to ~0.1-0.5 s and upload = credit window / that RTT. Nothing stalls (no sheds, no starve
  episodes in the metrics line). Documented as a property of the cap (40.03); real links rarely upload faster than they
  download at these rates. A fix would be a CONTINUE fast path ahead of a started bulk frame (touches `flush`: not C10a,
  backlog item; U8).

|---|---|---|---|---|

| wss p50 / max (ms) | 3.1 / 4.5 | 1226 / 1508 | 332 / 633 | 99 / 276 |

  single-threaded client never did. Not a finalwisp finding.

### Fairness
4 bulk streams on one connection, 12 s window (4 s for the first run), per-stream rate min/max:
| client link | ws | wss |
|---|---|---|
| pacing 12.5 MB/s, splice on (default) | 0.97-0.98 | 0.97 |
| pacing 1.25 MB/s, splice on (default), 3 runs | 0.76-0.87 | **0.24 / 0.40 / 0.43** (two streams get ~2x the other two) |
| pacing 1.25 MB/s, `--no-splice` | 0.93 | 0.93 |
| no pacing, tbf 10 Mbit qdisc on the link, splice on | 0.71 | 0.83 |
No stream starves anywhere (the slowest wss stream still got 120-185 KB/s of the 312 KB/s fair share), and the total
always meets the cap. The uneven split is wss + splice + a socket that drains steadily at a low rate: the stream whose
target read finds the client queue empty splices a whole 256 KiB pipe at once (`read_target` -> `splice_target`), and
under kTLS this lines up so two streams keep winning. It is finalwisp scheduling, not pacing error, and it did not show
with the same rate imposed by a tbf qdisc (0.83). Cheapest remedy inside C10a: no splice on capped connections (U7);
the root cause (splice opportunism vs. stream rotation on a slow kTLS socket) is a separate backlog item.

## Open questions for the maintainer (each with my pick)
- U1. Units: bytes/s with K/M/G = KiB/MiB/GiB (one grammar with --mem-budget) [pick], or bits/s SI like tc
  (`100mbit`), or accept both with explicit suffixes (`100Mbit`, `12MB`)?
- U2. Derived client lowat when a download cap is set: min(--notsent-lowat, max(16 KiB, rate/8)) [pick], or leave lowat
  alone (1 s+ interactive delay at 1 Mbit/s)?
- U3. Target lowat with the upload cap: max(16 KiB, rate/8) [pick, 3-4x less queued per stream], or pacing only?
- U4. UDP upload: not capped in C10a, stated in 40.03 and the startup line [pick]; or set the option anyway (works only
  under fq: host-dependent behaviour, against the no-per-host-tuning rule)? C10b's token bucket covers UDP later.
- U5. Per IP: not possible with pacing alone (each socket paces itself; re-dividing an IP's rate over its connections
  means setsockopt on other workers' fds at every connect/close, racy with fd reuse, and idle connections hold shares).
  Document "per IP about --max-conns-per-ip x --download-rate-per-conn" as a **steady-state approximation for tracked
  connections only, not a guarantee** [rt2 reviewer B]: untracked keys (a full shard fails open, Q11), a trusted proxy's
  client without the header (not charged), and the unpaced first 10 segments of each connection all exceed it [pick]; the real per-IP total is C10b
  (shared token bucket per C3b key) or an operator-side tc/eBPF setup (40.01 recipe), not C10a.
- U7. Splice on capped connections: off when `--download-rate-per-conn` is set (startup: `cfg.splice = false` for the
  process, zero hot-path cost; wss 4-stream split 0.24-0.43 -> 0.93) [pick]; splice gives CPU savings only at multi-GB/s
  rates, which a cap rules out in practice. Alternative: keep splice and root-cause its stream rotation on slow kTLS
  sockets first (backlog either way). Note: with U7, a very high non-binding cap (e.g. 4000M) also loses splice.
- U8. A download cap slows the same connection's upload (credit loop behind paced frames, measured 10-27x the cap):
  accept + document in C10a [pick]. A "CONTINUE fast path" cannot overtake a started bulk frame (`flush` finishes a
  partly sent bulk frame first, client.rs ~382-388, WebSocket framing forbids interleaving inside a frame) [rt2 reviewer B]:
  a remedy must schedule control frames BETWEEN frames sooner, or shrink bulk frames on capped connections (both
  per-flush / per-read code: separate backlog item).
- U6. The 10-segment unpaced start (640 KiB over loopback to a local proxy): accept and document [pick]; avoiding it
  needs a user-space bucket for the first bytes.
