Human version: musl still gives the smallest idle memory (about 5x less per idle connection than base-3), and its burst
memory looked no worse than glibc here (the old 1.8 GiB peak did not reproduce). But base-3 already sits at 4.7 KiB per
idle connection, so the absolute gain is small (tens of MiB per 10,000 idle connections), and the price is the mapping
guard (~420 lines back) plus musl's single malloc lock, which already shows futex wait/wake traffic at 4 workers
(strace count; its CPU cost is not measured). mimalloc, the usual fix
for the lock, makes memory worse for us (idle per connection 30-60x higher unless we add a collect hook, bursts higher).
Recommendation: keep static glibc. Run the one A/B below only if 4 KiB/conn of idle memory matters to the maintainer.
Confidence: high on the memory/syscall numbers (laptop, n = 2-6); high that the futex word is `__malloc_lock`, medium on
how much it matters without strace (strace perturbs scheduling and lock hold times);
low on any CPU/throughput effect (not measured, by rule).

## 1. Feasibility (target, toolchain)
- Rust target x86_64-unknown-linux-musl: Tier 2 with host tools (rustc platform-support). Pinned nightly 2026-09-06 bundles
  musl **1.2.5** (checked: `strings libc.a` in the self-contained dir; Rust >= 1.93 ships 1.2.5, blog.rust-lang.org
  2025-12-05 "Updating Rust's Linux musl targets to 1.2.5"). Static-pie by default, std works, no code change needed:
  `cargo build --release --locked --target x86_64-unknown-linux-musl` (CC_x86_64_unknown_linux_musl=gcc is enough for
  ring, as in 70.11). Binary 9.5 MB vs 12.4 MB glibc static.
- musl + mimalloc: the libmimalloc-sys C build FAILS with Ubuntu's gcc (glibc headers: undefined `__memcpy_chk`,
  `__isoc23_strtol`). It needs a real musl C toolchain (musl-tools' musl-gcc, or zig cc; I used zig 0.14.1 `cc -target
  x86_64-linux-musl`). For release.sh / the Forgejo clean lane that is a new build-image dependency, and the reproducible
  md5 (40.02) would then also depend on that compiler.
- Functional: `wst compat --only adv-lane,adv-noprio,wispjs` (ports 11300+): **3/3 PASS on all four builds**, all with
  the DEFAULT resolver (getaddrinfo). The proposed configuration (musl with --dns-own forced on) was NOT run here;
  --matrix has a --dns-own lane for that (70.09).
  (fw-glibc 55d175ae = base-3 release md5, fw-musl 947c610d, fw-musl-mi2 a8f415a0, fw-musl-mi3 0c1583a4).
- epoll / splice / kTLS / TCP_INFO: same syscalls; the libc crate exposes them for musl (the binary built and the
  adversarial + wisp-js gates passed). Not run here: tls, udp, membudget, fuzz-replay, cargo test on musl (70.11/20.29
  ran cargo test on musl before: 44 pass).

## 2. What is left of the cost

### 2a. DNS: does --dns-own cover musl's resolver problems? Yes, IF it is forced on for a musl build.
musl 1.2.5 getaddrinfo (src/network/lookup_name.c name_from_dns, res_msend.c), read today:
- A + AAAA in parallel, TCP fallback on TC (1.2.4), long CNAME chains (1.2.5): fixed upstream.
- Still there (by musl's design, not an unfinished fix: musl commit 5cf1ac244, 2020-05-19, makes a transient failure of
  either family fail the pair): `if (alens[i] < 4 || rcode == 2) return EAI_AGAIN`. SERVFAIL (res_msend.c `case 2`) is
  re-sent while `servfail_retry` (2 x queries) lasts, then ignored; the loop runs to the resolv.conf timeout (5 s default,
  not x attempts). Servers are queried in parallel, so another server's answer ends it early; a lone SERVFAILing server
  costs the full timeout. Search/ndots handled; no `options rotate`; max 3 servers.
- --dns-own (dns.rs, 70.09) covers the failure modes above (it is itself bounded: max 3 servers, CNAME chain 8): /etc/hosts first, search/domain/ndots (glibc order), A and AAAA per family
  (A failure + AAAA = ok), SERVFAIL -> next server, TC -> TCP, deadline 2 s windows, cancel. With --dns-own no getaddrinfo
  call is left (net.rs:746 is the only call; the bind address is a literal parse).
- Gap: --dns-own is OFF by default (cli.rs). A musl build must force it on (~5 lines, e.g. `cfg!(target_env = "musl")`
  in the default) or the musl getaddrinfo is what users get. `localhost` then needs /etc/hosts (as with musl itself).
- Bonus: no NSS on musl, so main.rs nss_builtin_only (70.12) is not needed there.

### 2b. Mapping guard (20.29, archive/vma-guard e00ba6e): still needed for mallocng. Why:
- mallocng still maps every block >= 131052 B on its own (meta.h MMAP_THRESHOLD 131052; malloc.c `if (n >=
  MMAP_THRESHOLD) mmap(...)`, `if (p == MAP_FAILED) return 0`): no arena fallback at vm.max_map_count, Rust aborts on
  NULL. Unchanged since 20.29 (SIGABRT measured on VPS1 at limit 1024).
- base-3 changes nothing here: the block cache covers 16..132 KiB only. At L2/L3 obufs now stay at 65539..131144 B
  (mem.rs Stage::keep comment, 60.12 #2; the 512 KiB of the 70.11 backlog is gone), which still crosses 131052; level-0/1
  obufs (keep 2 x out_high), upload pend and big partial frames can be larger.
- When does it bite (estimate, a GUESS; 0.77 maps per block is the 20.29 Vec-doubling probe, not an invariant):
  65530 maps / 0.77 maps per >=128 KiB block -> ~85k mapped blocks -> >= ~10 GiB of heap. The default byte budget (MemTotal / 2, 20.26) fires first on hosts with < ~20 GiB RAM;
  on bigger hosts (default budget included), with --mem-budget 0 or a large --mem-budget the guard is the only thing
  between a load spike and SIGABRT. Even the guard has a known window (20.29 backlog: obuf reserve at guard L3), which
  belongs in the re-port scope.
  Some distros now ship vm.max_map_count 1048576+ (this laptop: 2097152); a server cannot rely on that (no sysctls rule).
- Lines that come back: archive/vma-guard vs its base 2731789 = **+422 / -36 in server/src** (about 104 of them tests,
  ~74 comment lines; ~245 code lines) in main.rs, mem.rs, worker.rs. `git merge-tree` onto base-3: **conflicts in all
  three files** (base-3 added +904 mem.rs, +1281 worker.rs since): a re-port, not a cherry-pick, plus its open backlog
  item (cap the obuf reserve below MAP_BIG at guard L3). Compare base-2's "~1,100 extra lines": the resolver (~1,100 incl.
  tests) is now in master anyway, so musl's net new code is **~420 lines + ~5 (dns default) + release.sh target switch**.
- glibc has a one-call fix (mallopt M_MMAP_MAX, 70.03: arena fallback below the kernel limit); mallocng has no such knob,
  hence the guard. mimalloc: mapping snapshots stayed at 100-140 (sampled after each phase, not continuously); it
  allocates from large arena/segment reservations, so a guard is probably not needed, but that is not proven here.

### 2c. The global malloc lock (mallocng) - now measured as a count
- Source (mallocng glue.h): `rdlock()` and `wrlock()` are the same `LOCK(__malloc_lock)` (RDLOCK_IS_EXCLUSIVE 1): every
  malloc takes the one process-wide lock; free is lock-free only when the slot is neither the first nor the last free one
  of its group (1.2.5 source; the 2020 openwall thread "Review of mallocng motivation/goals" discusses the same
  trade-off, before the inline lock landed).
- strace -f -c, wbench connchurn 10x10 3 s, laptop (counts per run; strace slows everything and so INFLATES contention):
  | server, --threads | accepted conns | mmap+munmap /conn | + mprotect + madvise /conn | futex calls (/conn) |
  |---|---|---|---|---|
  | glibc t1 | 3493 | 0.15 | 0.24 | 4 (0.001) |
  | musl t1 | 3049 | 0.64 | 0.66 | 9 (0.003) |
  | musl+mi3 t1 | 2988 | 0.03 | 0.07 | 6 (0.002) |
  | glibc t4 | 8047 | 0.07 | 0.12 (339 mprotect: arena growth) | 5 (0.001) |
  | musl t4 | 6046 | 0.16 | 0.17 | **1396 (0.23)**, 340 EAGAIN |
  | musl+mi3 t4 | 8715 | 0.01 | 0.04 | 4 (0.000) |
  Counts include startup and shutdown. Which lock: a second strace run of musl t4 (stracek-muslk2-t4.txt + .maps, the
  maps read from the same process): 2280 of 2300 futex calls are on 0x796cf3df4588; the binary's load bias (first LOAD
  segment, vaddr 0, mapped at 0x796cf3c00000) gives 0x796cf3df4588 - 0x796cf3c00000 = **0x1f4588 = `__malloc_lock`**
  (nm), exactly. The mimalloc build on the same load has 4 futex calls. So the malloc lock sees wait/wake traffic at 4
  workers on connection churn (futex calls count waits AND wakes; they show the lock is hot enough to sleep, not the CPU
  cost). How much CPU it costs without strace is NOT measured (the A/B below); 2 vCPU boxes (2 workers) were the earlier
  basis for "~equal". The connection counts are under strace and are not a throughput result.

### 2d. CPU per new connection
- Known (60.10): +25-30% before the block cache, ~equal after (2 vCPU boxes). Now the per-connection syscall residue:
  musl 0.64 mmap+munmap per connection at t1 (70.11 had 0.54: mallocng groups for 16/24/32 KiB and 4 KiB size classes,
  outside the cache range) vs glibc 0.15 (t4: 0.16 vs 0.07; with glibc's mprotect counted 0.17 vs 0.12). Plus the lock above at >= 4 workers. Expectation (GUESS): ~equal on
  2 vCPU, worse with more workers; must be measured.

### 2e. mallocng vs musl + mimalloc
Idle (wst idle, 2000 conns, 64 KiB echo, settled RSS; KiB per idle connection, median):
| build | --threads 2 (6 reps) | --threads 8 (4 reps) | RSS before load |
|---|---|---|---|
| glibc (base-3) | **4.7** [4.7 4.7 4.7 3.8 3.6 4.7] | 4.6 | 2.6 MiB |
| musl mallocng | **0.9** [0.9 x6] | 0.9 | 1.6 MiB |
| musl + mimalloc v2 | 294 | 349 | 47.8 / 77.9 MiB |
| musl + mimalloc v3 | 146 | 129 | 13.5 / 31.6 MiB |
| v2 + mi_collect(false) per sweep | 79 (4 reps) | | |
| v2 + mi_collect(true) per sweep | ~0 (settles below its 47.8 MiB start) | | |
| v3 + mi_collect(false) per sweep | 1.9 | | |
| v3 + mi_collect(true) per sweep | 1.35 [0.6 1.5 1.3 1.4] | | 13.5 MiB |
Why (partly inferred): mimalloc purges freed pages only on later allocator activity (purge_delay 10 ms v2 / 1000 ms v3,
x arena_purge_mult) and keeps freed blocks in per-thread page free lists; an idle worker does not call it, so the pages
stay resident (the same mechanism, on another version/workload: microsoft/mimalloc#1422 "Freed arena memory stays
resident in an idle process"). mi_collect(true) at each idle sweep brought connected-idle down to 1.35 KiB/conn, so the
memory is reclaimable; it does not restore glibc's total footprint (+11 / +29 MiB baseline at t2 / t8). mi_collect works
on the calling thread's heap (plus arena purge), so it must run on each worker. My hook runs from the idle sweep, which
only runs while the worker has clients: after a burst where every client left, mimalloc kept 50-100 MiB (below). A real
integration needs a "worker went idle" collect; not built.

Burst then idle (burst_probe.py: own systemd scope; download 20x10 4 s, echo 20x10 4 s, connchurn 10x10 3 s, then 12 s
idle with no clients; cgroup memory.peak incl. socket memory, VmHWM, memory.current; medians, t2 3 reps / t8 2 reps):
| build | t2 peak / HWM / cur+12s MiB | t8 peak / HWM / cur+12s MiB | max maps (snapshots after phases) |
|---|---|---|---|
| glibc | 850 / 257 / 3.0 | 862 / 326 / 5.4 | 345 / 298 |
| musl | 840 / 229 / **1.3** | 730 / 224 / **2.0** | 292 / 265 |
| mi3 (no collect) | 1086 / 407 / 54 | 1095 / 491 / 78 | 100 / 125 |
| mi3 collect(true) | 1088 / 377 / 53 | 929 / 385 / 81 | 100 / 124 |
| mi2 collect(true) | 1037 / 402 / 74 | 1225 / 513 / 100 | 106 / 139 |
The old "musl HWM up to 1.8 GiB vs 1.1 glibc" (one laptop run) did NOT reproduce under this load (musl HWM <= glibc in
5/5 runs); a different load (potato / many big uploads) could still differ: not tested.

## 3. Expected effect on our metrics (A = musl mallocng; B = musl + mimalloc v3 with a collect hook)
- Idle KiB/conn: A 0.9 vs 4.7 (measured); B 1.4 with the hook (measured) but +11 MiB baseline at 2 threads, +29 at 8.
- Burst peak + return: A <= glibc (measured, this load); B HWM 1.2-1.6x, 50-100 MiB kept after all clients leave (needs
  a "collect when the worker goes idle" wake; not built).
- CPU per new connection: A unknown, `__malloc_lock` futex traffic at 4 workers (count); B fewest mmap/munmap, no futex
  surge (count).
  Throughput: no new data (earlier musl laptop runs: within noise, 60.01).
- Code: A +~420 (guard re-port) +~5 (dns default) + release.sh/CI target; B +2 crates (mimalloc, libmimalloc-sys,
  vendored C ~20k (v2) / ~24k (v3) lines), feature/cfg in mem.rs, block cache off or ported to mi_usable_size, the collect hook + wake,
  musl C compiler in the build image. Neither removes code from the glibc build if glibc stays an option.
- Maintenance: A: musl is stable and conservative; the guard is ours to maintain (20.29 limits + backlog). B: mimalloc
  v2/v3 behave differently (idle 294 vs 146) and change per release; tuning by env/options = per-host tuning (principle).

## 4. If we run one experiment (A only)
Binaries: fw-glibc = base-3 release (55d175ae) vs fw-musl = base-3 + `--dns-own` forced on for musl (5-line change, no
guard; the guard is irrelevant at these loads), both run with `--dns-own` so DNS is equal. Build both from one commit.
1. VPS1/VPS2 (2 vCPU, the deployment shape), `wst regress` style, rotated interleaved A/B, >= 16 reps per case,
   paired Wilcoxon: connchurn 10x10, connchurn-tls 10x10, burstidle 10x10, download/echo/upload 10x10, rr, potato
   (32M/128M). Per case record rps/MiB/s AND server CPU (utime+stime from /proc/PID/stat) per connection / per MiB, and
   cgroup memory.peak.
2. Lock scaling: --threads N only up to the cores of the host (more is oversubscription, not lock scaling).
   VPS3 (4 vCPU, no root): t2 / t4. The quiet laptop (15 CPUs) for t8 / t14 ONLY with the maintainer's OK.
   connchurn 10x10 and 40x10, same rotation, CPU per connection and rps.
3. Memory: wst idle 2000 at t2/t16, and the burst probe at t2/t16 (as here) on the boxes.
Decision rule: switch only if musl ties or wins every case on both boxes (a loss must reproduce) AND CPU per new connection
at the highest thread count measured (t4 on VPS3; t14 if the laptop run is allowed) is within +5% of glibc. Then (and only then) re-port the guard (~420 lines) + fuzz + soak on the musl binary.
Otherwise close the mallocng track (keep archive/vma-guard). A screen without the guard cannot prove the guarded build's
CPU; the guard adds one load + compare per alloc/free (20.29), so re-check CPU per connection after the re-port.
