## TLDR
- **Stable, correct: every expectation PASS.** 12 h, ~32 TiB through two servers: 0 crashes / restarts / OOM kills /
  memory.max events, memory level 0 all the time (level_changes 0), both servers exit 0 on SIGTERM with
  `ev=metrics_final`. Probes 1,418/1,418 OK (incl. the new 20.33 interleaved upload step); 6,001 wbench runs (663 of them SIGKILLed on
  purpose), 0 errors or timeouts; upmux (20.33) 364/364, connchurn 299/299; 24/24 abuse bursts OK.
- **Dead peers and live peers exactly as designed:** 1,420/1,420 half-open clients reaped (idle 178-186 s, queued
  download 151-156 s, plain and TLS); 0 false resets (200-cohort 12 h, 385k idle connections, 1,231 slow readers incl.
  389 zero-window pauses of 3-10 min, 6,362 s SIGSTOPped). Dead targets: every stream now ends with CLOSE 0x47 (idle and
  download ~178-181 s after the cut, upload ~950 s); base-1.2 never closed idle/download streams (70.13 is new).
- **Pool (own-alloc):** pool_fallback / pool_capped / madvise_fail / munmap_fail = 0; pool_remote 0; after the clients
  left: dirty 0, chunks 4 (A) / 8 (B). sheds / refusals / holds / 0x49 = 0 (credit v2 never needed the safety net).
- **kTLS starve path was exercised by the soak itself** (no pressure episodes were injected; lead decision): the host
  entered TCP memory pressure 427 times (TcpExt, ~16 min of 12 h), B logged 793 starve episodes (max 1.46 s, 30 given
  B room); no wss run stalled (110 B downloads, min 188 MiB/s; 709/709 TLS probes OK).
- **Watch 1 (memory, not proven a leak):** a small rise of the non-pool heap. Theil-Sen on 30-min minima: cgroup anon
  A +217 KiB/h [141, 282], B +142 KiB/h [88, 218] (95 % bucket bootstrap; CIs exclude 0); quiet-window slopes have wide CIs
  that include 0 (RSS A +2.0 % [-1.8, +7.3], B +3.4 % [-1.0, +9.4] /h). After all clients left: anon A 5.2 / B 4.8 MiB,
  RSS 7.4 / 7.8 MiB, fds 17 (11-min smoke: anon 3.1 / 2.8 MiB; soak24 base-1.2 after 6 h: 4.0 / 3.8 MiB). The pool is not
  it (dirty 0 at the end). glibc heap fragmentation and a slow per-connection leak look the same here; a cycle test
  separates them (below).
- **Watch 2 (latency): `pool_release_max_us` 65 ms (A) / 255 ms (B).** Four jumps above 10 ms in 12 h (min 34, 40, 54,
  100), all with host CPU 96-99 % and load 6.9-8.4 on 4 vCPU; no new max after min 100. release() is bounded (1 ms
  time bound, 16 calls, 4 munmaps per turn), and the gauge is wall-clock (Instant), so preemption and mmap_lock waits
  count. Likely a scheduling artifact of the saturated box; not shown.

## Setup (as 30.11 soak24, plus 30.14 additions)
- Box VPS3, 4 vCPU, 7.5 GB, kernel 7.0.0-38; nothing else of ours running. Binary: master release
  (bench/release.sh, static glibc, own-alloc default) md5 1850d055; wbench (bench/, master) md5 832ca38d.
- Root used only for: `/root/soak-nft.sh up/down` (the 30.11 table) and `modprobe tls` (kTLS module not loaded after a
  reboot; master refuses --tls-cert without kTLS). No sysctl, no pressure episodes.
- A plain ws :7001, B wss :7002 (kTLS), each in a user scope MemoryMax=1G, `--metrics-interval 10`. Mix: download,
  upload, rr, churn (half via DNS), browse (30 % with 8 MiB bulk), udp-rr, canary, kills, plus **upmux** (wbench upload,
  1 conn x 4-10 streams, 1/2/4 KiB DATA: the 20.33 case) and **connchurn** (a new WebSocket/TLS connection per request);
  75 % A / 25 % B. Idle holder 300-3000 conns, 200-conn cohort, 12 slow readers (zero-window pauses), half-open every
  8-12 min (10 idle + 10 queued download, A and B alternately), dead targets every 10-15 min, abuse every ~30 min
  (partial frames on A, blackhole CONNECTs on B), hourly 5-min quiet window + bench window ({aged A, fresh F} x {aged,
  fresh target} x download 3x3/4x4, 2 rounds).
- Probes every minute per server: 32 MiB pattern download, 4 MiB upload echo (sha256), 100-stream echo, **upmux** (new:
  8 echo streams x 256 KiB, 1-4 KiB frames interleaved round robin, many frames per send, per-stream credit, sha per
  stream), CLOSE reasons 0x44 / 0x42 / 0x48, UDP.
- Load: host CPU 75 % mean outside the quiet windows, >= 95 % in 28 % of the samples (as in 30.11, a saturated box:
  throughput numbers are not benchmarks).

## Memory (Watch 1)
| estimator | A | B |
|---|---|---|
| quiet windows (11, Theil-Sen, 95 % window bootstrap): RSS | +284 KiB/h, +2.0 % [-1.8, +7.3] | +390 KiB/h, +3.4 % [-1.0, +9.4] |
| quiet windows: cgroup memory.current | +0.9 % [-2.2, +5.0] | +4.9 % [-1.8, +9.0] |
| 30-min minima (22, bucket bootstrap): cgroup anon | +217 KiB/h [141, 282] | +142 KiB/h [88, 218] |
| 30-min minima: RSS | +221 KiB/h [141, 280] | +146 KiB/h [89, 220] |
| anon min h1-2 -> h11-12 | 5.4 -> 7.0 MiB | 4.1 -> 5.2 MiB |
| anon after the clients left | 5.2 MiB (smoke 3.1) | 4.8 MiB (smoke 2.8) |
The quiet-window values swing by 5-9 MiB between hours (B RSS 7.6-17.3 MiB) with no ESTAB relation, so that
estimator cannot bound ~2 %/h. The minima are the denser estimator and show a small positive slope in both servers. The
pool is excluded (dirty 0 and chunks 4 / 8 at the end; in-run quiet dirty <= 3 MiB, kept by design under the cap).
What remains is glibc heap (allocations < 16 KiB or > 128 KiB, non-worker threads, rustls state on B). At this rate it is
~3-5 MiB/day under a 32 TiB/12 h mix; whether it plateaus (fragmentation) or grows without bound (leak) is open.
Follow-up (proposal, ~2 h, any quiet box, no root): a cycle test: fresh server, N = 20 cycles of a fixed 5-min mix (this
soak's workloads, no half-open), 60 s idle after each, record cgroup anon after each idle; a linear rise per cycle =
leak, a plateau = retained heap. For B also with connchurn alone (TLS handshake state).

Pool chunks in the quiet windows rose 4-9 -> 12-16 (Theil-Sen +0.8-1.0 chunks/h, CI excludes 0) with a flat
connection count: mapped but clean chunks (address space, one VMA each, no RSS), all returned when the clients left
(final 4 / 8). A fragmentation pattern of long-lived connections pinning chunks; not a memory cost at this size. Watch.

## Latency of pool release (Watch 2)
Jumps of the process max: A 1.3 ms (min 0.2) -> 2.8 -> 5.1 -> 14.7 (min 34) -> 65.2 ms (min 54); B 0.1 -> ... -> 3.5 ms
(min 27) -> 90.8 ms (min 40) -> 255.0 ms (min 100). Host CPU 96-99 %, load 6.9-8.4 at each. The canary rr p99 spikes in
the same minutes (61 ms at min 40). The gauge cannot tell CPU from waiting. Proposal: record the release step's thread
CPU time (CLOCK_THREAD_CPUTIME_ID) beside the wall time, or count releases > 10 ms, then reproduce on a quiet box with
a saturating neighbour. Until then: not a finding.

## kTLS starve (50.02) without injected pressure
TcpExt TCPMemoryPressures rose 4 -> 431 during the run (TCPMemoryPressuresChrono +955 s); the 10-s samples never caught
it (sockstat TCP mem max 113,912 pages, tcp_mem[1] 117,275): short spikes from the soak's own loopback load (browse
bulk, downloads, slow readers, queued half-open downloads). B: ktls_starve 793, slices (B room) 30, longest 1,457 ms;
A (plain) 0. No wss download or probe stalled. So the A/A2/B fix ran ~800 times under real load without a failure. Note
for the lead: the soak itself pushes VPS3 into short host TCP pressure (likely true of soak12/24 too).

## Other observations
- Dead targets (70.13 target keepalive, new since base-1.2): idle 176.5-180.3 s, download 180.6-182.6 s, upload
  947.7-952.2 s after the cut, all CLOSE 0x47 (base-1.2: idle/download never, upload 0x03 at ~950 s). Connection stays
  usable (echo every 60 s: 0 failures); 0 server sockets to the dead target afterwards.
- Heap after abuse bursts: A -0.3 MiB median (max +6.7), B -0.7 (max +8.7).
- Bench windows (11 x 16 cells, 0 errors): no aging signal (A/F with the aged target -0.7 / -2.3 %/h over 11 windows),
  but single cells fall to 0.7-1.0 GiB/s (F + fresh target 4x4 in windows 7, 8, 11): on a saturated 4-vCPU box this
  instrument is too noisy for a drift verdict (as in 30.11).
- One blackhole CONNECT got 0x42 instead of 0x43 (min 698; same as soak12: an unreachable error instead of a timeout).

## Harness changes (bench/soak, for the merge)
soak.py: `--fw` required; servers get `--metrics-interval 10`, the lines are parsed into samples.csv (`{A,B}_m_*`:
conns, streams, dead_peers, refusals, sheds, pool_*, ktls_starve*, host_tcp_pressure*, close_xx); whole lines only;
upmux + connchurn workloads; nft table checked at start (a DSCP AF11 packet must be dropped; RST-closed sockets) or
`--no-halfopen --no-deadtarget`; server stop waits 45 s (master drains 30 s); probe timeout 150 s; make() inside try.
probe.py: upmux step. analyze.py: metrics table per server generation, pool gauges in slopes/quiet windows/plot,
run-wide expectations (no death, exit 0 + metrics_final, OOM/max over every sample, probes, every workload by the
table predicate, MK_ZERO keys present and 0, harness errors). Review three reviewers, two rounds (round 1 had no diff);
fixed: wbench timeouts with empty output passed (P1, all three), shutdown rc / final line not asserted, OOM read only
from the last row, missing keys counted as 0, nft check left a FIN_WAIT on 7001.
