Pointers: 60.02 (C1-C10 designs, Decisions Q1-Q12), 60.18 #12 (priority rule), 60.19 (base-4), 40.01 (deployment:
reverse proxy setup), 30.10 (regress, `--new-args`). Code refs are to master f565330 (worker/ modules after the split).

**Priority rule (60.18 #12):** (1) core and important features first; (2) features that do not touch the hot paths first.
Hot path here = per packet / per read / splice / send loop: `worker/input.rs` (read_client, frame parse), `worker/target.rs`
(read_target, splice, the per-event `TState` match), `worker/upload.rs` (20.33 batches, credit grants), `worker/udp.rs`
(per datagram), `worker/client.rs` (send). Off the hot path: `worker/conn.rs` (accept, adopt, close), `worker/upgrade.rs`
(HTTP upgrade), `worker/wisp.rs` `on_connect` (CONNECT only), `worker/connect.rs` (DNS, connect, Happy Eyeballs),
`worker/sweep.rs` (2 s sweep, shed), `main.rs` / `cli.rs` (startup), `metrics.rs` (its own thread).

## Dependencies
- **C3b needs C2 behind any reverse proxy** (40.01 recommends one without kTLS or to share 443): without C2 every client is
  the proxy's IP, so a per-IP limit locks out everyone behind it, worse than no limit. Same with C7 (no IP: one key `unix`).
  C3a needs neither.
- **One `push_fd` payload change, three consumers [rt]:** `Inbox.fds` carries only a `RawFd` (`net.rs` ~685, ~727) and is
  drained into `adopt` (`connect.rs` ~105). C3b needs the IP key (or the accepting worker's reservation) to travel with the
  fd, C7 needs the listener kind (TLS or not), C2 the peer address. Do it once, in wave 1.
- C4 `ip=` is the proxy without C2; C4 `rule=` needs the C1/C3 rule ids. C4 unix connection lines get `tx` only until C5
  `rx_bytes` exists. C10b per-IP reuses the C3b table. C6 needs C1 (policy on the proxied name; Q1) and C4 for debugging.
- C8 early: every later flag is in the file at no extra cost (one parser).

## What changes vs 60.02 now that base-4 exists
- **C8 = flag file (Q9), not TOML:** `flag value` / bare `flag` per line, `#` comments; the file becomes the argument list.
  The 60.18 #1 removed-flag errors then apply to file lines too (report file and line). The 60.02 `[section]` key names
  are replaced by flag names. Repeatable flags append today (`--dns-server`, `--cert-auth-key`, `cli.rs` ~176-181), so
  "the command line overrides the file" needs a rule for lists [rt] (open question a).
- **CONNECT check order (four steps, `wisp.rs` ~119-156) [rt]:**
  1. validation (0x41); split UDP-with-`--no-udp` out of it for Q7 (0x48); bound the host length here (today it is checked
     later, in `new_target`, `connect.rs` ~60), before C1 normalizes the name;
  2. C1 request policy (0x48);
  3. C3 `--max-streams-per-conn` (a local compare; refusals are labelled `limit`, also under memory pressure);
  4. memory admission / `max_streams` (0x49, exists), then C3b stream rate (the only shard-mutex step: no lock traffic and
     no per-IP token spent while memory refuses). 60.02 put the stream rate before admission; this replaces it.
  Both 0x49 kinds stay apart in metrics (`refuse_admit`/`refuse_streams` exist; add `refuse_limit`).
- **wsproxy (`upgrade.rs`):** it calls `new_target` directly (~90), so C1 and C3 run there too, **before** `http::switching`
  (~87), so a refusal is an HTTP status (the admission block at ~80-86, 503, is the template), not a 101 then a close. Its
  stream lives in `proxy_target`, not `streams`: count it explicitly (60.02: one connection, one stream).
- **C1:** both address-filter sites (`start_connect` and the late-DNS path `dns_late`) switch to the policy [rt].
  `--no-ipv6-targets` must also stop the own resolver's AAAA query (`dns.rs` ~558), not only `getaddrinfo`. Q2's own
  interface addresses: snapshot at startup (open question c). Q7 is a default change: release note.
- **C3 vs the memory levels (20.26, the mem.rs round, HostSock):**
  - level 3 pauses `accept_all` (backlog kept): C3 accept checks then do not run; nothing to reconcile;
  - **counts:** increment in `adopt`'s success branch (`conn.rs` ~163), or roll back at both `adopt` failure exits
    (`conn.rs` ~66 TLS state, ~159 `ep_add`), which close the fd without `close_client`: otherwise a count leaks forever
    (eviction needs `conns == 0`) [rt]. Every other close (abort, reset, shed, peer_gone, drain) reaches `close_client`.
  - **`--max-conns`:** the sum of `Inbox.load` is not a snapshot (`metrics.rs` ~204), so two workers can both see spare
    room: use one shared atomic reservation (check-and-increment), held through a `--balance` handoff, rolled back on
    failure [rt].
  - handed-over fds still in `inbox.fds` when a worker stops (60.12 drain): check that they are closed and uncounted
    (today an fd leak at most; with C3b a count leak) [rt].
  - HostSock (40.01) counts our own socket memory, so a per-IP connection cap also bounds how far one client can push the
    levels. Later idea, not in scope: shed by key.
- **C7 [rt]:** more TCP-only client calls than 60.02 lists:
  - `set_nodelay` / `set_notsent_lowat` (`conn.rs` ~35-37): skip; listener keepalive (`net::listen`) does not apply;
  - `tcp_only_local` / `net::same_host` (`conn.rs:150`) returns "remote" for AF_UNIX, so unix clients get capped buffers
    under memory pressure: mark them local;
  - `net::bytes_received` (`sweep.rs` ~378) returns None, so the 70.08 stall rule never fires for a unix client holding a
    partial frame: needs a fallback or an explicit note; `net::peer_gone` (`sweep.rs` ~126) returns None (skip it);
  - credit v2 RTT sample (`upload.rs` ~350) retries `TCP_INFO` on every grant when it fails: cache "no RTT" for unix
    clients, or C7 adds a syscall in the upload path;
  - `adopt` picks TLS from the global config (`conn.rs:62`): with TCP+TLS and a unix listener, the listener kind must
    choose (kTLS `TCP_ULP` fails on AF_UNIX); `shutdown_step` (`mod.rs` ~619) must close the shared unix fd once.
- **C4:** workers never write stderr (60.02 rule: per-worker outbox, log thread; the metrics thread can be it). UDP
  per-stream bytes are per datagram (`udp.rs` ~62, ~120-125; one add per `recvmmsg` batch is possible, and
  `udp_send_one` returns `Ok` for dropped datagrams, so "sent" needs a distinct result) [rt]: ship C4 for TCP first.
- **C10a:** set it in `adopt` (covers `--balance` handoffs) [rt]; it is kernel TCP pacing, not an exact payload quota; a
  paced client never reaches the 20.21 `LOWAT_FAST` switch (harmless, document it). The kernel rule (pacing without fq
  since 4.13) needs a check in the source before release [rt: unverified].
- **C6 [rt]:** `run_timers` scans only `Connecting` targets (`mod.rs` ~663) and every attempt resets its deadline
  (`connect.rs` ~254): `TState::Proxy` needs its own overall deadline and both consumers updated. The Wisp host is only
  checked for UTF-8 / non-empty (`wisp.rs` ~135): validate it as an authority before it goes into an HTTP CONNECT line
  (header injection). The new `TState` arm sits in the per-event match: gate the OFF build with `disasm_norm.py`.
- **Every ON cost is measured against base-4** (regress `--new-args`); every OFF cost must tie (60.02 rule 0).

## Proposed order (waves)
Changes to the lead's draft: **C2 moves up to wave 1; C7 moves down to wave 2** (more TCP-only sites than designed,
one of them in the upload path); **C10a moves up to wave 2**; C4 UDP counters join the measured wave.
- **Wave 1 (core, off the hot path):** C8 -> C3a (`--max-conns`, `--max-streams-per-conn`: the 60.02 CRITICAL-1 /
  RESOURCE-1 fixes, no IP needed) -> C1 (+Q7, +Q2 own addresses) -> `push_fd` payload + C2 + C3b. Then tag base-5.
- **Wave 2 (operations, off the hot path):** C4 (TCP), C5 endpoint, C7, C10a.
- **Wave 3 (hot path, measured; complex):** C5 `rx_bytes` (Q6 A/B), C4 UDP counters, C10b, then C6. Then PROXY protocol (Q8).
- Each wave ends with a regress (OFF ties vs base-4; ON costs listed) and a tag.
- Design review split: reviewer B agrees with C2 in wave 1 and C10a in wave 2. Reviewer A agrees on C2, calls C10a low-priority filler
  (fine in wave 2 only because it is ~30 lines), and would put C8 in wave 2 and C7 in wave 3. Kept C8 in wave 1 (startup
  only, a few dozen lines, and C1's lists want it); C7 in wave 2 as the middle ground.

## Open questions for the maintainer (short)
- Wave 1: (a) C8 lists: a list flag on the command line **replaces** the file's list (my pick; 60.02: merging hides rules)
  or **appends** (Q9 wording)? (b) C3b and C2 together (my pick), or C3b for direct peers first? (c) Own interface

- Wave 2: (d) C5 endpoint 127.0.0.1 by default, no auth (my pick)? (e) C10a worth shipping without an upload cap?

- Wave 3: (g) Is C6 needed by a real user now, or park it after PROXY protocol?

## Answers (60.18 #13, 2026-11-01)
- a replace, b yes, c startup snapshot, d yes.
- **e: both caps early in wave 2 (C10a).** Download per client: `SO_MAX_PACING_RATE` on the client socket. Upload per
  stream: pacing on the target socket. Both set once (no hot path). A per-client upload total stays C10b (wave 3). The C10a
  spec must verify that pacing holds with splice and with kTLS (and settle the kernel "no fq needed" rule in the source).
- **f: document the unix stall rule** (no 70.08 stall shed for unix clients, `TCP_INFO` is unavailable) in 40.01 with C7.
- **g: C6 is needed** (production sites use it) and must reach **parity with wispurr's upstream-proxy behaviour**
  (baselines/wispurr, SOURCE.md: source pin): flags, URL schemes, DNS mode, error codes. The C6 spec starts with a table
  of wispurr's behaviour (from its source) and our mapping; Q1 / Q1b stay (socks5h only with `--upstream-trust-dns`, no
  direct UDP) unless parity needs a documented exception.
