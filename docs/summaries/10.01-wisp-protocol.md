# 10.01 Wisp protocol: what it is (analysis)

Source: ref/wisp-protocol/protocol.md (v2.1), ref/wisp-server-python (v1-only reference server).

## One-line
Wisp multiplexes many TCP/UDP sockets over ONE WebSocket. Browser proxies (Ultraviolet/Scramjet via
libcurl.js or epoxy-tls) use it, because a browser cannot open raw sockets.

## Frame (every WS binary message = exactly one Wisp packet)
`u8 type | u32 stream_id (LE) | payload...`  stream_id 0 = connection-level.

| type | name | payload |
|---|---|---|
| 0x01 | CONNECT  (c->s) | u8 stream_type (1=TCP, 2=UDP) , u16 port LE , hostname utf8 (rest) |
| 0x02 | DATA     (both) | raw bytes |
| 0x03 | CONTINUE (s->c) | u32 buffer_remaining LE (credit, in packets) |
| 0x04 | CLOSE    (both) | u8 reason |
| 0x05 | INFO     (v2)   | u8 major, u8 minor, extensions: [u8 id, u32 len LE, bytes]* |

## Flow control
- Server advertises N packets of credit per stream (CONTINUE on stream 0 at handshake).
- Client decrements per DATA packet; stops at 0 until a new CONTINUE.
- Server must buffer per-stream FIFO, and send CONTINUE again as it drains (python: every N/4 packets).
- UDP streams: no CONTINUE.
- Server->client direction has NO flow control in protocol; only WS/TCP backpressure.

## Handshake
- v1 (no Sec-WebSocket-Protocol header): server sends CONTINUE(stream 0, N) immediately.
- v2 (header present): server sends INFO(2,x, exts) -> client INFO -> server CONTINUE(0, N) or CLOSE(0, reason).
- Ext 0x05 stream-open confirmation: server sends CONTINUE on stream after TCP connect succeeds.
- Ext 0x01 UDP, 0x02 password, 0x03 ed25519 key, 0x04 MOTD.
- URL must end in `/`. Non-`/` paths = legacy wsproxy (`/prefix/host:port`, raw TCP over WS).

## Close reasons
0x01 unknown, 0x02 voluntary, 0x03 network err, 0x04 incompatible ext,
0x41 invalid, 0x42 unreachable, 0x43 timeout, 0x44 refused, 0x47 data timeout,
0x48 blocked, 0x49 throttled, 0x81 client error, 0xc0-0xc2 auth.
finalwisp sends 0x47 when an open TCP target times out (keepalive or retransmission ETIMEDOUT, 70.13); other open-stream errors are 0x03.

## Where the reference python server spends time (speed targets)
- websockets lib framing + per-packet `bytes` concat (`struct.pack(...) + data`): copies every payload.
- asyncio.Queue per stream + 2 tasks per stream; each DATA = queue put/get + drain await.
- Blocking getaddrinfo in executor thread per CONNECT.
- 64 KiB TCP reads -> one WS message each (good batching), but each send awaits.
- Defaults: blocks loopback + private IPs (SSRF guard). Must keep this behaviour as default.
