# 60.06 base-1.1 release notes (2026-10-24)

Pointers: 60.05 (full review: H1-H7), 60.03 (base-1), harden reports
raw data (not published) (REPORT-harden.md in a worktree), raw data (not published)

base-1.1 = base-1 + hardening. No new features, no new default limits.
- H1 `dirty` list stores (index, generation): no abort when a client is closed after being marked dirty in the same turn.
- H2 rbuf grows with received bytes, not with a frame header's claimed size (14 bytes no longer pin 16 MiB).
- H3 runtime log writes cannot panic (dead stderr pipe).
- H4 rust-toolchain.toml pins nightly-2026-09-05 (rustc f248f4038) so A/Bs vs a tag are not confounded.
- H6 client CLOSE(0) during WaitInfo closes cleanly; a pipe2 failure retries later instead of disabling splice.
- H7 memory pressure (L2/L3 only): a client whose in-progress frame does not fit its buffer is paused (bytes stay in the
  kernel) and shed first, largest first, every sweep; rbuf growth does not touch untouched pages.
  glibc: M_MMAP_THRESHOLD fixed at 1 MiB at startup (shown in the capability line). Reason: after big buffers are freed,
  glibc's dynamic threshold ratchets up and each non-main arena keeps its top (tens of MiB per worker); malloc_trim cannot
  release it, cgroup memory counts it, and the server stayed at L2 (no admission) after an attack ended.
  Slab arrays reserve 1 MiB (own mapping, idle RSS unchanged); host mode subtracts only the untouched reserve.

## Measured
- 1000 connections x 10 MiB frames (frame and fragmented, cgroup 256M and --mem-budget 256M): base-1 OOM-killed in 1.3 s;
  base-1.1 never OOM, cgroup peak 210-223 MiB, holders shed ~1 s, admission back <= 0.84 s after the last shed, honest
  64 MiB downloads 36/36-38/38. 100 x 16 MiB headers: +2 MiB RSS (was +1600).
- regress vs base-1: laptop lo/tls/idle 12 reps 0 LOSS 0 watch (all ties; idle 17.1 -> 17.3 KiB/conn);
  VPS2 link 16 reps 0 LOSS; VPS2 potato 6 reps 0 LOSS, 96/96 alive both.
- potato rr 128M (2 vCPU, 1 core scope) was investigated: 0.88-0.89 in two runs, then 0.99 (16 reps, bisect: no single
  commit) and 0.99 (24-rep tiebreak, p 0.34). Pooled 56 pairs: 0.98, p 0.04. Recorded as a possible ~2% cost in that corner.
- Gates: wst compat --bin --matrix 17/17, cargo test 33/33, adversarial incl. #19/#20.

## Known limits (unchanged)
20.27 honest-upload 0x49 behind a stalling target on ~200 ms paths; KeyUpdate on kernels < 6.14; idle RSS at 1-2 threads
depends on glibc arenas. Under L2+ an honest client sending a frame larger than its buffer is shed (pressure only).

## Deployment: panic = "abort" (60.04 F15)
The release profile sets `panic = "abort"` (server/Cargo.toml). A panic in any thread ends the whole process, so every
connection on every worker closes at once. This is deliberate: no unwinding cost or code, and no half-updated worker
state (or poisoned mutex) survives a bug. The panic message goes to stderr. Run the server under a supervisor that
restarts it, for example a systemd unit with:

```
[Service]
ExecStart=/usr/local/bin/finalwisp --host 0.0.0.0 --port 6001
Restart=always
RestartSec=1
```

Clients see the connection close and reconnect. Known panic sources are fixed when found (20.09 re-entry, 60.05 H1/H3);
network input does not reach a panic in the parsers (60.04 section 3).
