# 60.12 Post-base-2 design review (2026-10-27): backlog priorities

Pointers: 60.10 (base-2 notes, backlog), 60.07 (B1-B3), 60.02 (C1-C10: C3 = limits, C8 = config file), 20.27, 20.26, 70.14.
Seats: reviewer A, reviewer B; reviewer C unavailable (402). Claims checked in code are marked [checked].

## Agreed by both
- A first, time-boxed: #2 obuf at L2. [checked] mem.rs L2/L3 keep = 64K, and free_drained(level>=2) frees cap > keep, while a
  read_target obuf is at least 69632 (reserve(ROOM_WISP+CHUNK)): every drained obuf at L2+ is freed (the "echo at L2+ maps"
  limit). Reviewer A: the 512 KiB growth is likely L1 (out_high 256K), already handled by 70.14; measure the level log with strace.
  Candidate: L2/L3 keep = 2 x out_high (128K).
- #1 credit redesign stays top, but write the acceptance bar first (0/40 kills at 200 ms stalling sink, >= 0.95 of base on
  1x1 stalling sink, echo 10x10 peak <= ~0.7 base, no whole-connection hold when honest) and spike the hard part
  (retiring overwritten credit). Cheap interim: PEND_HARD scaled to the stream window. The hold pauses the WHOLE connection
  (sibling streams too): test siblings on the same connection.
- Missing: minimal observability (event counters + periodic metrics log line; C5-lite), before B3 and C features.
- Missing: graceful shutdown/drain on SIGTERM [checked: only SIGHUP is handled], systemd unit + deployment doc.
- Missing: reverse-proxy coverage (nginx/Caddy in front) as a gate; untuned-host WAN runs; longer soak on the final binary.
- B3 is real for small VPSes (cgroup mode does not read sockstat); needs its own pressure benchmark (regress marks those
  cases invalid). B (sampler/caps) and A (hot path) must share one cap rule (tighter wins, restore once).
- Worker split OK if A owns the worker.rs hot path (incl. the rr ~2% probe), B is confined to mem.rs/net.rs caps, C lands
  dns-own (rebased) before A's credit change.
- C3 limits: --max-conns / --max-streams-per-conn early (fd exhaustion is not covered by the memory budget); a global
  connection limit needs an accept-time reservation, not a sum of Inbox.load (reviewer B).
- B1: stays parked; write a 1-page Wisp v2 download-credit proposal for upstream now (long lead time).

## Added 2026-10-29 (from 70.20 / 50.02)
- Burst memory: in an echo burst each stream's pend doubles 16K -> ~1 MiB; 1000 streams ~ 1 GiB (matches the 1.2-1.6 GiB burst
  HWM in 70.18). A bound on pend per stream / per connection at L0 is a credit/flow question (owner: credit), not an allocator one.
- UDP: read_udp checks out_high once per 8-datagram batch and has no read-path compaction, so a UDP client's obuf at L2 can pass
  the bound (70.20; unmeasured).
- "Compact before growing" (reviewers, 70.20): rejected for now (up to ~15 copies per byte at L0, ~0 measured gain); revisit only with data.
- 50.02 wss download zero reps under host TCP pressure (VPS1, kTLS): open, owner flow.
- Scudo (70.22, branch scudo-try): QUEUED (user 2026-10-29: "investigate more"). Idle 1.3/2.6 vs 4.7 KiB/conn (t2/t16) with an
  idle-sweep M_PURGE (~40 lines); risks: idle-echo peak +10%, futex 10-40x in echo 100x10 at 4 thr (CPU unknown), no fallback at
  vm.max_map_count (abort), 188 GB VSZ (RLIMIT_AS), SCUDO_OPTIONS env read at runtime, CI needs the same LLVM package.
  Next: gates (membudget, matrix, fuzz-replay), then the VPS A/B of 70.22 section 6 (bar: tie/win every CPU case on both boxes,
  idle win, map-limit case must not abort; a CPU loss = stop), then laptop thread scaling (quiet laptop, user OK).
- musl + Scudo (user 2026-10-29: "throw it in the ring", low priority): Stage 2 extra only, when Scudo is built from source anyway.
  One A/B glibc+Scudo vs musl+Scudo (connchurn t8/cores/all, echo, idle, burst peak). Adopt ONLY for a meaningful pro over
  glibc+Scudo (user: "a bit better" is not enough), e.g. a clear memory or CPU win that also outweighs forced --dns-own and the
  musl C/C++ toolchain in the build. Known context: Chimera Linux ships musl with Scudo as malloc (unverified this session).
- an archived note (not published) is stale (map_weight etc. no longer in mem.rs; slabspec 2026-10-29): mark it historical or update.

## Added 2026-10-29 (from 50.02 gold A/B, flow)
- Stream errors at scale: gold (72 threads, plain ws, loopback) `wst ab` download 100x10 at --threads 8 had 104 errors in every
  run on BOTH base-3 55d175ae and A2 16808573 (108 once on base-3); wbench stderr "server closed stream N (reason 0x03)", conns_ok
  100, throughput normal (~9 GB/s). 0x03 = our CLOSE "network error" (target_eof(ti, 0x03) in worker.rs on a target read error).
  To check: which target error (ECONNRESET at teardown? fd/backlog limits at 1000 streams?) and whether wbench counts teardown
  closes. raw data (not published) (copied from raw data (not published)).
- Flaky gate wispjs-udp under CPU load (2026-10-29): "UDP echo stream 0: timeout N/300" (v1 and v2, stream 1 fine). With 14 busy
  loops on the laptop: base-3 4/12 runs fail, master+ktls-starve 2/12; unloaded 0/4. Pre-existing, load-only (UDP loss or a short
  per-datagram timeout in tests/compat). Fix the test (retry/longer timeout, or count loss) so gates are not load-sensitive.
  raw data (not published)
- CLOSED 2026-10-29 (stream errors at scale, above): cause = harness, not server. wst children inherited an interactive
  shell's soft RLIMIT_NOFILE 1024, so 100x10 cases (1000 target sockets) failed ~190 streams (finalwisp, base-3) / 86 (epoxy)
  with 0x03. Gold showdown with `ulimit -n 524288`: 0 errors, download 100x10 master 18.20 / base-3 17.43 / epoxy 10.48 GiB/s
  (14 vs 41 cores). Fix: wst main raises soft to hard for every command. the flow branch's gold A/B dl 100x10 t8 (50.02) ran fd-starved
  (~10-20% of streams failed on both sides): that row is INCONCLUSIVE, not a tie; rerun with the fixed wst. The 10x10 and 1x1
  rows (<= 100 streams) were not affected.
- Not a bug (2026-10-29): reviewer C P2 "wst skips the NOFILE raise when hard = RLIM_INFINITY". On Linux the kernel refuses a NOFILE hard
  limit above fs.nr_open (do_prlimit, EPERM), so hard is never infinite; the plain soft<hard raise is correct (reviewer A review).
- B3 default-on evidence weakened (audit rescore with the paired-HL verdict fix, 2026-10-29, 30.13 on bench-audit): side-rr beside a
  bulk holder (jB-base2 upload10 holder0, jB-cur download10/echo10 holder0) and holder0 HWM flip watch/tie -> LOSS; eqsrv download20
  side p99 watch -> LOSS (auxiliary). B3 stays opt-in (no adoption reversal), but any B3 default-on evaluation must re-measure these
  side-rr/latency cases with the fixed stats first.
- --balance default-on candidate (audit, gold 2026-10-29): rr 10x10, 36 workers, 8 fresh starts each: without --balance the kernel
  reuseport hash puts 10 conns on 7-10 workers and req/s steps 375k/407k/423k/443k with collisions; with --balance all 8 runs use 10
  distinct workers, 441-448k (median 446k), no rr penalty there (the laptop 20.10 cost was -10..25%). Exploratory sequential cohorts,
  not a verdict: needs an interleaved A/B on laptop + VPS + a big box (rr/churn/bulk at several conn counts) before any default change.
