## Findings
### F1: config-parse "value shown" on the C10a rate message (harness false positive; message reworded)
- 07:05:03Z, lane 3, crash-c57d31ee (49 B). The file line `download-rate =\r` gives the value "=". The error was
  `--download-rate: bytes per second, 0 (off) or 16K..4095M (K/M/G = KiB/MiB/GiB; 1M = 8.4 Mbit/s), not (value not
  shown)`. The value is redacted. The harness checks only values that contain a character from its MARK set
  "@!$&*=~^|{}" (characters "no message text has"), and the C10a message has '=' twice.
- Fix (lead's decision, option B: keep the harness rule, change the server text): master cd20e93
  "(K/M/G: KiB/MiB/GiB; 1M is 8.4 Mbit/s)". The --help text is unchanged. Rebuilt config-parse, lanes 3 and 8
  restarted 07:09:01Z. Regress seed regress/config-parse/f1-rate-msg-eq-c57d31ee (replays clean).
### F2: config-parse "value shown" on the C1 ports message (same class; message reworded)
- 07:25:33Z, lane 8, on the F1-fixed binary, crash-c70f1ce7 (711 B; a line `allow-host |` gives the value "|"). The
  error was `--allow-ports: entry 1 of (value not shown): not [tcp:|udp:]N or N-M (1-65535)`, and '|' is in MARK.
- Fix: master c75afcc + 623b825 (rustfmt) "not N or N-M (1-65535), optionally after tcp: or udp:". Nothing quoted
  the old text. Lanes 3 and 8 restarted 07:28:31Z. Regress seed regress/config-parse/f2-ports-msg-bar-c70f1ce7.
  Both inputs replay clean on the final binary. No config-parse artifact after 07:28Z (6.2 h, 381 M execs).
- Literal scan (after F2): every non-test string literal in cli.rs, policy.rs, clientip.rs, upstream.rs, net.rs and
  dns.rs, with `{...}` format placeholders removed, checked for a MARK character. 4 hits: the F2 message (fixed) and 3
  benign ones:
  - cli.rs:192, the braces of the `Expanded` Debug impl (not an error message);
  - cli.rs:559, the RFC 9110 tchar set of --real-ip-header (a byte set; that error is `not a header name: {v:?}`,
    the value redacted by expand_config);
  - upstream.rs:238, `***@`, the masked credentials in the --upstream display string (capability line only; no error
    uses it).
  So no config-reachable error text has a MARK character any more.
- Lesson: a redaction check keyed on "characters no message has" needs a test of that premise. A unit test could
  scan the error strings, or the fuzz target could assert MARK against a list of all messages. Not added here (no
  server code in this task); suggested as a follow-up.
- Built later (branch mark-test, merged into master in f4202b2c = base-6-rc1): `REDACTION_MARKS` in cli.rs is shared
  with the config-parse fuzz target, and the unit test `cli::tests::error_texts_have_no_redaction_marks` (server/src/
  cli.rs) checks the premise. It runs every flag with 48 plain values on the command line and as a `--config` key,
  each flag with no value, value-less flags with a value, the config file's own line and size errors, argument shapes
  and `check()` prerequisites, and 16 values that hold a mark in a `--config` file only (there the value is hidden).
  No error text may hold a mark character. It led to 3 error-text fixes:
  - 96e500c6: the C10b `--upload-rate` / `--upload-rate-per-ip` texts said `>=`; now "at least".
  - c8a8d6f7: a `--proxy-protocol` error showed one entry of the value; from a `--config` line that leaked part of a
    hidden value. It now shows the whole value (a `--config` line hides it, as for every flag).
  - 9444a984: the C10b burst error showed the parsed parts; it now shows the whole value, hidden in the same way.
