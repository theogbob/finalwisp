## Setup
- Box: e5 (rented) could not be used: a Docker container without CAP_SYS_ADMIN/NET_ADMIN, `unshare -n`/`-Urn` EPERM, no
  /dev/kvm. The harness needs its own network namespace (it refuses to run otherwise: IP-literal CONNECTs would leave the
  box; fixed sink ports 4444/4445 collide across lanes). Lead decision: the build host, ephemeral Incus container fw-fuzz4
  (debian 13, security.nesting=true, limits.cpu=10, limits.memory=24GiB), everything at nice 19. Deleted at the end.
- **Host change on the build host: `sudo modprobe tls` at 2026-10-31 00:45:33Z** (lead approved; not persistent). The host
  had no tls module loaded and a container cannot autoload it (TCP_ULP "tls" -> ENOENT), so worker-tls would stop after
  the handshake. The module stays loaded until the next reboot of the build host.
- Source: git archive of base-4-rc1 (server/ + rust-toolchain.toml), toolchain nightly-2026-09-06 (the pin), cargo-fuzz
  0.13.2, `cargo fuzz build -O` (70.01 profile: debug assertions + overflow checks from the fuzz profile, ASan + LSan),
  two trees: oa (default, own-alloc) and na (--no-default-features). Seeds: seeds.py + the committed regress corpora.
- Plans server/fuzz/plan-70.27-oa.json (6 lanes) and plan-70.27-na.json (4 lanes; removed with the NOFEAT build in
  60.18 #11: `git show base-4:server/fuzz/plan-70.27-na.json`), 36000 s per lane, driver
  campaign.py unchanged (fork mode, bwrap --unshare-net). Stateful targets got full lanes in both builds; parsers ran
  in sequence on one lane per build. Start 00:47:14Z, end 10:53:19Z.
- 04:11Z both drivers were restarted (same lanes, remaining time, corpora kept) with ASAN_OPTIONS=log_path=sanlogs/<b>
  and LSAN_OPTIONS=report_objects=1, so a report survives libFuzzer's deletion of the job log (see L1). Side effect: the
  restart reused the lane log names, so the execs of segment 1 come from the 03:42Z snapshot (the 03:42-04:11 tail of
  the overwritten lanes is not counted: the totals are lower bounds).
- Checks: at 13 min and 1 h every lane was executing (0 crashes); a watcher polled artifacts/ and sanlogs/ every 60 s.

## Finding L1: LeakSanitizer report in an own-alloc worker-tls fork lane (false positive mechanism; fixed in fuzz builds)
- Lane 2 (oa worker-tls) job 144 exited with a LeakSanitizer report at 03:41Z; the lane log has only the ERROR line and
  libFuzzer deleted the job log, so the stack is lost. The input (TLS 1.2, ChaCha20) replays clean 3/3 and 300x in one
  process; the whole worker-tls corpus (2266 inputs) replayed in one process with -detect_leaks=1 is clean; 25 min of
  non-fork fuzzing from that corpus (3.1 M execs, in-loop leak checks never auto-disabled) found nothing; the na build
  never reported one.
- Mechanism (proven): the own-alloc pool serves 16-128 KiB from mmap'd 4 MiB chunks. LSan scans only its own heap,
  globals, stacks and registered root regions, so a glibc block referenced only from a pool block looks unreachable.
  Direct test (worker-stream fuzz build, same source A/B): a 64-byte malloc block referenced only from a 32 KiB pool block
  -> "Direct leak of 64 byte(s) in 1 object(s)" without the fix, clean with it.
- Not proven: that the 03:41Z report was this mechanism (no stack). No further report in the remaining 6.7 h with
  sanlogs on.
- Fix (master 73881a8, from branch fuzzlsan): `--cfg fuzzing` only, pool.rs set_member registers each mapped chunk as an
  LSan root region and unregisters it before munmap (weak symbols: no-op in `cargo fuzz build -s none`/coverage builds).
  Harness self-check `lsan_pool_check()` in Harness::new (own-alloc) asserts the case above. Release code: disasm_norm
  master vs branch 3276/3276 identical (default and NOFEAT); the default md5 changes only through panic-location line
  numbers (343bd7f0 -> bc459772). Reviews: reviewer B (no findings), reviewer A (clean; P3 fixed). Tradeoff: a pointer left in a
  freed pool block can now hide a real leak in the own-alloc build; the --no-default-features build keeps full precision.
- The campaign itself ran the RC1 source (no fix); RC1 server code is unaffected by L1 (no server behaviour involved).

## Real-browser suite (bench/browser, laptop, nice 19, functional only)
- Matrix as for base-3 (60.14): 15 cases (10 pages, wikipedia session, ws-echo, 2 downloads, busy-user) x epoxy /
  epoxy-v2 / libcurl x 2 reps = 90 per mode, fw-rc1 (md5 40ce5430), real internet, Scramjet b14b709a, Chromium 156.
- **Plain ws://: 86/90. TLS wss:// (built-in TLS + kTLS): 86/90.** Server alive after every run, 0 harness
  errors, 0 leaks (no request escaped Scramjet). Results: raw data (not published)
- The 4 failures (both modes, both reps): youtube with epoxy and epoxy-v2: `hyper::Error(Http2, Reset(StreamId(1),
  PROTOCOL_ERROR, Library))` inside epoxy's wasm HTTP/2 client -> Scramjet answers the document with 500. Re-run:
  identical on fw-rc1, base-2 (fw-base2b), epoxy-server and wisp-js; libcurl passes youtube on every server
  (raw data (not published)). It passed on 2026-10-28 (60.13): an upstream change (YouTube vs epoxy's h2
  client), not RC1. Not a Wisp-level failure (the stream carried the TLS records; the client's own h2 layer reset it).
- Harness change: `bench/browser/browser.py --tls` (fw: servers only): a per-run self-signed P-256 pair (openssl, in
  the run's scratch dir), finalwisp gets --tls-cert/--tls-key, the Wisp URL is wss://, and Chromium gets
  `--ignore-certificate-errors-spki-list` for that key only. Negative control: a wrong SPKI hash fails (document 500).
  Refused: non-fw servers, fw specs that already carry a cert, --trace (its pipeline split assumes plaintext). README
  updated. Review: reviewer B + reviewer A (2 rounds), findings fixed.

## Lessons (harness)
- rented containers cannot run the fuzz harness (no netns); use an Incus container with security.nesting.
- Containers cannot load kernel modules: kTLS targets need `tls` loaded on the host first.
- libFuzzer fork mode deletes a crashed job's log; set ASAN_OPTIONS=log_path from the start of a campaign.
- campaign.py names lane logs `<t>-lane<i>-<n>.log` with n reset per driver start: a driver restart overwrites them.
