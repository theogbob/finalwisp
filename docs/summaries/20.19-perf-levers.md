Pointers: 20.06 performance findings (history), 10.01 protocol, 30.01 bench/wbench, 30.09 bench/ab.py +
bench/vps/netns_hol.sh + bench/vps/slowdns.py + bench/dns_burst.py + bench/dns_hol.py (new in this branch),

Lens: protocol / userspace / client-visible behaviour under realistic workloads (one browser = one WebSocket
carrying bursts of short streams plus the occasional bulk download). Everything below was measured with
interleaved A/B runs (bench/ab.py: start server variant, run wbench, kill, next variant; median of N), on the

(wisp-js 0.5.0).

## Verdicts (one line each; the rate-limited-link numbers decide, loopback hid all of this)
- **SHIP, default on: `--notsent-lowat 131072`** (TCP_NOTSENT_LOWAT per client socket). 100 Mbit / 20 ms link,
  1 bulk download + pages of 6 small streams on one WebSocket: request p50 **610 -> 222 ms** (8 rotated reps),
  bulk still at link rate; 1 Gbit / 100 ms RTT single stream still = link rate (113 MiB/s); no regression on
  rr/churn/download/echo/upload on laptop or VPS loopback (7 reps rr/churn; rr 10x10 VPS recheck 0.994).
  Knob stays (0 = kernel default). Cost: +5% of one core at 950 Mbit (more wakeups).
- **SHIP: DNS in-flight coalescing + resolver pool 4 -> 16 threads** (`--dns-threads N`, `--no-dns-coalesce`).
  Page DNS phase with a 20 ms resolver: 1x6 44 -> 22 ms, 3x6 107 -> 23, 6x6 193 -> 25 (both together); a
  stalled upstream name blocks every other lookup for 3,024 ms today vs 22 ms coalesced; NXDOMAIN fan-out
  18/18 correct. ~30 lines in net.rs + a unit test (every waiter gets its answer, incl. failures).
- **KNOB, default on since 20.22 (`--no-prio` = off), two-lane client output** (`--prio`): on the same link, with lowat, **222 -> 168 ms**
  (runs 177-241 vs 163-198, ~25% more); alone only 610 -> 553 (the kernel queue dominates); neutral on loopback;
  adversarial + wisp-js 0.5.0 pass. My complexity call: it adds a second output lane with ordering invariants
  (absolute byte counters, frame-end ring, lane stickiness per stream, CLOSE placement, lane drop on close)
  to the hottest path in the server, and the prototype needed one ordering fix already. 25% on top of
  lowat is real but not large enough to carry that without (a) a review of `flush`/`send_bulk`/lane choice
  and (b) a throttled-client frame-order test (6.4). Ship it as a knob now; flip the default after both.
- **REJECT (measured or by analysis):** OUT_HIGH 256 KiB as a lever on its own (no gain on top of lowat on
  the link, 278 vs 221 ms; loopback gains are cache effects); framing / CONTINUE cadence; credit default;
  per-stream memory; allocator; setup cost; unmask fusion. Details in section 5.
- **KEEP:** the `browse` workload (wbench) + `reply` target, bench/ab.py (rotating A/B), the VPS netns
  rate-limited link and stub-resolver scripts: loopback cannot see any of the effects above.

## 1. Workload: `browse` (new, 30.01 wbench)
`wbench run --test browse --conns C --streams S [--bulk B] [--resp 2048,8192,32768,131072] [--reqs-per-stream 1]
[--page-gap-ms 0] [--bulk-size 64M]` against `wbench target --mode reply`. Per connection: a "page" = S short
streams opened at once (CONNECT + one 512-byte request in the same write; the request header tells the reply
target how many bytes to answer: 2 KiB, 8, 32, 128 KiB cycling), each stream is CLOSEd after its response,
the next page starts when the last stream of the page closed; plus B bulk streams that request --bulk-size
bytes again and again. Reported: req/s, request latency (CONNECT -> last response byte) p50/p90/p99, pages/s,
page latency, bulk MiB/s. The reply target speaks a trivial length-prefixed protocol ([u32 resp][u32 req]).
Sanity (laptop loopback, 1 conn x 6 streams, 4 s, 5 reps): 3,796 req/s, request p50 361 us, page p50 423 us,
server CPU 20% of a core. With one bulk stream added: 4,423 req/s, p50 659 us, bulk 6.5 GiB/s, CPU 98%
(the loop is saturated by the bulk stream; the small streams ride along). VPS: 1,736 req/s, p50 2.1 ms, bulk
1.9 GiB/s (client-bound: wbench shares the 4 vCPUs).
What it shows: on loopback the small-stream latency doubles behind a bulk stream (361 -> 659 us) although
the link drains at GiB/s; that is the server's own FIFO queue (OUT_HIGH 1 MiB: 1 MiB / 6.5 GiB/s = 160 us
plus the 4 MiB socket buffer). On a real link the same queue is seconds (section 2).

## 2. Latency under mixed load (head-of-line behind a bulk stream)
Mechanism: one WebSocket = one TCP connection = one FIFO. Server side the FIFO is obuf (up to OUT_HIGH 1 MiB
+ one 64 KiB read, or + 256 KiB splice pipe) followed by the kernel send queue (tcp_wmem autotunes to 4 MiB;
only the in-flight part, about one BDP, is useful; the rest is just queue). A 2 KiB response for another
stream enters at the tail. At 100 Mbit/s, 5 MiB of queue = 420 ms; at 20 Mbit/s = 2 s. Every browser request
in every other tab pays it while any download runs. The protocol has no server->client flow control, so the
client cannot help; only the server's queueing order and depth matter.

### 2.1 Setup (VPS, root, namespaces only: bench/vps/netns_hol.sh RATE DELAY LIMIT)
fwa (wbench client) <- veth, netem delay 10 ms each way, rate 100 Mbit, limit 200 pkts -> fws (finalwisp +
targets on loopback). `ab.py` with SRV_PREFIX/CLI_PREFIX runs each variant in its namespace. 4 s runs,
1 conn x 6 short streams + 1 bulk stream, 5 interleaved reps.

### 2.2 Results, 100 Mbit / 20 ms RTT (request latency = CONNECT to last byte of a 2-128 KiB response)

lowat: another 25%, non-overlapping runs). The remaining ~170 ms is 128 KiB unsent (11 ms) + in flight
(~550 KiB with the 200-packet netem queue, 50 ms) + the page's own transfer (180 KiB, 16 ms) + RTT + queueing
of the six responses behind each other; a smaller lowat (64 KiB) would shave ~5 ms more at more wakeups.

### 2.3 No throughput cap on a long fat link
VPS netns 1 Gbit / 50 ms each way (RTT 100 ms, BDP 12 MB), download 1x1, 6 s, median of 5 (default socket
buffers; the client's tcp_rmem caps at 3 MiB in flight): base 27.9, lowat 27.8, lowat+oh256 27.7 MiB/s.
With tcp_rmem/tcp_wmem max raised to 64 MiB in the namespaces (3 reps): base 113.1, lowat 113.1, both
113.1 MiB/s = the link. Cost: server CPU 3.1% -> 8.3% of a core at 950 Mbit (the loop wakes up per 128 KiB
of unsent space instead of per 4 MiB). echo 1x1 at 1 Gbit/100 ms: 28.2 / 28.1 / 29.3 MiB/s.
Why lowat does not cap: TCP_NOTSENT_LOWAT limits bytes *not yet sent*, not bytes in flight; the kernel keeps
the full cwnd on the wire and asks for a refill (EPOLLOUT) when unsent < 128 KiB; the loop refills within one
turn. Apple (all platforms) and Cloudflare use the same 128 KiB value for this reason.

### 2.4 Two-lane output (`--prio`; prototype c663a63, port in perf-reviewer A-merge; worker.rs `bulk` lane)
Streams whose last read filled CHUNK ("bulk mode", the flag that already selects the splice path) write their
DATA frames into `Client::bulk` instead of `obuf`; `flush` sends obuf first, then the lane. Order inside a
stream is kept: a stream with unsent bytes in the lane stays in the lane (`Target::bulk_end` vs
`Client::bulk_sent`, absolute byte counters), its CLOSE goes behind them, a partly sent lane frame is finished
before anything from obuf (`bulk_ends` ring of frame ends), wsproxy never uses the lane, and a connection
close drops the lane (the WS Close frame is already in obuf; RFC 6455 forbids data after it). The splice path
still requires both lanes empty. Memory: one extra Vec per client, freed by the idle sweep.
Loopback laptop (5 reps): browse+bulk req p50 686 -> 699 us (noise), echo 10x10 3,050 -> 3,225 MiB/s,
download 10x10 10,745 -> 9,808 MiB/s (runs 9.9-11.1k vs 9.6-11.2k: overlap). VPS loopback, rotated order,
6 reps (base / lowat / lane+lowat): download 10x10 3,754 / 3,625 / 3,690 MiB/s, echo 10x10 783 / 845 / 782,
browse+bulk req p50 2,231 / 2,316 / 2,367 us: all within the run-to-run spread. Compat: adversarial.py (15) +
wispjs.mjs v1+v2 (wisp-js 0.5.0) incl. "echo during bulk download intact" and 2x64 MiB pattern downloads:
ALL PASS with lane + lowat on. Rate-limited link: section 2.2 (lane + lowat 168 ms vs lowat 222 ms).
Verdict: it is the only lever that touches the server's own queue order and it is worth 25% on top of
lowat on a real link; it is neutral on loopback; its risk is the output-order invariants in the hot path
(one bug found and fixed during the prototype: a partly sent lane frame followed by obuf bytes). Ship as a
knob (default off, `--prio`); flip the default once (a) a review has gone over `flush`/`send_bulk`/
`read_target` lane choice/`close_target` and (b) the throttled-client frame-order test (6.4) exists.
The bug found in the prototype is also the first thing a reviewer should re-derive: a frame may be split
across two send() calls, and the lane switch must never happen inside a frame.

### 2.5 OUT_HIGH 256 KiB (lever 5)
Loopback: browse+bulk req p50 659 -> 385 us (laptop, 5 reps, runs 541-721 vs 351-407), VPS 2119 -> 1751 us.
download 10x10 laptop 9,862 -> 11,572 MiB/s with CPU 438 -> 355%; VPS 3,458 -> 3,926 with 198 -> 156%
(smaller hot set per connection). echo 10x10 and rr 10x10 within noise on both. download 1x1 VPS loopback
2,224 -> 1,850 (runs 1681-2448 vs 2081-2568; lowat+oh256 2,262): unresolved, probably noise. On the 100 Mbit
link it did not improve on lowat alone (278 vs 221 ms, overlapping runs). Verdict: a real memory/cache win on
loopback, but the two-lane output removes the reason for it (the bulk backlog no longer sits in front of
small frames), so decide after 2.4: if the lane is taken, keep 1 MiB; if not, 256 KiB + lowat.

## 3. DNS
Before 20.19: 4 getaddrinfo threads shared by all workers (`net::start_dns_pool(4)`), per-worker positive cache
(30 s, cleared entirely at 4096 entries), no negative cache, no in-flight dedup. A page load opens several
streams to the same host in one burst, before any answer is back, so each stream costs a pool thread for one
resolver round trip (20-100 ms on real resolvers; glibc also serialises A+AAAA per call).

### 3.1 In-flight coalescing + pool size (VPS netns, stub resolver bench/vps/slowdns.py: 20 ms per query)
bench/dns_burst.py: one Wisp connection; per round H fresh names x S streams, CONNECT + request in one
write; time until every stream answered. 15 rounds, median of 3 reps, ms:
| page | base (4 thr) | 16 thr | coalesce (4 thr) | coalesce + 16 thr |
|---|---|---|---|---|
| 1 host x 6 streams | 43.7 | 23.6 | **22.1** | 22.2 |
| 3 x 6 | 107.4 | 44.1 | **23.3** | 23.2 |
| 6 x 1 | 43.8 | **23.4** | 43.7 | 23.4 |
| 6 x 6 | 192.7 | 67.9 | 44.1 | **24.7** |
One resolver round trip (22 ms) is the floor; base is 2-9x above it. Coalescing is ~25 lines in
net.rs (a HashMap of in-flight names -> waiters, taken under the pool mutex; the resolving thread delivers to
every waiter's inbox). The per-worker cache is untouched (a worker still learns the answer once).

### 3.2 Failure fan-out and a stalled upstream (bench/dns_hol.py, 2 reps, all four variants)
- NXDOMAIN: 6 streams to one fresh `.nx` name per round, 3 rounds: every stream got its own CLOSE in every
  variant (18/18), so the coalesced path delivers failures to each waiter like successes (same DnsResp with
  an empty address list, per waiter).
- Stalled upstream: 6 streams to one name whose lookup takes 3 s, then one stream to a fast name (20 ms):
  the fast name answered after **3,024 ms** with today's pool (4 threads, all blocked by the same name),
  **22 ms** with coalescing (one thread blocked), 23.5 ms with 16 threads (6 < 16). With glibc's defaults a
  dead upstream blocks a thread for 10 s (5 s x 2 attempts), and one slow site can do this to every
  client of the server today.

### 3.3 Negative cache (built later as 20.23, see 20.06)
A failed lookup is not cached: every CONNECT to a dead name costs a full resolver round trip (and, for a
timing-out upstream, a pool thread for glibc's timeout x attempts = 10 s). Coalescing already collapses
concurrent repeats; a short negative TTL (5-10 s, CLOSE 0x42 at once) would collapse sequential ones
(a page retry, a reload). wisp-js/epoxy do not negative-cache either, so it is a server-side extra, not a
compat item. Small (10 lines in new_target/inbox_ready); recommend building with the above, default a few
seconds, because the pool is the shared resource all clients wait on.

## 5. Checked and rejected (with the reason)
- **WS/Wisp framing overhead, coalescing DATA, CONTINUE cadence.** Download: one frame per target read
  (payload up to 65,530 B behind a 4+5 byte header = 0.014%; reads under 126 B get a 2-byte header; splice
  chunks up to 256 KiB per frame). Merging consecutive small reads of one stream into one frame would save
  9 bytes and nothing else: the frame headers are written into the same buffer and go out in the same
  send(). Upload: frames are the client's; the server already batches consecutive DATA into one writev
  (20.09). CONTINUE: 13 bytes every 64 DATA packets (buffer/2) and never for streams that send fewer than
  64 packets (every browse stream): 0.1% of upload bytes at 16 KiB packets. Nothing to win; the numbers in
  20.06 (rr 306-409k req/s, 7+ GiB/s download) already say the framing is not on the critical path.
- **Credit default (128) vs RTT.** 128 x 16 KiB = 2 MiB per RTT caps one *upload* stream at 28 MiB/s on a
  71 ms link (20.06 30.05); browsing uploads are tiny and real clients send 16-50 KiB packets. `--buffer` is
  the operator knob for upload-heavy deployments; adaptive credit would add wire behaviour clients must
  tolerate (wisp-js replaces its credit with each CONTINUE value, epoxy too) for a case nobody has reported.
  Reject.
- **Memory per stream / connection.** Userspace: Target 176 B + slab slot 8 B + StreamMap entry ~16 B +
  `pend` Vec (0 B until the target socket refuses a write) = ~200 B per stream; Client 264 B + rbuf 16 KiB
  (grows to 256 KiB only under load, freed when idle, 20.11) + obuf (sized by what is queued). The kernel's
  TCP socket (~2-3 KiB + its buffers) dominates by 10x. Idle connection 12-14 KiB measured in 20.11. Reject.
- **Allocation behaviour / allocator.** Per frame: no allocation (frames are parsed in place in rbuf; DATA
  goes out by pointer). Per CONNECT: one String (host), the Target, a HashMap insert; per DNS miss one
  DnsReq/DnsResp. Fragmented messages (none from real clients) allocate once. Buffers grow by doubling
  and are released by the idle sweep. A different allocator could only change the <2% of CPU that is our
  code at all (20.06 profile: socket copies, page zeroing, unmask = 60%). Reject.
- **Connection setup cost.** accept4 + 2 setsockopt + epoll_ctl + 4 KiB rbuf + httparse + SHA-1 + the 101
  response, INFO/CONTINUE queued in the same send(): tens of microseconds, against a TCP (and usually TLS)
  handshake of one RTT. The TLS handshake is rustls in the loop (20.13, measured there). Reject.
- **Unmask / copy avoidance.** unmask_avx2 is 11% of the bulk-upload profile and memory-bound (stall on the
  first load of each line). The payload is read into rbuf by the kernel (copy_to_iter), XORed in place, and
  copied again by writev (copy_from_iter): three passes. The XOR cannot be fused into either kernel copy
  (no such interface), and 20.06 already tried smaller reads to keep the XOR in L1 (no gain). io_uring with
  registered buffers would remove nothing (the mask pass stays). Reject.
- **Splice header send + splice = 2 syscalls per 256 KiB chunk.** vmsplice of the header into the same pipe
  would make it one splice, but SPLICE_F_GIFT semantics and pipe ordering add risk for ~4k syscalls/s per
  GiB/s. Not worth it.

## 6. Missing benchmarks / tests to add
1. `browse` (with and without `--bulk`) in run_matrix.py / showdown.py against epoxy, wisp-js, wispurr:

   during this work was invisible on the laptop (A/A 1.002 / 0.989) and real on the VPS.
