# wss download 10x10: zero-throughput reps under host TCP memory pressure (VPS1)

Status: open, pre-existing (base-2 shows it). Not fixed in the B3 redesign branch (lead, 2026-10-29). Found by the flow work.

## What is seen
- Case: `wst regress` tls suite, `wss download 10x10` (kTLS, 10 conns x 10 streams, 4 s runs), loopback, on VPS1 only
  (VPS host, 2 vCPU EPYC-Rome, kernel 6.8.0-147). The host is in net.ipv4.tcp_mem pressure during the case (the harness
  marks it invalid: "host TCP memory pressure (41x)").
- A zero rep: wbench reports `mib_s_down` 0.0 (or < 1: 0.02, 0.28, 0.32, 0.57), `errors 0`, `conns_ok 10`, `stall_pings 0`,
  `lost 0`, server `cpu_pct` 3-5 % (idle), hwm ~10 MiB. The connections and the handshakes succeed; no data moves.
- Counts:
  - B1 on VPS1 (16 reps, base-2 50560e9a vs cand B 0d6f5a05 with --tcpmem-adapt): base 5/16 zero, new 7/16 zero
    (Fisher p ~0.7). Non-zero medians: base 454, new 563 MiB/s; the 5 pairs with both non-zero: ratio 1.01.
    Raw: raw data (not published)
  - Spike screen on VPS1 (8 reps, 2026-10-28): variant "no target caps" 5/8 zero (results.json: new median 0.0);
    base-2 had one rep at 0.14. Path: .../flow/b3r/sp187/sp-*-download_10x10/results.json (summary only, no raw).
  - VPS2 (KVM, same suites, B1 + B2, 32 reps each side): 0 zero reps (base 757-774, new 763-769 MiB/s).
- Plain ws `download 10x10` in the same runs never shows a zero rep, so the stall needs the kTLS path.

## What is not known
- Server logs of the zero reps were not kept (wst regress discards them); no strace / ss sample of a stalled rep.
- Whether the stall is a whole 4 s run or a start that never happens (wbench has no per-second timeline in regress mode).
- Whether it also happens without host pressure (all VPS1 runs of this case were in pressure).

# Root cause and fix (flow, 2026-10-29, branch ktls-starve)

Status: fixed on branch `ktls-starve` (A + B + A2 + D). The lead merges. Kernel report draft (not sent):
raw data (not published).

## Mechanism (kernel 6.8.0-147 on VPS1; same code in v6.12, v6.17, v7.0)
- Path: `tls_sw_sendmsg_locked` -> `tls_alloc_encrypted_msg` -> `sk_msg_alloc` -> `sk_wmem_schedule` ->
  `__sk_mem_raise_allocated(kind = SEND)`. Over `tcp_mem[2]` it goes to `suppress_allocation`: it moderates `sk_sndbuf`,
  then forces the charge only if `sk_wmem_queued + size >= sk_sndbuf`.
- With `sk_sndbuf` moderated to SOCK_MIN_SNDBUF (4608), an empty write queue and a small request, the charge is refused
  every time. `sk_stream_wait_memory` returns EAGAIN. Nothing is in flight, so no ACK and no EPOLLOUT ever come: the
  non-blocking sender stalls for the whole run. Plain TCP does not: `tcp_wmem_schedule` forces up to `tcp_wmem[0]`.
- bpftrace (fexit, 120 iterations, stuck runs): every client socket tries ~10 times/s; `tls_sw_sendmsg(size = 2..32 B)`
  = -EAGAIN, `sk_msg_alloc` = -ENOMEM, raise(SEND) = 0 with sndbuf < 500 KB, wmem_queued < 10 KB, SOCK_SNDBUF_LOCK clear.
  The small request is the rest of a WebSocket frame after a short write: flush sent only that rest (20.19 lane rule).
- Two related cases (review, kernel-checked): a socket whose SO_SNDBUF we set (`net::cap_bufs`/`uncap_bufs`) has
  SOCK_SNDBUF_LOCK and is never moderated, so the forced charge never applies at any size; and `sk_msg_alloc` charges per
  page-frag chunk, so a large request can still become a small charge.
- Where the host memory sits: in the zero runs ~350 MiB, in target connections (243 MiB wbench target send queues, 107 MiB
  server target receive queues). The server's kTLS sockets are empty.
- Why VPS1 only: VPS2 has the same tcp_mem (44769 59692 89538) and RAM. Open; candidates are KVM vs other hypervisor, CPU
  speed, or chance. No box time spent on it (lead).

## Fix (worker.rs, metrics.rs; plain ws path unchanged: everything is gated on kTLS + a blocked flush)
- A (e18e9e1 .. 5528565): a kTLS send that stops with SIOCOUTQ == 0 starts an episode (`starve_step`). Timer retries
  2 ms doubling to 100 ms (`starve_delay`, like the kernel's vm_wait). Rate-limited log via a bounded channel. An
  episode counts only if the first retry is still starved (kTLS's own tx_list gave 19 false hits per run otherwise).
- A2 (67957b5): on each timer retry flush first sends everything queued as ONE sendmsg, in exactly the normal flush order
  (rest of a partly sent lane frame, obuf up to the splice mark, the lane if no mark: `send_gather`). The request then
  reaches the forced-charge size. Order test with partial writes everywhere: `starve_retry_keeps_flush_order`.
- B (fallback): the blocked streams may read one STARVE_SLICE (16 KiB) each per retry past their cap, bounded by
  STARVE_CAP (256 KiB) over out_high per connection, counted in heap bytes and memory levels. Since A2 (c1df485): from
  retry 2 only if the gathered request is < 4608 B, else from retry 3 (two gathers failed: the locked-sndbuf and
  page-frag cases). Reading frees host TCP pages (the targets' receive queues).
- Tried and reverted: room measured from the bulk lane's cap (`out_high_bulk`, 08d7438). It brought the stalls back
  (3/100 vs 0/100): B only helps if it frees more than the host is over tcp_mem[2], and other processes set that
  overshoot. Known limit of B; A2 is what makes the fix not depend on it.
- D (4c657b2): the harness records `tcp_mem_peak` per rep and marks reps that reached tcp_mem[2] ("at tcp_mem max ...
  results not valid").
- Counters: `ktls_starve` (episodes past the first retry), `ktls_starve_end`, `ktls_starve_slices` (episodes given B
  room, once per episode), `ktls_starve_read` (bytes read past the cap), `ktls_starve_ms_max`, `ktls_starve_conn_max`.

## Test gap / known limits
- KeyUpdate pending (ku != 0): no gather on that retry (5-byte record; rare). CHANGED 60.15 T40 (2026-10-30, branch
  base4-fix): over tcp_mem[2] the kernel refuses the 5-byte KeyUpdate record whatever is queued (empty queue: the charge is
  not forced; non-empty: sk_stream_memory_free fails, net/tls/tls_sw.c:832 before the alloc at :844), so a pending
  KeyUpdate stalled the connection for good (VM, kernel 7.0, --tls-rekey-records 64: master 6/6 download reps at 0 MiB/s).
  Now our own KeyUpdates (ku 1 proactive, ku 2 asking the peer) wait behind the data under the old key and the starve
  retry gathers as usual. **Known limit:** the reply owed to the peer's update_requested (ku 3) keeps the RFC 8446 4.6.3
  order (before our next application data), so it still holds the data while refused, and it goes out only when the
  host's pressure eases (B cannot help: it adds room to read, and nothing more is queued for a forced charge). Rare: a
  client must send update_requested while the host is over tcp_mem[2]. Details: 60.17 T40.
- B's success depends on the host overshoot, which other processes set.
- No unit test can show the kernel side; the order test uses AF_UNIX. The kTLS proof is the VPS1 batches.
