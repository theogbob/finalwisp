# Scale tests on rented boxes: glibc vs musl vs Scudo at 8..256 threads, 100k idle connections (2026-10-29)

The scale work. Branch scale-tests (from master 1a311ea). Plan: 60.12; open
questions from 70.21 (musl) and 70.22 (Scudo). raw data (not published) (raw.jsonl per item, summaries,
load.jsonl = host loadavg + cgroup CPU/memory every 5 s), tables: phase1-table.csv, phase1-full-<box>.csv.

## TLDR
- **musl (mallocng) does not scale**: connchurn throughput 0.60-0.80x of glibc at 32-256 threads, server CPU per new connection
  2.0-2.8x (gold 36/72 threads) and 2.5-15x (epyc 32-256 threads). Already 1.1-1.3x at 8 threads. Everything else ties.
  This closes the 70.21 question for good: the futex/`__malloc_lock` signal was the real thing.
- **Scudo (70.22 build, 93408300)**: CPU per new connection +0.6..+3.5% on every box and thread count (LOSS, p < 0.05, all inside the
  5% margin); connchurn rate tie at >= 12 threads, small LOSS at 8 threads (0.97-0.99, 3 boxes). echo 100x10 LOSS reproduced on two
  boxes: gold t8 0.969 / 0.970 (CPU/MiB +3%), e5 t24 0.957 / 0.968 (CPU/MiB +4..6%). Download, rr: tie. So Scudo does NOT meet
  "win or tie everywhere" on CPU.
- **Phase 2, major finding: base-3 glibc keeps 25-59 KiB per idle connection at 100k connections** (RSS; vs 4.7 at 2000 in 70.22),
  musl 0.4-0.9, Scudo 0-1.1. Cgroup memory: glibc +26..28 KiB/conn (gold, epyc) and +59..60 (e5) over musl/Scudo = +2.6..6 GB per
  100k idle connections. Root cause (diagnostic, smaps): once the number of mmapped malloc chunks reaches M_MMAP_MAX (65536 default,
  32765 on max_map_count 65530 hosts by 70.03), glibc serves the remaining 16 KiB+ buffers from its arenas, and arena memory freed
  at the idle sweep is not returned. Threshold ~1.6 mmapped chunks per busy connection: ~20k busy connections on 65530 hosts
  (e5 20k: 16 KiB/conn, epyc 20k: 12), ~40k elsewhere (gold 20k: 1.6, 100k: 26-29).
- **gtrim fix candidates (70.23)**: malloc_trim at the idle sweep (V1) brings glibc to 0.8-1.0 KiB/conn at 20k and 100k on e5 and gold,
  CPU tie (connchurn, echo 100x10, 16 reps). But one trim at 100k idle connections stalls its worker 148-267 ms (client-visible max
  174-306 ms vs 66-78 ms baseline). V2 (V1 + M_MMAP_MAX = max_map_count/2 uncapped) avoids the stall where max_map_count is large
  (gold: trim_max 7 ms, max latency at the baseline) and equals V1 on 65530 hosts.
- **Phase 3 showdown (gold, n = 1 per cell)**: finalwisp first in every case: 1.4-1.7x the best other server on rr and 100x10
  cases, 3.3-3.7x on download 10x10, 5.1-5.2x on churn; idle 20k 4.8 KiB/conn vs epoxy 91-99, wisp-js 107.
- Peak memory goes the other way: VmHWM at the end of the 100k setup glibc 5.0-7.5 GB vs musl/Scudo 7.2-10.5 GB (2x on gold/epyc).
- Two suite bugs and two probe bugs found and fixed (below). Phase 0 A/A: tie on every box where wbench was not broken.

Human version: on big machines musl's allocator is a bottleneck for new connections (up to 15x the CPU per connection at 256
threads). Scudo is almost as fast as glibc but measurably slower (1-4%) in connection churn and in heavy echo. The surprise is
memory: with 100,000 idle connections the current glibc build keeps 25-60 KiB per connection that it should have given back,
because past a fixed number of memory mappings glibc puts buffers in its arenas and never returns them. musl and Scudo give
almost everything back. That is a real problem for the "lots of idle users" case and is fixable on the glibc side.

  download/echo/rr item). Client --threads = physical cores; server --threads as stated (always explicit).
- `wst ab` 3-way rotated interleaved, 16 reps, 4 s + 1 s warmup, paired exact Wilcoxon + 90% HL CI (stats.compare), verdict rule of

## Bugs found and fixed on the way (commits on scale-tests)
1. **wbench measurement window (8036c54, 64251fc)**: download/echo/rr counted while a phase flag was set; the main task flipped it on
   tokio timer wakeups, which came up to seconds late on busy boxes: windows of 3.4-6.5 s, and 6/32 e5 records with duration 0 (the
   start wakeup came after the end). Now counting is decided by Instant::now() in [start, end), elapsed = requested; JSON timer_late_ms
   (74 ms late even in a laptop smoke). connchurn was always clock-based. Review (all): reviewer A + reviewer C OK, P3s applied (--duration > 0
   check, cgroup sample order, burstidle excluded, loadavg floats).
2. **wst ab restart race (4500c77)**: the next server started while the SIGKILLed one's sockets were still closing (pid reaped, 36
   listeners + CLOSE_WAITs for > 0.3 s): EADDRINUSE on every other rep of echo 100x10 at >= 36 threads. Fix: wait_free(port) after stop.
3. **bigidle probe (5618e1d)**: client bind((src, 0)) reserves the port for every address and starved the server's own upstream
   connect()s (stall at ~14k); now IP_BIND_ADDRESS_NO_PORT, 10k per client process, conntrack drain wait, SIGTERM cleanup, smaps summary.
4. `wst ab` records per-rep cgroup CPU% and host loadavg (5ab9d05); `wst showdown --case TEST:CONNS:STREAMS[:SIZE]` (repeatable).
Not fixed (noted): wbench joins each connection task with a 5 s timeout; on a starved client a late task is counted as an error.
