## Summary
- One accounting point per client read, in `read_client` right after `read()`: `rx_total += n` (C5) and, only when an
  upload limit is on, an out-of-line meter call (C10b). UDP upload datagrams travel inside the client's WebSocket
  stream, so this point also counts and limits them. Per-stream UDP counters (C4) cannot use it (the stream id is known
  only after parsing): they stay separate and behind C4's `--log-streams`.
- Kernel counters measure something else (reviewer B): `TCP_INFO` `bytes_received` counts TCP-delivered bytes, including
  input not read yet and TLS record bytes under kTLS, and only for live TCP sockets (no AF_UNIX, C7; a closed
  connection needs the syscall at close). C5 wants bytes the server read (cleartext), so the per-read add stays.
  `TCP_INFO` at close is the right source for C4's per-connection TCP-level `rx`/`tx` (60.02 C4, unchanged).
- C10b = stop reading the client while its allowance is spent (TCP flow control holds the sender; the nginx stream
  `proxy_upload_rate` and HAProxy `bwlim-in` model). Per-IP: each connection leases its share (50 ms of the key's rate
  / the key's connections) from the C3b `IpTable`; idle leases go back at the sweep.
- OFF cost (disassembly, prototype vs base-5): `read_client` +1 `add` (rx_total) +3 byte tests with not-taken
  branches +1 `cmp`; every per-byte function offset-only. Client stays 504 B (slot 512): the pause flag uses the last
  padding byte.
- Design review (reviewer B, reviewer A) kept the single read point; its lease, stall and timing
  findings are fixed in P4 / P5 or written into this doc (section Design review).
- A/B on VPS1 + VPS2 (section A/B results): flags off, one borderline pooled LOSS (VPS1 churn 10x10, 0.969, p 0.05)
  that a layout-control run did not reproduce (the add alone vs no add: 0.997 [0.972-1.021], 128 new pairs, all tie);
  steps 2-3: no LOSS. Q6: rx_bytes always on. ON cost: per-connection limit unmeasurable, per-IP 3-5% (VPS1,
  prototype); merged build on VPS2: per-IP -13% on upload 10x10, cpu +19%, a read split at the lease edge, fixed by
  the lease top-up (back to about 1.00; "Merged A/B" at the end).

Kernel facts used:
- `TCP_INFO` `tcpi_bytes_received` (u64 at offset 128, Linux 4.1+, RFC 4898 tcpEStatsAppHCThruOctetsReceived): bytes
  the peer delivered in order, including bytes still queued unread; for kTLS the TLS records (ciphertext). Already read
  by `net::bytes_received` (70.08). `SO_MEMINFO` is socket memory, not a byte count; `/proc/net/tcp` has no byte
  counts; `sock_diag` (`INET_DIAG_INFO`) dumps `tcp_info` of every socket from another thread (what `ss` does).
- kTLS RX: a `read()` smaller than the decrypted record returns part of it and keeps the rest for the next read
  (`tls_sw_recvmsg`, rx_list; the 2026 receive-path fixes keep that contract). finalwisp already does this when the free
  `rbuf` space is below a record; the prototype checks it under a limit (below).
- A socket the application reads slowly does not grow its receive buffer: receive autotuning follows the read rate
  (`tcp_rcv_space_adjust`). Measured: a client limited to 64 KiB/s kept `rb131072` (tcp_rmem default) and a Recv-Q of
  at most ~80 KB for 8 s (`ss -tmi`).
- `SO_MAX_PACING_RATE` paces what we send (download, C10a, research); it cannot limit upload.

## Approaches compared
| | A: one read-path point (chosen) | B: kernel counters | C: separate hooks per feature | D: credit-based upload cap |
|---|---|---|---|---|
| C5 rx_bytes | `rx_total += n` after `read()` (1 instruction) | `TCP_INFO` at every close + per live client per sample (or a `sock_diag` dump per scrape) | same add, own site | n/a |
| C10b | out-of-line meter: clamp the read to the allowance, debit after; pause flag + timer | impossible (a limit must act before the read) | own pause test + own debit | withhold CONTINUE |
| C4 UDP per stream | separate (stream id needed), gated by `--log-streams` | n/a (UDP has no TCP_INFO) | same | n/a |
| paths touched | per read (1 add + 3 tests + 1 cmp), per loop turn (1 `len` test), accept / close (1 test each) | close (1 syscall), sweep or scrape (1 syscall per client) | per read (more tests) | per CONTINUE |
| OFF cost | 1 add + 3 not-taken branches per read | none per read; a syscall per close if always on (connchurn) | as A or more | none |
| ON cost | 2 calls + 1 vDSO clock read per read; per-IP: one shard lock per lease (a share, 4-256 KiB) | 1 syscall per live client per sample (100k clients: 100k getsockopt per sample) | as A | none |
| failure modes | resume granularity 100 ms; a low rate delays control frames (pongs) | stale between samples; AF_UNIX unsupported; kTLS ciphertext; closed clients' bytes need the close syscall anyway | duplicated rules drift | credit counts packets, not bytes; wsproxy has no credit; a client may ignore credit (only the pend caps catch it) |
| verdict | chosen | for C4 per-connection lines only | rejected: same work, more branches | rejected: not a byte limit |

Per-IP share, three options: (1) a shard lock per read: exact, lock traffic per read; (2) a fixed rate per connection =
IP rate / connections of the key (60.02): no lock, wrong when connections are uneven or idle; (3) **lease** (chosen): a
connection whose own bucket allows a read and whose lease is below MIN_ROOM takes its share from the key's bucket:
50 ms of the key's rate divided by the key's live connections, within MIN_ROOM (4 KiB)..256 KiB and at most the burst
(`IpTable::take_bytes`). The shared bucket never goes below 0.

Outstanding leases (reviewer B, both design reviews). Bytes a key's connections read in any window T are at most
B + R x T + L, where L is the leases already out at the window's start (they were taken from the bucket earlier). Bound
on L with N live connections: each lease is at most max(4 KiB, min(256 KiB, R x 50 ms / n)) with n the connection count
when it was taken, so L <= min(N x 256 KiB, R x 50 ms x H(N)) + N x 4 KiB (H(N) = 1 + 1/2 + ... + 1/N <= 1 + ln N; the
harmonic term covers connections that joined one by one). Example R = 1M, N = 100: L <= 0.27 MB + 0.4 MB. (Merged A/B top-up, below: while no
connection of the key waits and the bucket pays it all, a lease may also be topped up to one read's room, at most
TOPUP_MAX = 512 KiB. The top-up comes out of the bucket like a lease, so the B + R x T + L form holds; the share and
harmonic estimate does not cover topped-up leases, so the coarse bound doubles: L <= N x 512 KiB, review.) Leases go
back at close (one site) and, after LEASE_IDLE_MS (1 s) without a successful read, at the idle sweep: in practice
1-3 s after the last read (2 s sweep). Under contention the starved-first queue (below) grants exactly MIN_ROOM, so L
is then at most N x 4 KiB. Tighter (L = 0) would need the table to know consumed bytes, a lock per read: option (1).

## Chosen design
### Flags (names to align with C10a, open question 1)
- `--upload-rate R[/B]`: per connection, bytes per second (K/M/G), burst B (default R, at least 16K). R 8K..1T.
- `--upload-rate-per-ip R[/B]`: shared by one client key (C3b keys: IPv4 /32, IPv6 /64; behind a proxy it needs C2
  `--trusted-proxy`, like every per-IP limit). It creates the `IpTable` like the other per-IP flags.
- R >= 8K so a client limited only by its own bucket never trips the 70.08 stall rule (4096 B per 2 s sweep =
  2 KiB/s); B >= 16K so an HTTP upgrade and the first frames pass at once; B >= R/10 (P5, reviewer B): paused clients
  resume on the 100 ms tick and the bucket holds at most B, so a smaller B caps the rate at 10 x B per second
  (1M/16K would give ~160 KiB/s). Rejected at startup with the reason (open question 4).
- Startup capability line: `per-ip: ... upload R B/s burst B` (prototype) and a `limits:` part for `--upload-rate`.

### Semantics
- Counted and limited: every byte `read_client` reads from the client socket after the TLS handshake (HTTP upgrade,
  WebSocket framing, Wisp headers, TCP and UDP payloads, pongs). Not counted: TLS handshake records (`tls_read_records`
  reads them; `tx_bytes` does not count our handshake sends either) and kTLS control records (`tls_control`).
- Over the allowance: the client is not read (`Client::lpaused`); its TCP receive window closes and the sender waits.
  Other clients are not affected. All streams of the limited connection wait together (one TCP stream: head-of-line,
  as on a slow client link); a small request behind a bulk upload on the same connection waits for the bytes ahead.
- A limited client that sent FIN (EPOLLRDHUP) is not closed at the pause (no `rdhup` close in the `lpaused` return,
  unlike `mpaused` / frame_held): the limiter adds no new input drop. It does not promise delivery (reviewer B): when the
  read reaches EOF, `close_client` drops the streams and `close_target` does not drain `pend`, as without a limit; and
  at shutdown STOP_DRAIN treats a connection without streams as idle. Time to EOF: about the queued bytes / R; the
  queue is the kernel receive buffer, which autotuning keeps near tcp_rmem[1] for a slow reader (measured above), an
  observation, not an enforced bound.
- EPOLLET (P3, unchanged): a pause keeps `c.readable` (the edge is not lost); resume clears only `lpaused` and pushes a
  generation-checked token (`resume` reads only while `readable`); the short-read test keeps `&& !c.rdhup`
  (input.rs:143) so a peer that hung up is read to EOF; bytes already read are processed (`process_input`, 20.33 staged
  iovecs flushed) before `read_client` returns, and `room` runs only between reads.
- Download is not limited here (C10a, `SO_MAX_PACING_RATE`).

### Hook sites (by function)
- `Worker::read_client` (input.rs):
  0. `meter::room` returns 0 only after it paused the client (`debug_assert!(space > 0)`: the make-room block keeps
     `space >= RBUF_MIN`; a 0 without a pause would leave a readable client that nothing resumes, reviewer A).
  1. loop entry: `lpaused` joins the first early-return test (`dead || closing || paused || opaused || lpaused ||
     !readable`), without the rdhup close.
  2. before `read()`: `let ask = if self.meter { match meter::room(..) { 0 => return, r => r } } else { space };`
     `meter::room` is `#[cold] #[inline(never)]`, a free function over disjoint Worker fields (`read_client` holds `c`).
  3. `read(fd, .., ask)`; `rfull = n == space` (grow only after a full buffer, as before), `drained = n < ask`.
  4. after `c.rlen += n`: `self.rx_total += n` (always, Q6) and `if self.meter { meter::debit(..) }` (cold, out of line).
- `Worker::run` (mod.rs): the epoll timeout is TIMER_TICK_MS also while `lwait` is not empty; after `linger_check`,
  `if !self.lwait.is_empty() { self.meter_timers() }`.
- `Worker::meter_timers` (meter.rs): at most once per TIMER_TICK_MS (`lscan`): resume due clients (`lpaused = false`,
  push to `ready`: the socket may hold data and EPOLLET sends no new edge); drop entries of clients that closed.
  deliberate: a list scanned per tick, as `Worker::connecting` (a heap if thousands of clients per worker pause at once).
- `Worker::adopt` (conn.rs): after the epoll registration succeeds, `if self.meter { self.meter_adopt(i) }` (full
  bucket, no lease). The two adopt failure exits never created a Meter: nothing to release there.
- `Worker::close_client` (conn.rs): `if self.meter { self.meter_close(ci, key) }` between taking the peer key and
  `unload(key)`: the unread lease goes back to the key's bucket. One release site (every close reaches close_client).
- `Worker::count_stalls` (sweep.rs): a client the limiter paused at any time during the sweep interval
  (`Meter::blocked`, set by `room` when it pauses, cleared by `meter_sweep` after each sweep; not `lpaused` at sweep
  time, which the timers may have cleared just before, reviewer B) is not a stall: `rstall = 0` and its baseline
  (`rx_mark`) restarts at the current `bytes_received` (P5). peer_gone (TCP ACK age) and level 3 / frame_held shedding
  are unchanged, so memory stays bounded: a per-IP-starved client holding a frame above `rbuf_max` is still shed by
  the holder rule at level 2+ (frame_held), and level 3 sheds by backlog. (P4 had removed the exemption to stop a
  swarm of per-IP-paused clients holding partial frames, reviewer A; reviewer B's point that the stall rule would then shed
  clients we starved wins: the rule is for clients that stop sending, and the holder rule covers the memory.)
- Handshake deadline (sweep.rs:123-127): a client in Http / WaitInfo for HS_SWEEPS (5 sweeps, 8-10 s) is closed,
  limited or not. B >= 16K lets the upgrade through at once on the own bucket; a per-IP key whose bucket stays empty
  that long loses its new connection's handshake. Kept on purpose: exempting limiter waits would let a key that
  drains its own bucket hold handshake slots forever (slowloris). The starved-first queue serves a new connection in
  a bounded time (below), well inside the deadline unless the key has more than ~(R x 8 s / 4 KiB) waiters.
- `Worker::idle_sweep` (sweep.rs): `self.sweep()`, then `if self.meter { self.meter_sweep() }` (clear `blocked`,
  reclaim idle leases), then `stats.rx_bytes.set(self.rx_total)`.
- `Worker::close_client` publishes `rx_bytes` before `unload`, whose `Inbox.load` decrement is now Release (main's
  `live()` reads Acquire): when main sees 0 connections at shutdown, the last close's bytes are in Stats (P5, reviewer B).
  An empty worker may sleep with no sweep; this covers it. Immediate exit (second signal) stays best effort.
- Per-IP starved-first queue (spec, not in the prototype; Q7, reviewer B: no-starvation is required for a shared cap):
  `Entry` gains `head: u32, tail: u32, head_at: u32` (12 B). A connection whose take got less than MIN_ROOM takes a
  ticket (`tail += 1`, kept in its Meter). While `head != tail`, tokens go only to the ticket holder `t == head` (or
  `t > head` once `now - head_at > (t - head) x 200 ms`, which skips tickets of connections that closed or did not
  come back: no cancel list), exactly MIN_ROOM per grant; a grant advances `head` and `head_at`. Service bound: a
  waiter is served within (t - head) x max(MIN_ROOM / R, 200 ms) plus one tick. Non-holders get 0 while the queue is
  not empty, so one busy connection cannot take every refill. All of it is under the shard lock already taken.
- `IpTable` (clientip.rs): `Entry.ub: f64` (bytes left), refilled in `refill` from the same `at` and STALE_MS rule as the
  stream tokens; `idle()` also needs a full byte bucket (a reconnect cannot reset a drained key); `take_bytes(k, need,
  now) -> u64` (the share, at least `need`; never below 0; untracked key: `need`, fail open Q11); `give_bytes(k, n, now)` (clamped to the burst).

### Data structures
- `Client::lpaused: bool` in the last padding byte (release `Client` 504 B before and after, slab slot 512; a wider
  field makes the slot 520, 60.22).
- `Worker`: `rx_total: u64`, `meter: bool`, `meters: Vec<Meter>` by client slot (empty when `meter` is false),
  `lwait: Vec<(u32 idx, u32 gen, u64 due_ms)>`, `lscan: u64`. `Meter` 40 B (P5, fields below). `meter` is true only when an upload limit is set: metrics alone
  never allocate `meters` or read the clock (Q2). Clock: `now_ms64()`, monotonic u64 ms (no wrap); the IpTable keeps
  its u32 ms clock and the 60.22 STALE_MS rule, its upload paths read `now_ms()` under the shard lock (P5).
- `Config::upload_rate: Option<(u64, u64)>`. Stats appended last: `rx_bytes` (prototype); the spec adds `upl_pauses`
  (pause episodes) and `upl_ip_waits` (pauses because the key's bucket was empty).
- Refill: `own = min(B x 1000, own + dt_ms x R)` (milli-bytes, saturating); room = min(space, own / 1000, lease); a
  paused client is woken only when room >= MIN_ROOM (4096) or the whole free rbuf if smaller: wait = (MIN_ROOM x 1000 -
  own) / R ms (at most 0.5 s at 8K), or the next tick when the key's bucket gave nothing. Wake-ups happen on the
  100 ms tick, so the effective wait is rounded up to it (P4 removed the unreachable 20 ms IP retry, reviewer A).
- `Meter` (P5) = `{ own, at (last refill = last read attempt), rd (last successful read: `debit` copies `at`, no clock
  read), lease, blocked }`, 40 B per slot.

### C4 UDP counters (separate, gated)
- Upload in `on_message`'s UDP branch (before `udp_send`); download in `read_udp` once per `recvmmsg` batch (n datagrams,
  bytes summed in the existing per-datagram loop). Both behind one Worker bool `log_streams` (C4 `--log-streams`), into
  a side vector by target slot (Target sits at its 240 B guard, test `target_size`: no field). Upload counters mean
  datagrams received from the client; drops are a separate count, only when logging, at every drop site (reviewer B): both
  `udp_send_one` callers (udp.rs:29, :62; today `Ok` for a dropped datagram, 60.20 [rt]), oversize, the resolve-queue
  cap and level 3 (udp.rs:49-60).
- OFF cost: 1 not-taken branch per upload datagram and per download batch. Ship C4 for TCP first (60.20); UDP counters
  with this wave, measured by the udp-rr cell.

  `process_input`, `Client::flush`, `send_bulk`. Per accept / close: `adopt` and `close_client` one test + call each;
  the C3b table functions changed with `Entry` (per-IP paths only).
- Expectation for the implementation: the same classes (`read_client`: 1 add + 3 tests + 1 cmp on the OFF path; `run`:
  one more `len` test per turn; `adopt` / `close_client`: one test each; per-byte functions offset-only or Config
  immediates). Hoisting `self.meter` into a local before the loop may save one reload.
- P4 (design review fixes) did not touch input.rs: the `read_client` OFF path is as in P3. It adds one store to
  `close_client` (rx_bytes publish), one test + cold call to `idle_sweep`, and removes one test from `count_stalls`.
  Not re-disassembled; the implementation re-checks all of it against step 1.
- ON: per metered read two calls + one vDSO clock read (a lease also reads the IpTable u32 clock); per lease one shard
  lock. Not measured (laptop rule): A/B plan.

## Safety analysis
- Abuse: many connections from one key bypass `--upload-rate` -> `--upload-rate-per-ip`; IPv6 /64 rotation fills table
  shards -> new keys are untracked (fail open, Q11) and only the per-connection limit applies; `--max-conns` stays the
  backstop. Per-IP limits need C2 behind a proxy (else every client shares the proxy's key): document in 40.01.
- Memory per limited client: Meter 40 B per slot + 16 B per `lwait` entry while paused; the kernel receive buffer stays
  small (slow reader). `meters` grows to the highest slot (like `peers_of`).
- Leases (P5, reviewer B): taken only for the key the connection charged (`peers_of[ci].key`, set once at accept or at the
  upgrade); refunded exactly once (`meter_close` takes the lease with `mem::take`, before `unload` releases the key; the
  idle reclaim also takes it); never a synthetic refund: an untracked key returns `None` from `take_bytes` and nothing
  is added to the lease. Stale `lwait` (idx, gen) entries never touch a reused slot (`clients.get(ci, g)`), and
  `meter_adopt` resets the slot's Meter. Adopt failures never lease. No count can leak (C3b `conns` stays in `unload`).
- Starvation: with a per-connection limit a connection pauses only itself. Within a connection all streams pause
  (head-of-line, documented). Per IP the prototype has only the share by connection count and "no lease while the own
  bucket blocks" (P4): rough, the first reader after a refill wins and workers race on the shard lock. The spec adds
  the starved-first ticket queue (hook sites) for a bounded service time (Q7).
- Credit v2: the limited client still obeys credit. A pong behind queued upload waits until the bytes ahead of it are
  read: up to the receive queue / R (about 16 s at 8K for a 128 KiB queue), past PONG_LATE (5 s). Then
  `Pinger::active` falls back to the base rule (credit.rs:112-114) and the RTT sample is inflated but the window is
  capped at WMAX (credit.rs:299): graceful, no close (reviewer B, reviewer A; the P3 text said "one wait", wrong).
- Trusted proxy (C2): the key is known only after the upgrade (upgrade.rs:147-148). The HTTP parse takes partial input,
  so the bootstrap is every read until the request completes, up to `http::MAX_REQUEST`, plus the rest of the
  completing read (reviewer B). Spec: count these bytes in `Meter` (`boot`) and charge them to the key when it is set
  (one `take_bytes` that may leave the lease negative: the next reads wait for it). Bound before charging: MAX_REQUEST
  plus one rbuf. A trusted proxy that sends no client-address header leaves the client without a key for life: per
  connection limit only (fail open, 60.22 Missing), `realip_missing` counts it (Q6).
- 20.33 batching: a pause happens only between reads, never with staged iovecs (the existing debug assert holds).
- Pause flags: `lpaused` is independent of `mpaused` (20.26), `hpaused` (20.27; HOLD_SWEEPS still counts) and
  `opaused`; resume clears only `lpaused`. Level 3 (`st.read`) and frame_held (level 2+) still apply on top.
- kTLS: a clamped read can end inside a record (kept by the kernel); a KeyUpdate or alert waits for the next read (as
  with any pause). The TLS 1.3 EPOLLOUT probe read goes through `read_client` and waits too.
- Clock: local buckets u64 ms (no wrap). IpTable: u32 ms with the 60.22 STALE_MS rule; P5 reads `now` under the shard
  lock in `take_bytes` / `give_bytes`, so no upload path can bring a reordered `now` (reviewer B). A u64 table clock would
  also remove the 49.7-day wrap for keys untouched that long (sleeping workers), at +4 B per Entry; the sweep refresh
  (60.22) already covers live entries. Pick: keep u32 (Entry size), revisit with the ticket fields. Overflow:
  saturating milli-byte arithmetic; R <= 1T.
- `--balance`: the Meter is created by the adopting worker; the per-IP key travels in `Handoff` (C3b), so the lease goes
  back from the worker that took it.

## Prototype evidence
A research branch (not published); laptop, `nice -n 19`, functional only.
- `cargo test --release`: 151 passed (base-5 149 + `clientip::upload_lease_bounded_and_given_back` + worker
  `upload_rate_pauses_and_resumes`); `cargo clippy --all-targets -D warnings` clean; fmt clean. P5: same 151 tests,
