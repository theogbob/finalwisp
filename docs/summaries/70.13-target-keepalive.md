# 70.13 TCP keepalive on target sockets (2026-10-26)

Pointers: 70.02 (client keepalive, net::KEEP_*), 60.09 (review base 2: "dead-target streams"), soak 30.11. Branch
base2-tka from final-cand 374c6a2.

Problem: a target that vanishes (no FIN/RST) while its stream is idle or only downloading leaves the stream open
forever: nothing is unacked on our side, so TCP never times out. Uploads already end via the retransmission timeout
(~16 min).

Change: open TCP targets get the same keepalive as clients (120 s idle, 4 probes 15 s apart), unless
`--no-keepalive`. It is armed lazily by `Worker::sweep` (every IDLE_SWEEP_MS = 2 s; `Target::keepalive`), not at
connect: connect losers and streams that end before the next sweep pay nothing (cf. LAZY_CAP), the others pay 4
setsockopt once; detection comes at most one sweep later (~182 s instead of ~180 s). A read/write ETIMEDOUT on an open
TCP target closes the stream with CLOSE 0x47 ("TCP data transfer timed out"; `net::data_reason`), other errors keep
0x03. The ICMP-derived errnos (EHOSTUNREACH, ENETUNREACH, ECONNREFUSED,
EACCES (v6 REJECT), EHOSTDOWN, ENONET, ENOPROTOOPT, EOPNOTSUPP, EPROTO, EMSGSIZE) also map to 0x47: the kernel reports
a TCP timeout with the last soft ICMP error if one came (tcp_write_err: sk_err_soft ?: ETIMEDOUT; review 2026-10-26,
Reviewer A, 2 rounds), and without IP_RECVERR an open socket sees them only that way. UDP and creation-phase reasons (0x42/0x43/0x44) are unchanged. Raw wsproxy streams get WS close 1000 as before.

Clients: wisp-js (TransferTimeout), libcurl.js (wisp-js WispWebSocket) and epoxy (ServerStreamTimedOut) close the
stream on any CLOSE reason the same way; the reason is only reported.
