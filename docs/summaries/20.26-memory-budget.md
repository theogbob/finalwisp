# 20.26 Memory budget: slow down instead of being OOM-killed (2026-10-23)

Pointers: 20.01 server/ (code: server/src/mem.rs, worker.rs `set_level`, net.rs `cap_bufs`/`uncap_bufs`),
40.10 tests/compat/membudget.py, data raw data (not published) (the problem), 20.06 (sections
20.21 lowat, 20.22 lanes).

## Problem
Under a cgroup limit (`systemd-run --user --scope -p MemoryMax=64M -p MemorySwapMax=0`) finalwisp was OOM-killed on
download 10x10 even at 64 MiB; epoxy survived 64 MiB. At 1 GiB the peak was 92 MiB = anon 17 + sock 65.
Breakdown measured here (master, 1 thread, `ss -tm` at the sock peak): sock 41 MiB = target sockets' *receive*
queues 35 MiB (100 targets x ~360 KiB: a target parked in `blocked` because its client's obuf is at OUT_HIGH keeps
its autotuned rcvbuf full) + client send queues 2 MiB (--notsent-lowat already bounds the unsent part). anon 16 MiB
= obuf + bulk lane (up to ~2 x (1 MiB + CHUNK) capacity per client) + rbuf.
Timeline at MemoryMax=32M (5 ms samples): 1 -> 32 MiB in **~25 ms** after the load starts (anon 13, sock 10.5).
No sampler can react to that: a budget-derived starting level is needed (below).
Master: OOM-killed at 32M in 4/4 runs, at 64M in 3 of ~8 runs.

## Design
**Budget** (startup, no flag): /proc/self/cgroup -> the v2 path; walk up to /sys/fs/cgroup; budget = the smallest
memory.max or memory.high on the path, usage read from that cgroup. No limit: budget = MemTotal / 2, usage = heap
bytes (counting allocator) + the host's TCP memory (/proc/net/sockstat). `--mem-budget BYTES[K|M|G]` overrides the
budget (usage source unchanged); `--mem-budget 0` = off. Startup line (60.01: part of the capability line, see 20.06), e.g.
`finalwisp: capabilities: 1 threads, memory budget 32 MiB (cgroup limit /sys/fs/cgroup/...scope; usage = cgroup memory.current - inactive_file, small: level 1 from the start), ...`.

**cgroup v1 (80.01, kcompat)**: no v2 limit on our path (pure v1: RHEL 8, Amazon Linux 2; hybrid: Ubuntu 20.04) ->
the v1 memory controller: our path from the "N:memory:/path" line of /proc/self/cgroup, the mount from
/proc/self/mountinfo (fstype cgroup, super option memory; its root field is stripped from our path, so a container
whose own cgroup is mounted as the hierarchy root works). Budget = the smallest memory.limit_in_bytes from our
directory up to the mount point, or our memory.stat hierarchical_memory_limit if smaller (sees limits above the mount,
e.g. a pod's); values >= 2^62 are "unlimited". Usage = memory.usage_in_bytes - total_inactive_file of the directory
with the limit (for a limit above the mount: our own directory, so siblings under that limit are not seen); same
sampler cadence and keep-last-good contract as v2. With use_hierarchy=0 (only before 5.11, rare: systemd sets 1) the
walk-up minimum is stricter than the kernel's. Path not under the mount root or with "..":
not ours, host mode. Known difference: v1 does not charge socket buffers to the cgroup (unless kmem.tcp is limited),
so they are neither in the usage nor under the limit. Capability line: "cgroup v1 limit DIR; usage = cgroup v1
memory.usage_in_bytes - total_inactive_file" and "cgroup: v1|v2|hybrid". Tested with fake trees
(mem.rs cgroup_budget_v1_hybrid_v2_layouts, v1_sampler_files); a real v1 host waits for the VM tier (REPORT-kernel.md).

**Sampler** (thread `mem`): pread on kept-open fds. memory.current every 20 ms below 25% of the budget, 5 ms up to
40%, 2 ms above or under pressure. Above the first threshold it subtracts inactive_file (memory.stat, read at most
every 100 ms) so a warm page cache does not count. Publishes `mem::LEVEL` (AtomicU8) with hysteresis and writes
every worker's inbox eventfd on a change. Workers load LEVEL once per loop turn (after the inbox drain) and call
`set_level` only on a change: **no per-I/O syscalls, no per-I/O atomics**.

**Stages** (`mem::STAGES`, one const table; per mille of the budget; initial guesses for tuning):
| | enter / exit | out_high / low / hard | rbuf max | CONTINUE grant | socket cap | admission | other |
|---|---|---|---|---|---|---|---|
| L0 | - | 1M / 256K / 8M | 256K | --buffer | autotune | yes | = master |
| L1 | 500 / 400 | 256K / 64K / 1M | 64K | 32 | 32K | yes, stream limit | drained buffers > 256K freed at once |
| L2 | 700 / 600 | 64K / 16K / 256K | 16K | 8 | 32K (was 16K, 60.12) | no: CONNECT -> CLOSE 0x49, accept() paused | over-credit pend cap 1 MiB |
| L3 | 850 / 750 | as L2 | 16K | 8 | 32K (was 16K) | no | clients not read; shed streams with pend + outq > 1 MiB (RST, CLOSE 0x49) |

- **Small budgets start at L1** (`SMALL_BUDGET` = 256 MiB): the 25 ms rise above. At L1 from the start download
  10x10 stays at ~17-23 MiB and survives 16 MiB. Above 256 MiB growth is bounded by real link rates and the sampler.
- **Socket caps** (`net::cap_bufs`): SO_RCVBUF + SO_SNDBUF on every client and TCP target socket, live ones in one
  walk at the transition, new ones at accept / connect. The kernel doubles the value and stops autotuning; queued
  data stays, new data is limited at once. Client SO_SNDBUF is at least 64 KiB (the loopback MSS): below 2 segments
  one segment is in flight at a time and the receiver's delayed ACK paces it (download 10x10 at a 32K cap: 18 MiB/s;
  with the client send side at 64K: 3.1 GiB/s). TCP_MAXSEG cannot tell (fresh loopback sockets report 32 KiB).
  Target caps are not raised: loopback probe (python, one socket, both sides capped): 16K 4 MiB/s, 32K 820 MiB/s,
  64K 6.5 GiB/s; a 1448-byte MSS is not affected. TCP_WINDOW_CLAMP was tested and rejected (64K/128K left the
  queue at ~2 MiB on loopback).
  **60.12 #2b (2026-10-27): L2/L3 cap 16K -> 32K.** The 16K cap (32 KiB in the kernel) was the 4 MiB/s case of
  the probe above, kept for L2/L3 on the "a 1448-byte MSS is not affected" argument. On kernel 7.0.0-38 (laptop)
  it stalled loopback streams: echo 10x10 at 16M collapsed to 0-10 MiB/s in 2-4 of 8 runs (base-2 too); ss skmem
  showed receiver drops (TcpExtTCPRcvQDrop), mostly at the target application's socket fed by our 16K-capped
  target socket, so the sender retransmitted after RTOs. Kernel history (tcp_can_ingest): 1d2fbaad7cd8 "tcp: stronger sk_rcvbuf
  checks" (Dumazet, 2025-07, from 6.17) drops an skb when rmem + skb->truesize > rcvbuf (unless the queue is empty);
  f017c1f768b6 (2025-09) uses skb->len instead of truesize; "tcp: give up on stronger sk_rcvbuf checks (for now)"
  (Kicinski, 2026-02-26, listed in 7.0-rc3) goes back to rmem <= rcvbuf. 7.0.0-38 still dropped here (exact drop
  reason not traced: no root on the laptop). Kernel 6.8 (VPS2): 0 stalls, 0 drops at 16K. With 32K at L2/L3: laptop 0/8 stalled,
  1.3-1.5 GiB/s, drops 3 vs 67, cgroup peak equal (12.8 vs 13.0 MiB). A client receive floor (64K at L2) did
  not help (7/8 stalled on 7.0) and cost +3-4 MiB peak at 16M on 6.8: not taken. L2/L3 admit no new streams, so
  max_streams (4 x cap per stream) only binds at L1 (unchanged). So the per-stream socket bound at
  L2/L3 now equals L1's (review): a stream set admitted at L0 (budget >= SMALL_BUDGET) is no longer halved in kernel
  memory at L2; it relies on the heap levers and the L3 shed/escape. grant_window at L2/L3 follows the cap
  (16K -> 32K: two 16 KiB packets per CONTINUE instead of one). A client whose worker budget is too
  small for client_rcv keeps min(sock_cap, client_rcv) (16K at L2/L3, review).
- **Relief** (`net::uncap_bufs`): the sizes from before the cap (saved with getsockopt) are set again, then
  SO_BUF_LOCK = 0 (Linux 5.15+; not in RHEL 9) so autotuning continues. Clearing the lock alone does not work for the receive side:
  probe 16K cap -> unlock: rcvbuf stays 32 KiB, ~0 MiB/s; restore + unlock: 9 GiB/s and growing. Restored values are
  clamped to rmem_max/wmem_max; kernels < 5.15 keep them locked at that size.
  60.09 D1: this includes a held upload client (20.27 0x49 hold, `Client::hpaused`): capped while held (big backlogs
  usually come with pressure), it gets its saved sizes back at relief but, on kernels < 5.15 (no SO_BUF_LOCK; capability
  line `buflock: no`), stays locked there, so autotuning never grows its receive window again and its upload stays
  bounded by that rcvbuf / RTT for the rest of the connection. No fix without SO_BUF_LOCK; a reconnect gets a fresh socket.
- **lowat / kTLS**: kTLS client sockets get the same SO_SNDBUF cap. TCP_NOTSENT_LOWAT limits the unsent part, the cap
  limits unsent + in flight, so they do not fight: under a cap the cap governs; after a 20.21 lift (lowat i32::MAX)
  the cap alone bounds the queue, which is what pressure wants.
- **Credit**: Target `credit` (last grant) and `allow` (packets the client may still send: new grant + what earlier
  grants left in flight, `next_allow`, computed before `since` is reset; saturating). Unit test
  `credit_allowance_catches_over_credit_after_refills` simulates a client with CONTINUE lag 0-63 packets and
  grant changes: an honest one is never flagged, one that keeps sending past a stalled target is caught. Refill at half of min(credit, grant): a 128-grant shrinks at once, an 8-grant grows back as
  soon as the pressure is gone. At L1+ a new stream gets CONTINUE(grant) right after CONNECT. Both reference clients
  set remaining = n on CONTINUE (wisp-js connection.mjs `continue_received`, epoxy `flow_set`). The handshake
  CONTINUE keeps --buffer. Level 0: half = buffer / 2 as before.
- **Admission**: CLOSE **0x49** (Throttled; wisp-js `ConnThrottled`, epoxy `ServerStreamThrottled`): the stream
  fails, the connection stays. Also the reason finalwisp already uses for DNS overload. wsproxy gets HTTP 503.
  accept() pause keeps the listener; on relief `set_level` calls accept_all (the EPOLLET edge is used up).
  At capped levels a worker also refuses streams beyond `max_streams` = budget/threads x SOCK_SHARE (50%) /
  (4 x sock_cap): a capped stream still costs up to ~4 x cap (measured: 150 KiB per upload stream to a stalled
  sink with a 64K cap), so the budget implies a stream count. 32 MiB at L1: 127 streams.
- **Upload backlog** (`pend`, the only queue not bounded by a per-client size: credit is per packet and a client
  may hold credit on many streams to a stalled target): per-worker `pend_total` and per-client `Client::pend`, kept
  exact with one add each when a target's backlog changes (`Target::acct`, `pend_account`). Over `pend_cap`
  (budget x 25% / threads, at least 1 MiB; ~520 MiB per worker on the 31 GiB laptop) only a client holding at
  least the average share (`pend * clients_with_backlog >= pend_total`) is not read (`mpaused`). It resumes when
  its own backlog is 0, or with all paused clients (`pend_paused` list) once the total is under 3/4 of the cap.
  Over the cap for 2 idle sweeps (or between 3/4 and the cap with clients paused), the largest backlogs are shed
  (RST + CLOSE 0x49) down to 3/4. At every level, as the cap itself. A paused client that hangs up is closed at
  once. (Review B: the first version paused whichever client hit the cap, so one stalled stream froze every
  other client's uploads on the worker. Check 4 of membudget.py: old build Y 0.33 MiB/s, now 1.7-1.9 GiB/s.)
- **Counting allocator** (`mem::Counting`): heap bytes in use, per-thread slots (plain load + store, no locked
  instruction; threads beyond 63 share one atomic slot). Used for host mode and the log lines.
- **L3 escape** (review C): at L3, when `mem::USED` makes no new low for 2 idle sweeps, the clients holding the most
  buffer memory (rbuf + obuf + bulk + frag + pend) are closed, about 1/8 of the worker budget per round (best
  effort WS Close 1013 when their output is empty and they are past the handshake).
- **L3 shed** counts unsent bytes only (SIOCOUTQNSD), so a healthy upload with much data in flight stays.
- **Dwell**: a level steps down only 250 ms after the last change; up at once (16M flapped L1 <-> L2 every ~0.5 s).
- **Host mode** counts host TCP memory above a baseline: the value at startup, lowered whenever it falls, taken
  again while the server has no clients.
- **Workers start at the published level** (the floor is set by main before the workers exist).
- **wsproxy** pause/resume: resume below min(PEND_LOW, out_low), so L2/L3 do not flap.
- **Log**: level changes, at most one line per 5 s, except changes to/from L3 and back to the base level.

## Known limits (accepted for now)
- UDP streams' resolving queue (256 KiB each) is not in pend_total.
- TLS handshake records are still read at L3 (accept is paused from L2, so only handshakes already in flight).
- fds handed over by --balance are adopted at L2.
- A hostile *download* client is bounded (out_high, capped sockets, stream limit) and only closed by the L3 escape.
- Relief of a long-lived socket is checked with the python probe, not in membudget.py.
- Idle RSS (20.06 20.11b): the targets Slab grown during a burst pinned the freed buffers in each worker
  arena (110 KiB per idle connection instead of 15); fixed on idlefix (Slab reserves 128 KiB as its own mmap).
  The reserve counts in heap_bytes (host-mode usage): 2 x 128 KiB per worker, never resident.
- pend_cap and its shedding apply at level 0 too (budget share for uploads): 1 GiB host, 4 threads = 64 MiB per
  worker; honest uploads to stalled targets beyond that get paused, then shed.

## Open / for tuning
