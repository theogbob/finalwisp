## The build
- ONE build: x86_64 glibc, statically linked (`-C target-feature=+crt-static`, static-pie), built by bench/release.sh, which
  refuses a build host with glibc < 2.34 and writes BUILDINFO (git, dirty, rustc, glibc, target, date, md5).
- Runs without the host's glibc: no glibc-version floor (the dynamic build needed >= 2.34: no RHEL 8 / Ubuntu 20.04 /
  Debian 11 / AL2). Host lookups use the built-in files + dns modules; /etc/nsswitch.conf is ignored for hosts (a host NSS
  module dlopened into a static process crashed, SIGFPE on ubuntu:24.04). Cost: names only an NSS plug-in knows (LDAP/sss,
  mdns without resolved) do not resolve. systemd-resolved's stub works.
- Not chosen: musl (no throughput advantage; +25-30% CPU per new connection before the cache, ~equal after; needs ~1,100 extra
  lines: own resolver + mapping guard; global malloc lock untested above 8 threads). Parked with its guard (vma-guard).

## Changes since base-1.1
Robustness
- Dead clients: listener keepalive 120 s + 4 x 15 s; TCP_INFO dead-peer check (no ACK for 150 s with >= 2 unanswered
  retransmits/probes on two consecutive sweeps) resets a dead peer that has data queued. Not TCP_USER_TIMEOUT (it aborts live
  zero-window readers on 5.11+). Idle dead peers closed at ~182 s, queued downloads at ~152 s (plain and kTLS). --no-keepalive.
- Dead targets: TCP keepalive on target sockets (armed at the first idle sweep; same timing); a vanished site ends the stream
  with CLOSE 0x47 (wisp-js / epoxy close only that stream). Was: idle/download streams to a dead site stayed open forever.
- Honest uploads on long paths: an in-credit stream whose backlog passes PEND_HARD (64 MiB) now holds its client (not read)
  instead of CLOSE 0x49; resumes at 48 MiB; 0x49 only after 3 idle sweeps. Real netem 200 ms: 13/40 -> 0/40 uploads killed.
- Memory pressure: HOLD_FLOOR (a whole frame <= 64 KiB is never held at L2/L3: honest 64 KiB uploaders were shed);
  a client with a partial frame above rbuf_max that moves < 4 KiB per sweep (tcpi_bytes_received, kTLS included) for 2 sweeps is
  shed at L2 (drip attack); sampler log through a bounded queue, failed reads keep the last good value.
- SSRF filter: 6to4 (2002::/16) and ::/96 classified by the embedded IPv4; Teredo treated as private.
- Fuzz fixes (TLS double alert, non-UTF-8 argv), cleanup.
Memory
- glibc M_MMAP_THRESHOLD 16 KiB + M_MMAP_MAX = min(65536, max_map_count/2) (without the cap the process aborted at the kernel's
  mapping limit), plus a per-worker block cache (16-132 KiB blocks, 256 slots, <= min(16 MiB, worker budget/16); 1 MiB at level 2+;
  only blocks unused since the last sweep are freed; worker sweeps desynchronised). At level 1 a drained output/bulk lane is
  freed only from 2 MiB up (70.14; it was freed at > 512 KiB on every drain: a download lane of 512 KiB + 24 bytes was
  mapped/unmapped per cycle, -5..-9% potato download on VPS1); level 2+ frees as before. Idle: ~120-170 -> 4.7 KiB/conn userspace
  (+~8 KiB kernel per idle socket, every build). THP=always: same per-connection cost (deb12: +2-4 MiB once at startup).
Old kernels / containers
- cgroup v1 memory limits (Ubuntu 20.04, RHEL 8, AL2 defaults; hybrid too); a limit inherited from a hidden ancestor (pod) is
  flagged with a warning: set --mem-budget to a safe share.
- Capability line: kernel, cgroup version, SO_BUF_LOCK (no = kernel < 5.15: sockets capped under pressure stay capped).
- Clear kTLS startup errors (no tls module / kernel without CONFIG_TLS / TLS RX needs 4.17+): use a TLS proxy and ws://.

## Known limits
- Kernel < 6.14: a client KeyUpdate closes the connection (no kTLS rekey). Debian 11 kernel: no kTLS at all (no wss).
  Since 60.12 (branch ops, decision 2026-10-27 option A, no --tls-userspace): each such close is counted
  (tls::KEYUPDATE_CLOSES) and logged as one line at most every 60 s (reason, kernel release, count, hint: TLS at a
  reverse proxy + ws://, or Linux 6.14+). Who sends one (kucheck, source-verified, raw data (not published)):
  browsers never in practice (Chrome/BoringSSL never; Firefox/NSS after ~1.8e10 records; Node/OpenSSL/Go/mbedTLS never);
  native rustls clients (native wisp-mux/epoxy, our wbench) send update_requested after 2^24 = 16,777,216 records under
  one AES-GCM key, never under ChaCha20. So on < 6.14 such a connection closes after 16.8M records: use Linux 6.14+,
  TLS at a reverse proxy, or ChaCha20 (kTLS ChaCha20 needs Linux 5.11+; focal 5.4 / rocky8 4.18 offer AES-GCM only).
  Deployment doc: 40.01.
- Kernel < 5.15: sockets capped during a pressure episode stay capped (incl. a held upload client's rcvbuf).
- Static build: nsswitch.conf ignored for hosts.
- Under a small budget, pend_sweep can shed a held upload after 2 sweeps (before its 3-sweep hold ends).
- After a long idle gap, one HTTP upgrade handshake (Http/WaitInfo, HS_SWEEPS) can expire at ~6-8 s (desynced sweep
  phase); the TLS handshake has its own 10 s deadline (design review 2026-10-27, reviewer B).
- At level 1 a busy client can keep up to ~1 MiB per lane until idle (level 2 frees it).
- Echo at L2+ still maps/unmaps large obufs; obuf grows to 512 KiB at L2 although out_high is 64 KiB (diagnose).
