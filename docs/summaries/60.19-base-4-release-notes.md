## Breaking changes
- Removed flags (60.18 #1): `--credit-v2`, `--prio`, `--no-tcpmem-adapt` (no-op aliases of the default) and
  `--no-dns-coalesce`. A start command that still passes one **exits 2** with "<flag> was removed in base-4 (60.18):
  <why>; drop it". Delete the flag; behaviour is unchanged (DNS coalescing is now always on), except where an alias
  came after its opposite (last wins): `--tcpmem-adapt --no-tcpmem-adapt` ran with adaptation off, so delete both
  (60.16; 40.03 "Removed").
- Memory usage without a cgroup limit (Host mode) now counts this process's own socket memory (cgroup v2 memory.stat
  `sock`) instead of the whole host's TCP memory, when its cgroup allows it (40.01 "HostSock"). A busy neighbour no
  longer pushes finalwisp into the memory levels when it runs in a cgroup of its own; in a cgroup shared with other
  processes their TCP and UDP sockets count (in 60.17's test as much as the host-wide count). The
  capability line names the source.
- `--help` / usage text is split into main options, opt-in and advanced / diagnostic (40.03).

## Upgrade notes (from base-3)
- Delete any removed flag from the start command (Breaking changes); the server exits 2 and names it otherwise.
- Give finalwisp a cgroup of its own (a systemd unit, a container, or `systemd-run --scope`). With a limit
  (`MemoryMax=`, `--memory`) the limit is the budget and counts only this cgroup. With no limit, base-4 counts this
  cgroup's own sockets (HostSock, 40.01); in a shared cgroup (an ssh session scope) the others' sockets count too. The
  capability line names the source.
- Nothing else to change: same ports, Wisp versions, close reasons and defaults. The binary is static and reproducible
  (bench/release.sh; compare the md5 above). The old allocator build stays available (`NOFEAT=1 bench/release.sh`,
  60.18 #3) if the own allocator's memory shape (Costs) does not suit a host.
- Expect: lower idle memory per connection (2000 idle conns, RC regress: VPS1 / VPS2 4.8 -> 1.2-1.25 KiB/conn, e5 5.55
  -> 4.85, gold 72 threads 5.0 -> 4.6), a short higher peak RSS after big bursts (Costs), and dead clients in a long
  zero-window pause closed at up to ~360 s (was ~240 s).

## What changed since base-3 (tag base-3 at 6de8b4f, code = merge of b3-optin 4097cb1; md5 55d175ae)
Speed
- **Upload batching across interleaved streams** (20.33): DATA frames for several streams in one client read are staged
  per target and written with one writev per target (was: one writev per frame as soon as two streams alternated).
- **Own allocator for the big per-connection buffers is the default build** (70.25 round 5): 16-128 KiB buffers of
  worker threads come from per-worker 4 MiB chunks and go back to the kernel in bounded batches; glibc serves the rest.
  The old path stays buildable (`NOFEAT=1 bench/release.sh`) until base-4 has soaked (60.18 #3).
Correctness and robustness
- **kTLS send stall under host TCP memory pressure fixed** (50.02): a kTLS send that the kernel refuses with nothing in
  flight is retried on a timer as one gathered send (A2), with a bounded extra read as fallback (B).
- **Refused KeyUpdate no longer stalls kTLS sends** (60.17 T40): our own KeyUpdates (proactive, or asking the peer) stay
  pending and are retried while data goes on under the old key; only the reply owed to a peer's update_requested keeps
  the RFC 8446 order.
- **Level-3 self-lock fixed** (60.17 T03 P4): level 3 reads a client while its streams have no upload backlog, so
  receive queues that filled at level 0 drain and the level can fall again.
- **Memory levels** (60.17 mem.rs round): level 2/3 client receive buffer 16 -> 32 KiB (below the loopback MSS the old
  value stalled); level 1 target send buffer 40 KiB (was the 32 KiB cap); flap damping (Dwell: the step down from a
  level that flapped waits up to 4 s); Host mode counts our own cgroup socket memory (HostSock, above).
  SMALL_BUDGET stays 256 MiB (a 128 MiB level-0 start was tried and rejected, 60.17 P2).
- **Dead-peer check needs 3 unanswered probes in a row (was 2)** (60.17 "RC finding", net.rs PEER_GONE_PROBES): a live
  zero-window reader that lost 2 probe exchanges on a CPU-saturated host was reset (RC1 gold soak: 1 of 2,058 pauses in
  the first 12 h; 1 of 4,093 over 24 h, 30.18).
  netem loss on lo (VPS2): 30 % loss RC1 12/20 reset -> 3/20; paired 10 % loss RC1 5/50 -> 0/50; no-loss port 0/20.
  Dead clients are still closed in the 70.13 band (plain idle 182 s / download 152 s, kTLS 180 / 152 s); a client that
  dies late in a long zero-window pause is closed at up to ~360 s (was ~240 s). (The check is on clients only; dead
  targets are unchanged.)
- UDP download bounded per datagram batch (60.17 T02): obuf stays below out_high + one datagram frame (was up to
  ~512 KiB over).
- B3 `--tcpmem-adapt` (opt-in) redesigned (20.31 "B redesign"): the host TCP level alone never caps a same-host socket.
Operations
- Flag cleanup and usage sections (60.16, 60.18); `--balance` stays opt-in (60.15 T21).
- Log truth (60.16): the capability line says "pool off" / "pool on for N of M workers" when the pool cannot run, and
  "memory budget off" with a warning when MemTotal is unreadable; a worker thread never writes stderr directly
  (TLS KeyUpdate log goes through a bounded queue with a drop count).
- New metric `pool_release_cpu_max_us` beside `pool_release_max_us` (thread CPU time of the longest pool release).
Tooling (no server change)
- Bench audit fixes (30.13): client CPU after exit, idle accounting, one paired statistic for verdicts.
- `wst regress`: any benchmark error makes a case invalid; raw idle values saved (60.15 T08/T09). Host tcp_mem-max reps
  marked invalid (50.02 D).
- wbench: clock-based measure window, `--verify` byte integrity at rate (60.15 T06), per-reason error counters
  (`error_kinds`), parse-time checks of --duration / --warmup; clippy-clean, in CI.
- Soak harness on master (30.14), cycle test (30.15), RC soak lanes (30.16): `--tcp-safe` (one bulk lane, a TCP gate,
  0.5 s monitor), smaps observers, cycle.py `--floor-hook` + heapsnap.py (glibc malloc_info per floor) (30.17).
- `wst regress --suite idle` (30.10): n pairs at --reps n (was n/2) and an RSS resolution floor (a WIN / LOSS / watch on
  the idle row needs |paired difference| >= max(0.25 MiB, the measured step), else tie); the current / settled RSS
  columns sum VmRSS (exact) instead of the /proc/PID/stat rss field (approximate per-CPU counter on kernels >= 6.16);
  peak columns are still VmHWM (Known limits).
- Heap profiling for leak hunts: branch archive/leak-dhat (test-only feature dhat-heap, bench/soak/dhatctl.py; not merged,
  release.sh refuses the feature) (30.17).

## Known limits
- **Owed KeyUpdate (ku 3):** if the host is over tcp_mem[2] when a client asks for a KeyUpdate reply, the refused reply
  still holds that connection's data until the pressure eases (rare; RFC 8446 order). 60.17 T40, 50.02.
- **Own allocator costs** (above): ~1 % server CPU on echo-heavy big boxes, connchurn about -0.5 %. Accepted by the maintainer
  at default-on (70.25 round 5).
- **--balance stays opt-in** (60.15 T21): churn/rr +4..11 % on 36-72 thread boxes, but connchurn rps down to 0.925
  (LOSS in 7 of 8 connchurn cells) and echo 100x10 0.974-0.980 with it (n=16, epyc2 and gold).
- **Watch cells before RC1, not losses** (60.17; re-run in the RC1 regress, see "RC results": none reproduced as a loss;
  kept here for the record):
  - udp-rr 1x1 on VPS2: 0.972 [0.938, 1.003] unclear at n=32 (3-5 % low in both runs, no mechanism; T02);
  - wss rr 10x10 on VPS1: 0.982 [0.93, 1.025] unclear at n=32 (P4);
  - round regress (n=16): VPS1 churn 10x10 watch 0.958 [0.922, 0.995]; VPS2 download 1x1 watch 0.969;
  - echo 10x10 probe (host-pressure cell, n=16): VPS2 0.918 [0.62, 1.13] watch, VPS1 download 10x10 0.913 watch;
    bimodal in both builds under host tcp_mem pressure, no level change in the run.
- Host-pressure cells (download / echo / burstidle 10x10 on loopback, 2-vCPU boxes) are invalid as timing (tcp_mem
  pressure during the run); 50.02's stall happened only on VPS1 (why only there: open).
- Dead-peer check (60.17): under heavy sustained packet loss a live and a dead peer look the same to a passive check;
  3 probes make a false reset much rarer (p^3 instead of p^2), not impossible. A client that dies in the middle of a long
  zero-window pause is closed at up to ~360 s.
- Peak RSS columns (VmHWM, wst "peak MiB") on many-CPU boxes come from the kernel's approximate per-CPU counter and can
  read several MiB high (30.10 exact RSS caveat); the settled / idle RSS of wst is exact since base-4's harness fix.
- Memory: a budget below 256 MiB runs at level 1 from the start; at level 1 an upload 1x1 still runs at about half the
  rate of a server without a budget (VPS1 200M: 0.48-0.50 vs off with the target send buffer unset or 256 KiB; 40 to 256 KiB
  sized alike, 60.17 step B). Host mode in a cgroup shared
  with other processes counts their sockets (40.01). Kernel TCP memory pressure is not in the budget (opt-in B3).
- **Heap floor after load (watch item, not a leak):** the idle floor (cgroup anon) still rises a little after each load
  cycle and slows down: LIGHT 1 cycles 31-60 +3.37 / +3.47 KiB per cycle (A / B; 95 % CI upper 4.00 / 3.79, limit 5),
  LIGHT 2 thread arenas +48 KiB/h decelerating (30.17); HEAVY B +139 KiB/h in hours 12-24, down from ~+668 in hours 0-12
  (30.18). Allocator check (30.17 heap follow-up): no leak. glibc arena in-use is flat with tcache off (per cycle A +3.99
  -> +0.42, B +5.62 -> +0.78 KiB), so that growth was freed chunks held in the worker threads' tcache; a heap profile of
  cycles 4-13 found ~10 KiB still live per process (A 9,774 B in 27 blocks, B 9,106 B in 23), all peak capacity of
  long-lived worker containers, none sized by a cumulative count. What stays open: the cgroup anon floor rose about as
  fast in cycles 2-14 with tcache off (A +16.0 / B +12.0 KiB per cycle, vs +18.6 / +16.2 with it), so part of the early
  rise is not allocator in-use; it falls later in longer runs (heap check cycles 15-28 about +6), but 14 cycles do not
  show a plateau. A longer tcache-off run is in the backlog (60.12).
- glibc 2.43 malloc statistics drift (30.17): `mremap_chunk` counts 16 B too many per mremap of an mmapped chunk, so
  malloc_info / mallinfo2 "mmapped" grows linearly while no memory grows (the static binary links 2.43; every System
  Vec past the 16 KiB mmap threshold grows by mremap). Read that counter as drift; RSS and smaps are not affected.
- Server B's quiet-window minima (LIGHT 2: wss; HEAVY: 6G budget) rise faster than the 1 %/h soak bar: LIGHT 2 rss +2.40 %/h [+1.71, +3.26] of a
  3-5 MiB floor (30.17, the 30.14 watch 1 item), HEAVY raw +1.59 %/h [+1.25, +2.01] (floor 8.1 -> 28.3 MiB; 30.18). Same
  arena shape as the floor item above; A (control) passes in both.
- pool_release_max_us reached 65 / 255 ms on a CPU-saturated 4-vCPU box (host CPU 96-99 %; 30.14 watch 2). The RC soaks
  read it beside the new CPU-time metric: LIGHT 2 A 12.5 / B 95.3 ms wall vs 2.3 / 1.8 ms CPU (30.17), HEAVY A 76.6 / B
  38.6 ms wall vs 23.6 ms CPU (30.18): the long ones are scheduling waits on busy boxes, not release work.
- From base-3 and earlier, unchanged: KeyUpdate on kernels < 6.14 closes the connection; credit v2 sibling share 0.68
  (base-2 0.83) with a stalled sibling target, one upload stream to a fast target -2.5..4.4 % (60.14); B3 off in its
  own netns, cgroup v1, kernels < 5.15.
