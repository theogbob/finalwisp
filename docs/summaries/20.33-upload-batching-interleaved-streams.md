# 20.33 Upload batching across interleaved streams (spec, flow, 2026-10-29)

Branch `upload-mux` (from master bab8134). Status: implemented, measured on VPS2 (no LOSS; 1-stream ties). Ready for merge.

## Finding
`wbench upload --conns 1`, small DATA, several streams on one connection: finalwisp collapses, epoxy does not.
Gold (audit): 1 KiB x 1/4/10 streams = 2248 / 186 / 192 MiB/s (epoxy 48 / 685 / 1001); 16 KiB 2777 / 1720 / 1743.
VPS1 (audit): 1 KiB 1255 / 211 / 199 (epoxy 48.9 / 429 / 368). Laptop (functional only, no verdict): 1771 / 258 / 281.

## Mechanism (laptop strace -f of the server, --threads 1, 1 conn, sink targets; counts per MiB uploaded)
| case | target writes / MiB | iovecs per writev | client reads / MiB (KiB per read) | CONTINUE frames / MiB |
|---|---|---|---|---|
| 1 KiB x 1 stream | 16.2 | 62.2 | 4.5 (228) | 1.3 |
| 1 KiB x 4 streams | 1006.9 | 1.0 | 4.5 (225) | 1.7 |
| 1 KiB x 10 streams | 1006.0 | 1.0 | 4.5 (228) | 1.9 |
| 16 KiB x 1 stream | 4.9 | 12.9 | 4.9 (209) | 1.2 |
| 16 KiB x 4 streams | 62.4 | 1.0 | 4.4 (234) | 1.3 |
| 16 KiB x 10 streams | 63.6 | 1.0 | 4.3 (237) | 1.4 |
- The client read side is the same in all cases (~225 KiB per read). CONTINUE work is negligible (< 2 per MiB).
- The 20.09 upload batching (`up_target` + `up_iov`, worker.rs ~902 and Wisp DATA dispatch ~1716) stages only
  CONSECUTIVE DATA frames for one target: a frame for another target flushes the batch. wbench (run.rs `fill`) sends
  per-frame round robin across streams, so with >= 2 streams every frame is its own writev with one iovec: one
  syscall per 1 KiB (1006 per MiB vs 16), the whole cost.
- Real clients interleave too (epoxy/wisp-js multiplex streams per message), so this is not a bench artifact.

## Fix (spec)
Stage per target across interleaved frames of one client read batch; flush every touched target once at the end.
- State (Worker, reused, no per-op heap): `up_bufs: Vec<(u32 /*ti*/, Vec<iovec>)>` = buckets in first-touch order,
  `up_n` = buckets in use (their Vecs keep capacity). Replaces `up_target`/`up_iov`.
- Stage (DATA, body in rbuf, target Open, pend empty, body non-empty): find the bucket of ti (linear: few streams);
  none -> take the next bucket (if UP_TARGETS = 32 buckets are in use, flush all first); push the iovec. If the
  bucket reaches IOV_BATCH (64): flush that bucket only. Total staged entries also capped (UP_MAX = 1024) -> flush all.
- Flush all (`flush_upload`): for each bucket in first-touch order: the existing writev + pend + after_write logic
  (unchanged, moved into `flush_target(bucket)`). Called where flush_upload is called today: end of process_input,
  before any non-DATA Wisp frame (CONNECT/CLOSE/... keep their order vs all staged data, as now), and before a DATA
  frame that is not staged (fragmented/copied body, pend non-empty, not Open) - the conservative choice, as today.
- close_target(ti): flush ti's bucket (data before CLOSE), not only when it is the current target. sweep / set_level
  guards: "no bucket in use" instead of `up_target == NO_TARGET`.
- Order: per stream strict (one bucket per target, iovecs in arrival order, one flush per bucket in order); across
  streams order does not exist on the wire (different target sockets), so nothing visible changes.
- Credit (20.30 v2 / base rule): `since` and cv.on_data still count per frame at staging; after_write runs once per
  flushed bucket instead of once per frame (as for a single stream today). Backpressure: partial writev -> rest into
  pend with the same caps (pend_over / PEND_HARD, 0x49 hold/shed) as today.
- Safety: iovecs point into the client's rbuf; still flushed before process_input returns (rbuf not touched while
  parsing a batch). Write error on one target closes only that target; other buckets still flush.

## Implementation (worker.rs)
- `Worker::up_bufs: Vec<UpBucket { ti, iov }>`, `up_n`, `up_total`; `stage_upload`, `flush_upload` (all buckets in
  first-touch order), `flush_bucket` (the old flush body, unchanged logic). UP_TARGETS 32, IOV_BATCH 64, UP_MAX 1024.
- rbuf rule (field doc + `debug_assert!` in read_client, fuzz harness asserts nothing staged after each connection): the
  staged iovecs point into one client's rbuf, which is not compacted, grown, re-read or freed while anything is staged.
- A WS PING now also flushes first (every non-DATA frame does: Wisp non-DATA, CLOSE, PONG via credit_pong, PING).
- close_target flushes its own bucket (not only "the current target").
- Tests: upload_interleaved_streams_batch_per_target, upload_batch_partial_and_eagain_buckets,
  upload_non_data_frame_flushes_all_buckets (mutations: no PING flush, reversed bucket order, wrong pend copy: all fail).
  Fuzz seeds `interleaved*` (worker-wisp, worker-stream).
