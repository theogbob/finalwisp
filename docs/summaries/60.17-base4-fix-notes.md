## T04 client ping/pong or idle timeouts vs the upload hold and the credit-v2 pings (source read, 2026-10-30)
Question (60.12): can a 4-6 s whole-connection upload hold (0x49 hold, pend_sweep) or the credit-v2 WS ping after each
CONTINUE batch trip a client-side timeout?
- wisp-js 0.5.0 (tests/compat/node_modules/@mercuryworkshop/wisp-js/src): the client has no timer on the Wisp connection or
  its streams. The only client timer is the send throttle in websocket.mjs (polls bufferedAmount every 10 ms while the
  WebSocket send buffer is over half full: it waits, it never closes). Pings are answered by the WebSocket layer (browser /
  node ws). The 30 s ping_interval is the wisp-js SERVER's own keepalive.
- wisp-mux / epoxy (ref/epoxy-tls 0c11678, wisp/src, client/src): no timeout, ping or pong logic in the mux, stream or ws
  modules (rg timeout|ping|pong|interval: none); tokio_websockets answers pings itself; in the browser the native WebSocket
  does. The only interval is epoxy-server's 30 s ping (server side).
- libcurl.js (libcurl-transport 2.0.5 bundle used by bench/browser, and the libcurl.js source fcfefe1): no ping/pong code;
  its timers are the emscripten event loop and the recv poll (setInterval 0). libcurl.js sets no CURLOPT_*TIMEOUT or
  LOW_SPEED option in client/libcurl/*.c, so libcurl defaults apply: no transfer timeout, connect timeout 300 s. A new
  stream's CONNECT + TLS handshake behind a held connection waits at most the hold (seconds), far below 300 s.
Result: no client-side timer that a hold of seconds or our pings can trip. **No code change.** Already covered by tests:
credit_v2.py (eager wisp-js pong pattern, foreign pongs), browser 90/90 with credit v2 (60.14).
Limit: application timeouts above the transport (a page's own fetch timeout) are out of scope; they see a slower upload,
not a protocol error.

## T40 kTLS stall: a pending KeyUpdate under host TCP memory pressure (commits 1dc99c3 .. cf18913)
Symptom: with the host over tcp_mem[2], a kTLS client with a KeyUpdate pending sent nothing more, ever: flush sent the
KeyUpdate first and returned on EAGAIN, and the 50.02 A2 gather skipped ku != 0.
Kernel (6.8-7.0, net/tls/tls_sw.c tls_sw_sendmsg_locked): the 5-byte KeyUpdate record is refused whatever is queued. With an
empty queue the charge is not forced (wmem_queued + size < sndbuf); with a queue >= sndbuf, sk_stream_memory_free fails at
:832 before the alloc at :844.
Repro: incus VM fw-ku on the build host (ubuntu 26.04, kernel 7.0, 4 CPU), tcp_mem lowered to "3000 4000 5000" in the VM only,
wss 10x10 with --tls-rekey-records 64 (makes KeyUpdates frequent; the default is 2^23 records). Functional only: stalled
reps (< 50 MiB/s) are counted, no timing claims.
Attempts that failed in the VM (strace attached 1.5 s into a run):
- 1dc99c3: gather the data, then the KeyUpdate. The KeyUpdate was still refused; each 200 ms retry sent one 16 KiB record:
  ~1 MiB/s crawl.
- Gather 8 KiB under MSG_MORE, so the KeyUpdate push meets an open record: still refused, 0.7 MiB/s (diff kept in
  raw data (not published)).
Fix: our own KeyUpdates do not hold the data. ku states: 0 none, 1 ours (proactive TX rekey), 2 ours asking the peer
(update_requested, RX budget), 3 the reply owed to the peer's update_requested. A refused 1 or 2 stays pending and is
retried at every flush while the data goes on under the old key (2^23 records of TX slack before the hard limit; for 2 the
peer's RX limit closes as before). 3 keeps the RFC 8446 4.6.3 order: it goes first (before the starve gather), and a
refused one holds the data. ku_after_peer_update maps (requested, ku): requested -> 3; not requested and 2 -> 1; else
unchanged. The RX ask is not set over a pending 3.
Correction (review three reviewers, reviewer A+reviewer B P1, 2026-10-30): bc27503 treated ku 2 as "peer-requested", but 2 is our own ask and
the owed reply was ku 1; f77de14 added state 3. cf18913 (reviewer A P3): send 3 before the starve gather.
Tests: refused_key_update_holds_data_only_when_reply_owed (transition table + 9 flush cases with test hooks send_log and
ku_refuse; fails on the master rule). Full cargo test both feature sets, clippy, fmt clean.
VM results (6 reps, rekey 64; rekey 0 controls healthy on both builds, 0 errors):
| build | download stalled | download MiB/s | echo stalled | echo MiB/s |
|---|---|---|---|---|
| master 1850d055 | 6/6 | 0 | 1/6 | 13-896 |
| f77de14 | 0/6 | 949-1805 | 0/6 | 535-886 |
**Known limit:** a refused ku 3 still holds the data until the pressure eases (rare: needs the client's update_requested
while the host is over tcp_mem[2]); see 50.02 "known limits". Also: starve_step uses out_empty(), which ignores a pending
KeyUpdate, so a refused KeyUpdate with no data queued is retried only at the next flush (pre-existing, harmless).
Functional gate on the final build (cf18913, md5 2bf08155, fixed copy raw data (not published); laptop, kernel

## T03 P3 design note: count our own socket memory instead of the host's (not implemented; lead takes it to the maintainer)
Today (mem.rs detect/sampler): with a cgroup limit (v2 memory.max/high, or v1 limit) the budget's usage is the cgroup's
own memory.current (v2) or memory.usage_in_bytes (v1) minus inactive file: already "ours". Only **Host mode** (no cgroup
limit: --mem-budget on a host or in an unlimited cgroup, or auto = MemTotal/2) adds the **host-wide** TCP memory above
its startup level (/proc/net/sockstat "TCP: mem", TCP0 baseline). (a') is that case: on loopback, the bench's own client
and target sockets count, so download 10x10 at <= 200M went to L3 and shed with a ~5 MiB heap. In production the same
happens with any TCP-heavy neighbour (a proxy, a database, another finalwisp) or after the baseline (TCP0) was taken
while the host was idle.
Options for Host mode:
1. cgroup v2 (the common case: systemd services and most container runtimes put us in our own cgroup with the memory
   controller on): usage = heap + memory.stat `sock` of our own cgroup. `sock` = "memory used in network transmission
   buffers" (cgroup-v2.rst), charged per cgroup for every socket we own (TCP and UDP, both directions). It is the source
   20.31's guard (a) already reads (own_sock_stat), so no new file. No baseline needed (sockets of other cgroups never
   count). Caveat: our own cgroup may hold other processes (a shell, a sidecar); still far closer than host-wide.
2. cgroup v1: memory.kmem.tcp.usage_in_bytes exists, but the kernel accounts TCP buffers to a v1 memcg only after
   memory.kmem.tcp.limit_in_bytes was written for it (mm/memcontrol-v1.c memcg_update_tcp_max sets tcpmem_active;
   sockets created earlier stay unaccounted). Usually never written, so the value is 0: not usable as a default; read it
   only when memory.kmem.tcp.limit_in_bytes is below "unlimited", else keep today's host-wide term.
3. No cgroup (rare: a bare process outside any memory cgroup): keep host-wide sockstat minus TCP0.
What host-wide TCP memory must still drive: the kernel's own tcp_mem pressure is host-wide (one counter for all
sockets), and over tcp_mem[2] every socket's charge is refused (50.02/T40). That is not our memory budget but a host
condition: it stays with 20.31 B3 (--tcpmem-adapt, TCP_LEVEL, caps only, never above level 1) and its guard (a) (our
share >= 25 % of the host's TCP pages, read from the same `sock` line). So option 1 separates the two signals cleanly:
budget level = our heap + our sockets; TCP level = host tcp_mem pressure with our share as the guard.
Interaction: B3 and the budget then never double-count: today in Host mode a host pressure raises both the memory
level (host TCP term) and the TCP level; with option 1 only the TCP level (when our share is big enough) and only up
to the level-1 caps, which is what 20.31 decided for kernel pressure ("kernel TCP pressure is not OOM").
Risk: our sockets can be large while the heap is small (download into slow clients): option 1 still counts them (they
are in `sock`), so the budget keeps its job. Loss: a neighbour's TCP memory no longer pushes us to shed, which is the
intent (we cannot free someone else's memory).
Recommendation (mine): option 1 in Host mode when our cgroup v2 memory.stat has a `sock` line, else today's term;
v1 kmem.tcp only when its limit is set. Effort S-M (mem.rs sampler + detect + tests with a fake memory.stat).

### P3 design review (three reviewers, 2026-10-30) and decision
Reviewer A ( fallback), reviewer B, reviewer C: **all three adopt the change, with amendments.** Agreed points (2-3 seats):
- `sock` (v2 memory.stat, bytes, hierarchical = our subtree, TCP + UDP) is the right Host-mode signal. Kernel 6.8: outgoing
  sockets are charged to the creating task (sk_alloc), accepted ones at accept() to the accepting task
  (inet_csk_accept: mem_cgroup_sk_alloc + force-charge of what is queued). Connections still in the listen backlog (admit
  off at L2/L3) are nobody's until accepted: a bounded jump on accept. Sockets created before a cgroup move stay with the
  old cgroup: documented, not detected.
- `cgroup.memory=nosocket` (sock stays 0): detect from /proc/cmdline at startup -> host-wide. A sock line alone is not
  enough.
- Real root cgroup: memory.stat exists there but memory.current does not (checked on VPS1/VPS2: root stat yes, current
  no); its `sock` is everyone else's. Require memory.current in the same directory (also fixes B3's own_sock_stat, a
  pre-existing bug: in the real root B3's "own share" is other cgroups' sockets).
- Keep the startup TCP0 baseline (taken before accept) for the fallback path; keep B3's host pages (tpages) working when the
  Host branch no longer reads sockstat (reviewer A: implementation trap at the tsock/host_pages split).
- No default protection is lost: with the auto budget (MemTotal/2) the host-wide term alone tops out far below L1
  (tcp_mem[2] ~ 9 % of RAM); kernel tcp_mem pressure stays B3's (opt-in, 60.18), a pre-existing gap.
- Proof beyond (a)/(b)/(c): server in its own scope with the capability line naming the source (else the test exercises the
  fallback); a negative control (server in the bench's scope still counts the bench); a socket-heavy small-heap own load
  (T03 P4 64M upload, slow readers) still reaches the levels; calibration sock vs (sockstat - TCP0) with the server alone;
  sampler cost; unit tests on fake trees (no file, no sock line, root, nosocket, read failure); B3 still enters in Host mode.
Split points, my decisions:
- Baseline for `sock`: reviewer B/reviewer C absolute; reviewer A keeps the idle re-baseline (absorbs siblings' steady sockets in a shared
  cgroup, ~0 in our own). **Keep the idle re-baseline** (existing rule, only taken with no clients for 1 s, so it never
  absorbs our own sockets).
- Read rate: reviewer C <= 10/s (100 ms); reviewer A/reviewer B every tick after measuring. Measured idle, 2 vCPU 6.8: memory.stat 8-11 us
  per pread, /proc/net/sockstat 10-33 us. **Read every tick but at most every 5 ms**, and measure sampler CPU at L3 in the
  proof; if the flush cost under load is high, fall back to 20 ms.
- Runtime "sock stays 0" tripwire: reviewer A/reviewer C yes, reviewer B says 0 is not proof. **No tripwire**: cmdline check + capability
  line + documented limit.
- v1 kmem.tcp: dropped (all three): Host mode + v1 keeps host-wide.
Box layout (VPS1/VPS2): kernel 6.8, memory controller delegated at the root (cpu memory pids), `systemd-run --scope -p
MemoryAccounting=yes` gets its own scope with memory.stat + memory.current; ssh sessions run in a session scope (shared
with the bench unless the server gets its own scope).
Plan: implement in the mem.rs round (after slab's tidy), proof as above; if the data disagree: keep today's count, documented.

## RC finding: peer_gone false reset of a live zero-window reader (gold heavy soak), branch peer-gone3
- Gold 12 h heavy soak (RC1): 1 of 2,058 zero-window pauses of a live slow reader (plain) was reset ~350 s into a 403 s
  pause (dead_peers 0 -> 1). Host CPU-saturated after a 5.9 GB/s window: softnet drops up to 83k/CPU, TCPRcvQDrop 95,840,
  TCPBacklogDrop 24,420, host TCP pressure 0.
- Mechanism (net.rs + Linux v6.8 tcp_output.c / tcp_input.c): the probes are the kernel's zero-window (persist) probes,
  not our keepalive (it skips sockets with queued data). icsk_probes_out (tcpi_probes) rises at each probe send and any
  acceptable ACK (the live peer's dup ACK) clears it and refreshes tcpi_last_ack_recv. The backoff doubles to 120 s, so
  probes at ~102, 205, 325, 445 s of a pause. Rule was ACK age >= 150 s AND >= 2 in a row (+ the 2-sweep latch): two lost
  probe exchanges (probe or reply; loopback drops hit both) at ~205 and ~325 s reset a live reader at ~327-330 s.
- Repro (VPS2 root, kernel 6.8; netem loss on lo only for the WS ports via prio + u32; 20 or 50 download clients that
  never read, SO_RCVBUF 64K, 460 s pause; a systemd-run timer removes the qdisc if the driver dies; tc empty after
  every run): 30 % loss: **RC1 12/20 reset**, no-loss port 0/20; **fix 3/20**. Paired 10 % loss (both ports lossy, RC1
  vs fix side by side): **RC1 5/50, fix 0/50**. Data: base4fix raw data (not published)
- Fix: PEER_GONE_PROBES = 3 (net.rs gone_by, test peer_gone_needs_three_unanswered_probes, fails with 2 and with 4).
  A live peer must lose 3 exchanges in a row (>= 240 s at full backoff). Limit: under heavy sustained loss a live and a

- Cause: wst regress/idle sample the server session with sample.group_usage, which summed /proc/PID/stat field 24 (rss).
  On kernel >= 6.16 that field is the approximate percpu_counter read (global count only), while VmRSS in status is the
  exact sum (commit 82241a83cd15). The batch is max(32, 2*CPUs) = 144 pages = 576 KiB per CPU on 72 CPUs; after many
  threads free on many CPUs the unflushed negative deltas leave stat high. Paired check (out/st2, 8 runs, same instant):
  b3 VmRSS 15.2-15.7 vs stat 15.3-24.0; rc1 VmRSS 16.4-17.3 vs stat 24.3-32.1. rc1 frees on more CPUs, so it read
  higher: a false LOSS.

  status is gone); 2 new tests, 38/38 bench tests pass (run on gold). Reviews: reviewer B clean; reviewer A

  the approximate counter (peak RSS columns can carry the same bias on many-CPU boxes).
