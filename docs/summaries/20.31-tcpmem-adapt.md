## Premise (measured on VPS1: 2 vCPU, 3.8 GiB, kernel 6.8, base-2 binary 50560e9a, default sysctls)
- tcp_mem = 44769 / 59692 / 89538 pages = **175 / 233 / 350 MiB** (4.5% / 6% / 9% of MemTotal: the kernel's default
  scaling, so every 2-4 GiB VPS has a pressure threshold of ~120-250 MiB). tcp_rmem/tcp_wmem max 16 MiB.
- The current sampler cannot see it: host mode budget = MemTotal/2 = 1.9 GiB (the server's ~110 MiB of socket memory is
  ~6% of it: level 0 throughout); cgroup mode does not read sockstat at all.

Sampled every 50 ms (sockstat "TCP mem", TcpExt TCPMemoryPressures / ...Chrono, ss -tm per process at mid-run):

Host mode with a budget that does see it (--mem-budget 400M: level 1 at 200 MiB above the idle baseline), loopback 10x10:
download pressure 30 -> 1-5 entries, 3.7 -> 0.35-0.96 s, but 1700 -> 1170-1240 MiB/s; upload 0 entries, but 965-1210 ->
365-430 MiB/s (it flapped 1 <-> 0 every few hundred ms: 8-9 level-down lines per run); echo 273-405 -> 523-638 MiB/s
(caps beat the kernel's pressure). --mem-budget 200M (stays at level 1, no flapping): upload 693-714, echo 524-563,
download still in pressure (4 errors: level 3 sheds; there the peers' memory alone passes tcp_mem[1]).

What this says:
1. Pressure is real on a default small VPS and the kernel's own remedy is brutal: 1G/20ms echo 10x10 collapses to 3.5 MiB/s,
   download with the target on the host to 1.4 MiB/s (memory at tcp_mem[2]: allocations fail). Bulk regress cases on
   VPS1/VPS2 are invalid for this reason.
2. **The server's own share with 100-200 streams is 60-120 MiB** = 25-50% of tcp_mem[1] on this box. With remote peers
   (production) it reaches pressure by itself at roughly 2-3x that load, or earlier when other processes use TCP memory.
   In every bench setup above the peers on the same host hold the rest, so loopback/netns bulk cases mix both.
3. Capping only our sockets cannot end a pressure caused by others (netns download with the target on the host: the
   target's send queues alone are 250 MiB). A rule that ignores our share would cost us throughput for nothing there.
4. Level-1 caps are not free (upload -40..-65% when flapping, -30% download), so the trigger must be close to the real
   threshold, with hysteresis and a dwell, and be judged by a benchmark that compares against the kernel's pressure.

## Decisions (lead, 2026-10-27) and what was built
1. Default OFF, opt-in `--tcpmem-adapt`. Default-on only if the pressure benchmark shows a net win AND the normal regress
   has no LOSS; the maintainer decides with that data.
2. TCP level max = 1 (Stage caps only). Level 2 would refuse streams/accepts: kernel TCP pressure is not OOM. Level 2 from
   TCP only if the benchmark shows level 1 cannot leave pressure.
3. Guard (a) only, and REQUIRED: our share = memory.stat `sock` of our own cgroup v2 (read in every budget mode, host mode
   too). No such file (cgroup v1, no memory controller) = "tcpmem adapt disabled: share unknown" in the capability line.
   At runtime a failed read, or `sock` 0 while we have connections (boot option cgroup.memory=nosocket), = no entry,
   logged once. Guard (b) (SO_MEMINFO sums in A's sweep) dropped unless the benchmark needs it.
4. Off without SO_BUF_LOCK (Linux < 5.15; restoring a cap there loses autotuning for the socket's life), logged.
5. Thresholds and dwell as proposed; one cap rule via set_level / Stage; sizes only from mem::STAGES.

Built (server/src/mem.rs `TcpAdapt`, `tcp_next`, `tcp_adapt_setup`, sampler; main.rs capability line; metrics.rs keys):
- Needs the memory budget (the sampler); `--mem-budget 0` = off, logged.
- The sampler keeps the memory level `ml` (own hysteresis + 250 ms dwell) and the TCP level `tl` (0/1); it publishes
  LEVEL = max(ml, tl). With the flag off `tl` stays 0 and the published level is exactly the old one.
- TCP level 1: enter at >= 900 permille of tcp_mem[1] when our share >= 250 permille (read at most every 100 ms, only
  when at the threshold); leave below min(tcp_mem[0], 90% of the entry) and >= 2 s after entering.
- The sampler polls at 5 ms when sockstat is above 3/4 of the exit threshold (else unchanged).
- Logs: `finalwisp: tcp level 0 -> 1 (host TCP memory N of M pages tcp_mem[1], K pages moved into our heap, own share X%)` on every TCP change; the
  memory-level line gets the same reason when the flag is on.
- Metrics (60.12 line): tcp_level, tcp_pages, tcp_moved ((iii) heap pages counted toward the exit), tcp_own_pm (na = not read yet, unknown = failed), tcp_enters, t_tcp1, and
  host_tcp_pressures / host_tcp_pressure_ms (TcpExt, since boot, this netns; printed in every line).

Limits found while building:
- **Only the host's initial network namespace shows net.ipv4.tcp_mem** (checked on VPS1, 6.8: `ip netns exec X cat
  /proc/sys/net/ipv4/tcp_mem` = ENOENT; sockstat "mem" is global and still readable). A container with its own network
  namespace (Docker default) therefore gets "tcpmem adapt disabled: net.ipv4.tcp_mem is unreadable". Option for later:
  derive the kernel default from the free-buffer pages (wrong if an admin changed tcp_mem), or accept the limit.
- memory.stat `sock` counts all our socket memory (UDP too), sockstat counts TCP only: under UDP load our share reads high.
- If the server shares its cgroup with other processes, their socket memory counts as ours.

## Normal regress, --tcpmem-adapt ON vs OFF (lead request; VPS1, same binary d886e697, lo,tls,idle,potato, 16 reps; raw data (not published))
**0 LOSS among valid cases, 0 WIN; the 5 bulk 10x10 cases stay INVALID** (host TCP pressure during the case: download 247x,
upload 117x, echo 78x, burstidle 848x, wss download 104x; the suite counts host-wide, both variants together). B3 does not
make them valid: on loopback the client, server and target sockets are all on this host, and B3 only caps ours.
What the invalid cells show (flag on / off, all p < 0.02 except wss): **upload 10x10 0.44, peak RSS 7.45 -> 399 MiB**;
download 10x10 0.81 (CPU per MiB 2.6x); burstidle 0.82 (2.55x); echo 10x10 1.48; wss download 1.07 (p 0.065).
Valid cases (no pressure: B3 never acts): download/upload/echo 1x1, connchurn, connchurn-tls, idle tie; rr, wss rr unclear;
churn 0.965 watch; potato: 4 watch (churn 16M 0.911, 32M 0.936, upload 32M 0.863, upload 128M 0.926; all n.s., n = 8), rest
tie/unclear, all alive. Same binary both sides, the flag only acts under host pressure (not in potato): these are noise-level.

**Defect in (b) found here (upload 10x10, peak 7 -> 399 MiB):** at memory level 0 the stream credit stays at --buffer (128
packets) and grant_window is 0 (packets only), while (b) caps the target sockets to 32 KiB. On loopback a capped target
socket drains slower than the client sends, so the upload backlog (pend) takes up to 128 x 16 KiB per stream x 100 streams
in heap: B3 moves the memory from kernel socket buffers into our heap, and costs 56% upload throughput. The full level-1
stage bounded this with grant 8 / hs 8 / grant_window (mem.rs grant_window doc: "the capped socket holds 2 x the cap, so a
draining target keeps the backlog at ~0"); (b) dropped exactly that coupling. The 1 Gbit benchmark did not show it (the
link, not the 32 KiB target socket, was the bottleneck: upload tie). Download 10x10 / burstidle 0.81: 32 KiB target caps on
loopback (MSS 64 KiB) cost CPU per MiB 2.6x, as the full stage would.
Proposed fix (b2), not implemented (lead: report, then idle): with TCP caps take grant, hs, win and the refill rule
(credit coupling) from the cap level too; keep out_high/keep/rbuf/max_streams at level 0. Then re-run the 1 Gbit pressure
benchmark (download 10x10 alone must stay a tie) and this regress (upload 10x10 peak RSS must stay near base).
Default-on is **not supported** by this data until (b2) is measured.

## (b2) credit from the cap level (2026-10-28, commit 0701c2d + 1f8dfa7)
With TCP level 1 at memory level 0 the workers now also take the level-1 credit: grant 8, hs 8 (mem::stage), grant_window,
the refill rule (refill_due) and its out_low gate (worker after_write), all from the cap level; queues (out_high/out_low for
target reads), keep, rbuf, pend_over, max_streams stay at the memory level. Reviewed (reviewer A + reviewer B): no defect; doc fixes.
Known limit (review, pre-existing from (b)): raw (wsproxy) streams have no credit; under TCP caps at memory level 0 their
pend is still bounded only by the level-0 out_high (1 MiB per stream).
**credit-v2 + B3:** the flow branch's branch credit-v2 adds a second credit mode (credit.rs) and is not on master yet; (b2) was not
tested with it. Once both are on master they need a joint test (this pressure benchmark + the loopback regress with
--tcpmem-adapt and credit-v2 on).

## Design (proposal, before the decisions above)
**One level path.** The sampler (mem.rs, thread `mem`) computes a TCP level next to the memory level and publishes
`LEVEL = max(mem level, tcp level)`. Workers are unchanged: `set_level` applies the Stage caps, so there is one cap rule
(tighter wins automatically: one published level), sizes are saved once (Client/Target `saved`) and restored once at
level 0. Cap sizes come only from `mem::STAGES` (never hard-coded here; the flow work is raising the L2/L3 client_rcv floor).
- Input: /proc/net/sockstat "TCP ... mem" (pages; one pread on a kept-open fd, already used in host mode) in **both**
  host and cgroup mode, every sampler period (2-20 ms; it is a 200-byte read). tcp_mem read once at startup (the server
  never writes sysctls; a change of tcp_mem at runtime is picked up at the next restart: deliberate).
- TCP level (permille of tcp_mem[1], own hysteresis table, same `next_level` shape):
  L1 enter 900 (just below the kernel's pressure threshold), exit at tcp_mem[0] (the kernel leaves pressure there; 750 with
  the default ratio). L2 (no new streams/accepts) enter 1000 + a quarter of the way to tcp_mem[2], exit 900.
  **Never L3 from TCP** (L3 stops reading clients and sheds; a host-wide signal shared with other processes must not
  kill our clients). Dwell down 2 s (vs 250 ms for memory): the kernel's own exit is slow, and flapping cost upload 60%.
- **Own-share guard**: act only while our share of the host's TCP pages is >= 1/4 (else the pressure is someone else's and
  capping only costs us). Share source, in order: (a) cgroup v2 memory.stat `sock` of our own cgroup (charged per cgroup,
  readable whenever the memory controller is on for it: systemd services, containers); (b) else, while the TCP level
  would be >= 1, each worker sums SO_MEMINFO (sk_rmem_alloc + wmem_queued + fwd_alloc) of its sockets at its idle sweep
  (2 s; only under near-pressure, never on the I/O path) into a per-worker atomic. If neither works: no guard (act on the
  host value), logged once.
- Kernel < 5.15 (no SO_BUF_LOCK): sockets capped during an episode stay capped (existing known limit, 60.10); the
  capability line already says so. Option: no TCP adaptation without SO_BUF_LOCK (decide after the benchmark).
- Log: the level-change line gets the reason (`memory level 0 -> 1 (host TCP memory 54100 of 59692 pages, own 41%)`).
  Metrics (60.12 line): `tcp_level`, `tcp_pages`, `tcp_own_pct`, time at each TCP level, TcpExt TCPMemoryPressures delta.
- Flag: on by default per 60.07 B3 (user) with `--no-tcpmem-adapt`; OFF must equal base-2 except one sockstat read per
  sampler period in cgroup mode (cgroup mode reads memory.current already).
- Size: ~80-120 lines in mem.rs (sampler + table + guard (a)); guard (b) ~30 lines in worker.rs sweep (A's file: one call).

## B redesign: no TCP-level caps on same-host sockets (branch b3-redesign, 2026-10-29; the flow work)
Goal (user-approved task B): keep the B3 memory wins (echo/upload peaks, the 1 Gbit holder cells) without the loopback
bulk-download cost of 60.14 (download 0.65-0.72, burstidle 0.72-0.83, ~2.8x CPU per MiB under host tcp_mem pressure).
Default stays off; a default-on proposal needs the bar on both boxes.

**Rule (worker::tcp_only_local):** when the caps come only from the host TCP level (memory level 0, cap level 1), a
same-host socket is not capped, client or target. Same-host = net::same_host: the peer is loopback (127/8, ::1,
v4-mapped) or the peer address equals our local address. Remote sockets keep the caps of b3-optin; memory-level caps
(level >= 1) cap every socket as before. Why: what a capped receive buffer refuses waits in the sender's send queue; for
a same-host sender that is host TCP memory too, so the cap cannot lower it (b3cpu, VPS2 loopback: host pages 32k -> 47k
median with the caps, a self-sustaining TCP level 1), and below the loopback MSS (64 KiB) every read ran the local
sender's transmit (CPU per MiB 2.4-2.8x). Locality is read once per socket (getpeername + getsockname), only when such a
cap is due (accept, lazy cap, connect, level change). set_levels refits when memory level 0 is crossed even if the cap
sizes stay (the exemption depends on it; test tcp_level_caps_remote_sockets_only, mutation-checked).
- **Gap (by decision, no interface scan):** a peer on another non-loopback address of this host (A -> B, both local)
  counts as remote and is capped as before.
- **Same-host reverse proxy (40.01 nginx/Caddy):** every client is same-host, so the TCP level caps no client there;
  consistent with the rule (refused bytes would wait on this host anyway). Targets are still classified one by one.
- Netns/veth peers have other addresses: remote (the 1 Gbit bench relies on it).

**How it was chosen (spike, VPS1, 8 reps vs base-2, env knobs, reverted d0e6647):** current B3 download 0.886, CPU per
MiB 2.38x, echo 1.41x; no target caps download 1.68, CPU 0.742x, echo 2.59x; no client caps download 1.04, CPU 1.55x.
Bigger or MSS-scaled target caps do not help (rmem_max clamp; b3cpu agrees). Candidate B (1ceab27: no TCP-level client
caps at all + no same-host target caps) won on loopback but on the 1 Gbit bench lost echo vs current B3 (0.938, CI90
[0.909, 0.967], 46.6 vs 50.2 MiB/s) and raised upload memory.peak 62 -> 84 MiB: remote clients need the caps.
Candidate C (this rule, 3a3bcb4 + f4f0863, bench binary md5 8f1c2de8) = B on loopback, current B3 on remote links.
