## Run it
- One static binary (bench/release.sh): no glibc version floor, no runtime dependencies. Linux x86_64 only.
- Plain: `finalwisp --host 0.0.0.0 --port 6001` (ws://). Behind a TLS proxy: `--host 127.0.0.1` and let the proxy
  terminate TLS. Built-in TLS (kTLS): `--tls-cert fullchain.pem --tls-key privkey.pem` (wss://; repeat the pair for
  more names, picked by SNI; SIGHUP re-reads the files).
- No root needed. Ports < 1024 need CAP_NET_BIND_SERVICE. kTLS needs the `tls` kernel module loaded: `modprobe tls`
  now and `echo tls > /etc/modules-load.d/tls.conf` for boot; the server autoloads it only with CAP_NET_ADMIN (not
  recommended). Without the module a wss:// start exits with "modprobe tls"; ws:// is not affected.
- Config file (60.20 C8): `finalwisp --config /etc/finalwisp.conf` reads the same flags from a file, one per line
  without the dashes (`port 6001`, `allow-private`, `dns-server 10.0.0.53`; `#` comments). Flags after `--config`
  override the file; a list flag on the command line replaces the file's list. Errors name FILE:LINE (never the value)
  and exit 2. With systemd: `ExecStart=/usr/local/bin/finalwisp --config /etc/finalwisp.conf`; the service user must read the file
  (with the unit's `DynamicUser=yes` that means mode 644: keep secrets in the files it names, e.g. `auth-file`; or use a
  static user as the unit's comment on `--tls-key` says, and mode 640). Format and rules: 40.03 "Config file".
- Open files: one fd per connection and per stream (+2 pipe fds per client using splice). Set LimitNOFILE= (systemd) or
  `ulimit -n` / `--ulimit nofile=` (docker) high, e.g. 1048576; the startup warns below 65536.
- The server never writes sysctls and needs none. It only warns at startup about values that limit it (capability line,
  below): tcp_wmem/tcp_rmem max, tcp_mem max, somaxconn, RLIMIT_NOFILE.
- Build: `bench/release.sh` (own buffer allocator, 70.25: the only allocator path since 60.18 #11; the old glibc + 70.11
  block cache build, `NOFEAT=1`, was removed after base-4: build tag base-4 if you need it). The capability line says
  whether the pool runs ("pool on" / "pool off: <why>").


## Flags (`finalwisp --help`; full reference with defaults, units and evidence: 40.03)
- Main options: listen address and threads, SSRF filter (--allow-loopback / --allow-private), timeouts, kTLS
  (--tls-cert/--tls-key), DNS (--dns-threads, --dns-own, --dns-server), Wisp v2 auth and MOTD, --mem-budget,
  --drain-timeout, --metrics-interval, --metrics-listen (Prometheus, section "Metrics"), --no-credit-v2 (rollback to the
  base-2 credit rule).
- Opt-in: `--balance` hands new connections to the least loaded thread. It helps a few busy long-lived connections on
  big boxes (churn/rr +4..11 % at 36-72 threads) and costs on connection churn (connchurn rps -0.6..-7.5 % in 7 of 8
  cells, echo 100x10 up to -2.6 %), so it stays off (60.15 T21). `--tcpmem-adapt` (20.31 B3) caps REMOTE sockets near
  host TCP memory pressure; see 40.03 for what it needs.
- Bandwidth caps (60.30 C10a, off by default): `--download-rate RATE` per connection, `--upload-rate-per-stream RATE`
  per TCP stream; bytes/s with K/M/G (1M = 8.4 Mbit/s). Limits: section "Bandwidth caps" below.
- Upload caps (60.25 C10b, off by default): `--upload-rate R[/B]` per connection, `--upload-rate-per-ip R[/B]` per
  client key; bytes/s with K/M/G. Section "Upload caps" below.
- PROXY protocol (60.34, off by default): `--proxy-protocol tcp|unix` requires a v1/v2 header on that listener,
  `--proxy-protocol-from CIDRS` (required for tcp) names the load balancers. Section "Reverse proxy" below.
- Unix socket listener (60.31 C7, off by default): `--listen-unix PATH` (plain ws:// for a reverse proxy on this host,
  besides the TCP listener), `--unix-mode OCTAL` (default 660). Section "Reverse proxy" below.
- Upstream proxy (60.32 C6, off by default): `--upstream socks5://|socks5h://|http://[USER:PASS@]HOST[:PORT]` sends every
  TCP stream through one proxy; section "Upstream proxy" below.
- Advanced / diagnostic (leave at the default unless a problem points here): --graceful-close, --no-splice, --no-tfo,
  --no-keepalive, --no-prio, --notsent-lowat, --tls-rekey-records.
- Removed in base-4 (60.18): `--credit-v2`, `--prio`, `--no-tcpmem-adapt`, `--no-dns-coalesce`. A start command that still
  passes one exits 2 with "<flag> was removed in base-4 (60.18): <why>; drop it". Delete the flag.

## Building it yourself (60.36)
`bench/release.sh` is the build to use: fat LTO, codegen-units 1, opt-level 3, panic abort, static glibc, reproducible
(the same commit gives the same md5 anywhere, 40.02). Extra compiler flags were measured on base-6-rc1 (60.36: VPS2, AMD
EPYC-Milan): `-C target-cpu=x86-64-v3`, `-C target-cpu=znver3` (native), PGO and PGO + v3 give no measurable gain
(cycles per connection / request / MiB within ±3 %, regress n=16 all ties). The kernel does 90-99 % of the work (TCP,
splice, kTLS), so making finalwisp's own code faster barely shows. target-cpu builds also stop running on older CPUs and
lose the reproducible md5. The exact PGO steps are in 60.36 if you want to try it on your own hardware.

## Signals
- SIGHUP: re-read the TLS certificate files (all or nothing; a bad file keeps the old set). Live connections keep theirs.
- SIGTERM / SIGINT (60.12): stop accepting (connections already queued are accepted first, then the listeners close;
  new ones are refused), close idle Wisp connections at once (WS 1001 "going away", kTLS: + close_notify), serve the
  rest until they end or --drain-timeout passes, then 1001 to all and exit 0 (at most 2 s later). A second
  SIGTERM/SIGINT exits at once. Clients see 1001 and reconnect elsewhere. With --metrics-interval the last line is
  `ev=metrics_final`. Log lines written by the signal thread wait at most 500 ms each for stderr (a stuck log pipe
  cannot delay the exit; such a line is then lost).
- Supervisors: the kill timeout must be longer than --drain-timeout + 2 s. systemd TimeoutStopSec default 90 s: fine.
  docker stop default 10 s: use `docker stop -t 35` or `--drain-timeout 7`. Kubernetes terminationGracePeriodSeconds
  default 30 s: set it to 40 or --drain-timeout 25.
- Policy limits (60.20 C3a, opt-in, off by default): `--max-conns N` resets connections over N at accept (exact across
  threads and --balance); `--max-streams-per-conn N` answers a CONNECT over N streams on one connection with 0x49. They
  are policy, separate from the memory budget: the budget still pauses accepting under pressure (connections wait in the
  backlog) and refuses streams with 0x49 (refuse_admit / refuse_streams). Metrics (`--metrics-interval` line):
  `refuse_conns` (reset at accept), `refuse_limit` (CONNECT over the per-connection cap), and with --max-conns
  `conns_reserved` (exact, unlike `conns`) and `conns_max`. The capability line shows `limits: conns N, streams/conn M`
  when one is set.
- Destination policy (60.20 C1, 40.03 "Destination policy"): host, port and CIDR rules, --block-smtp, --no-direct-ip,
  --no-ipv6-targets; metric `refuse_policy`. Defaults changed in base-5: the server's own interface addresses and IPv6
  forms that embed IPv4 are blocked as targets also with --allow-private (--allow-self / --allow-embedded-v4 lift them).
  The own-address set is read once at startup: an address added later (DHCP, a cloud change) needs a restart, and a
  public IP that is not on an interface (cloud 1:1 NAT, EC2 elastic IP) is not in it: --block-dest it. Host rules match
  the ASCII name as the client sends it (browsers send IDN as punycode `xn--`) and cannot see CNAME chains: hard
  blocks belong in --block-dest. Every client name is resolved as an absolute name (base-5, 60.18 #16): getaddrinfo
  gets `name.`, --dns-own asks the name only, and resolv.conf `search` / `domain` / `ndots` are never applied, so
  `intranet` is never completed to `intranet.corp.example` behind the host rules' back. A short internal name must be
  sent as its full name (`intranet.corp.example`), or be in /etc/hosts (looked up first by both resolvers: Docker
  `--add-host`, Kubernetes hostAliases); Docker container names keep working (Docker's 127.0.0.11 answers `name.`). If the interface addresses cannot be read
  (getifaddrs fails) the server refuses to start unless --allow-self is given. An allowed name never lifts an address class (no DNS-rebinding hole).
- Limits: at memory levels 2-3 (admission off) queued connections are not accepted and get a reset when the listener
  closes. A SYN that completes between the last accept and the close also gets a reset (only the sysctl
  net.ipv4.tcp_migrate_req=1, Linux 5.14+, moves those to another listener; with one process there is none).

## Logging (60.24: --log-level, --log-conns; 60.35: --log-streams)
Everything goes to stderr (journald adds its own timestamp and unit). `--log-level` filters it: `error` prints only fatal
startup errors; `warn` adds every `warning:` line, the kTLS starve line, the KeyUpdate-refused line and memory levels 2/3;
`info` (default) adds the listening, capability, hint, other memory-level, signal / drain / shutdown and metrics lines;
`debug` adds `ev=conn_open` (with `--log-conns`). With the defaults stderr is byte for byte what base-5 printed.

Connection log (`--log-conns`, off by default): one logfmt line per connection that reached the server's event loop:
```text
finalwisp: ev=conn_close ts=2026-11-01T12:00:00.123Z w=3 cid=3:1842 ip=203.0.113.9 via=10.0.0.2 tls=1 proto=v2 auth=none dur_ms=93812 streams=41 refused=2 rx=18234 tx=91823412 why=client_close
```
- `ts` UTC, a few ms resolution; `w` worker thread; `cid` worker:sequence (unique per process run).
- `ip` the client (with `--trusted-proxy`: the client from the header, and `via=` the proxy); `-` if unknown.
- `proto` http (no WebSocket), v1, v2, wsproxy; `auth` none, ok, failed; `streams` CONNECTs that became a stream,
  `refused` CONNECTs refused (policy, limits, memory pressure).
- `rx` / `tx`: **wire bytes** from the kernel (TCP_INFO: received, acknowledged), WebSocket and TLS framing included; not
  the payload of the streams.
- `why`: client_close (the client closed: EOF, WS Close, close_notify, reset), ws_error (bad WebSocket frame),
  protocol_error (not HTTP / not TLS / a bad request / Wisp before INFO / bad version), hs_timeout (no complete handshake
  in time), auth_failed, tls_error (TLS handshake or kTLS failure, AEAD limit), pressure_shed (memory pressure: a shed,
  or a 503 wsproxy upgrade),
  dead_peer (keepalive / peer_gone), limit (a 429 per-IP limit or a 403 policy refusal of the upgrade), server_close
  (shutdown, a finished wsproxy target, a linger timeout, a plain HTTP request answered). The first reason found wins.
- A connection refused at accept (`--max-conns`, `--max-conns-per-ip` direct) never reaches the event loop: it gives
  `ev=conn_refused ts= w= ip= why=limit`, at most 20 lines per second per thread, then one
  `ev=refused_suppressed n=` per second. (A connection the server itself could not set up gives
  `ev=conn_refused ... why=server_close`.)
  60.34 on a PROXY listener also: a peer outside --proxy-protocol-from (`why=protocol_error`, ip = that peer), a bad
  header (`why=protocol_error`), no complete header in 4-6 s (`why=hs_timeout`), and a per-IP refusal after the header
  (`why=limit`, ip = the header's client). A connection closed before sending anything (a load balancer's TCP health
  check) gives no line.
- Lines are written by one log thread (at most 256 KiB queued per worker thread, written every 100 ms). A slow or stalled
  stderr never slows the workers: lines over the cap are dropped and counted (`ev=log_dropped n=`, metric
  `log_dropped`). With a reader such as journald, lines are not dropped at normal rates.
- Privacy: the client IP is logged only with `--log-conns` or `--log-streams`; target hostnames only with
  `--log-streams`. Auth user names, keys and passwords are never logged. Values are escaped (quotes, backslashes, control
  bytes and bytes that are not UTF-8 as `\xNN`; a value with a space or `=` is quoted) so a value cannot fake a line or
  a field, and a line is always valid UTF-8.

Stream log (`--log-streams`, off by default, 60.35; works with or without `--log-conns`, info level like it): one line per
stream (a CONNECT that got a target, TCP or UDP, and a wsproxy connection's target) and one per CONNECT refused before a
target existed:
```text
finalwisp: ev=stream_close ts=2026-11-02T06:46:47.430Z w=0 cid=0:1 ip=203.0.113.9 sid=1 t=tcp host=example.com port=443 dst=93.184.215.14 dur_ms=41 up=517 down=6211 reason=0x02 why=target_close
finalwisp: ev=stream_close ts=... w=0 cid=0:1 ip=203.0.113.9 sid=9 t=tcp host=10.0.0.1 port=80 dur_ms=0 up=0 down=0 reason=0x48 why=policy rule=private
finalwisp: ev=stream_close ts=... w=0 cid=0:1 ip=203.0.113.9 sid=17 t=udp host=1.1.1.1 port=53 dst=1.1.1.1 dur_ms=120 up=15 down=20 dgrams_up=3 dgrams_down=2 reason=none why=client_close
finalwisp: ev=stream_refused ts=... w=0 cid=0:1 ip=203.0.113.9 sid=5 t=tcp host=example.com port=22 reason=0x48 why=policy rule=ports
```
- `cid` matches the connection's `ev=conn_close` line (with `--log-conns`); `sid` the Wisp stream id; `t` tcp, udp or
  wsproxy (`sid=0`); `host` and `port` as the client sent them (escaped); `dst` the address the stream went to (absent if
  it never connected).
- With `--upstream` (60.32) the line has `upstream=1`: `dst` is the proxy, and up/down include the proxy handshake bytes.
- `up` / `down`: TCP: payload bytes from the kernel at close (TCP_INFO: acknowledged by the target, received from it; TLS
  records to the target count as payload); UDP: payload bytes of the datagrams sent / received, with `dgrams_up` /
  `dgrams_down` (a datagram dropped on a full socket buffer is not counted).
- `reason`: the Wisp CLOSE reason the server sent (`0x02` voluntary, `0x03` network, `0x41` invalid, `0x42` unreachable,
  `0x43` timeout, `0x44` refused, `0x47` a network error on the open stream, `0x48` blocked, `0x49` throttled), or
  `none` when the client closed the stream or the connection ended. A wsproxy stream (`t=wsproxy`) has no Wisp CLOSE:
  its `reason` is always `none`, and `why` says what happened.
- `why` (the first reason found wins): target_close (the target ended it, also a network error on the open stream),
  client_close (the client's CLOSE), conn_close (the connection
  ended), dns_fail, connect_fail (`rule=pace_fail`: the 60.30 pacing setup failed), upstream_fail (`rule=connect|timeout|proxy`), policy, limit, pressure, invalid
  (a bad CONNECT: stream type, host). `rule` names the rule for policy (`ports`, `direct_ip`, `ipv6`, `block_host`,
  `allow_host` from the request rules; `no_udp` for a UDP CONNECT with `--no-udp`; `block_dest`, `ipv6`, `loopback`, `private`, `embedded_v4`, `own` from the address
  rules; `ip_form`, `loopback` with `--upstream`), limit (`max_streams_per_conn`, `stream_rate`, `dns_inflight`) and
  pressure (`shed_pend`, `shed_hold`, `l3`, `over_credit`, `stream_cap`, `admission`).
- `ev=stream_refused`: the host as sent, cut to its first 255 bytes (then `host_len=` gives the length sent); at most 20
  lines per second per thread, then one `ev=stream_refused_suppressed n=` per second.
  `ev=stream_close` lines are not rate-limited: they share the 256 KiB queue per thread, and lines over it are dropped and
  counted (`log_dropped`). Expect one line per stream: size the log sink for the stream rate, not the connection rate.

## Metrics (60.12 line, 60.29 Prometheus endpoint)
The counters run always (per worker, at control points only, never per byte). Two ways to read them, both off by
default and usable together:
- `--metrics-interval SECS`: one logfmt `ev=metrics` line on stderr per interval, `ev=metrics_final` at exit.
- `--metrics-listen [ADDR:]PORT`: `GET /metrics` in the Prometheus text format 0.0.4 on its own listener. A bare port
  listens on 127.0.0.1. **No auth and no TLS**: keep it on loopback or a private address (any other address prints a
  warning), or put the reverse proxy's auth in front. It is never on the Wisp port (refused at startup), and a port in
  use exits 2 before the Wisp listener opens.
```yaml
# prometheus.yml (Prometheus on the same host; for a remote one use --metrics-listen 10.0.0.5:9464 and that target)
scrape_configs:
  - job_name: finalwisp
    scrape_interval: 15s
    static_configs:
      - targets: ["127.0.0.1:9464"]   # finalwisp --metrics-listen 9464
```
- The page holds the same values as the line, merged over the threads the same way (sums; `_max` gauges by max):
  counters as `finalwisp_<name>_total` (e.g. `finalwisp_accepted_total`, `finalwisp_refuse_policy_total`), gauges
  without the suffix (`finalwisp_connections`, `finalwisp_streams`, `finalwisp_memory_level`, `finalwisp_ip_keys_max`),
  CLOSE packets as `finalwisp_close_total{reason="0x49"}` (only reasons sent at least once), time at each memory level
  as `finalwisp_memory_level_seconds_total{level="0".."3"}`, `finalwisp_build_info{version=...} 1`,
  `finalwisp_process_resident_bytes`, `finalwisp_metrics_scrapes_total`. Base units only: KiB and ms values of the line
  are converted (`pool_dirty_kib` -> `finalwisp_pool_dirty_bytes`, `ktls_starve_ms_max` ->
  `finalwisp_ktls_starve_max_seconds`). Every family has a `# HELP` line (the counter's description) and a `# TYPE`.
  No per-client or per-destination label, and no secret, address or name, is ever exported (`finalwisp_conns_max` is
  --max-conns).
- One thread answers one scrape at a time; each connection gets at most 2 s in total (a client that sends nothing or
  drips bytes is closed then), a request head over 8 KiB gets 400. A stuck or hostile client can delay the next scrape
  by up to 2 s; the Wisp threads are never involved (the endpoint only reads their counters). Other paths get 404,
  other methods 405, `Connection: close` always.

## Close reasons
Wisp CLOSE (stream level, 10.01):
| reason | when |
|---|---|
| 0x02 voluntary | the target closed (EOF) |
| 0x03 network error | an open stream's socket failed (reset, broken pipe), a UDP send failed |
| 0x41 invalid | bad CONNECT (short, unknown type, port 0, a host that is empty, over 255 bytes, or holds NUL / control / space) |
| 0x42 unreachable | DNS: no such name / no address / lookup failed; no route (ENETUNREACH, EHOSTUNREACH) |
| 0x43 timeout | target connect timeout (--connect-timeout) |
| 0x44 refused | target refused the connection |
| 0x47 data timeout | an open target timed out: keepalive (idle or downloading target, ~180 s, 70.13) or retransmissions (dead target with upload data unacknowledged, ~950 s; 30.14, 30.17) |
| 0x48 blocked | the destination policy: a request rule (port, host, direct IP, IPv6 literal with --no-ipv6-targets), UDP with --no-udp (base-4: 0x41), or every address of the target filtered (loopback / private / own / embedded class, --block-dest, --no-ipv6-targets) |
| 0x49 throttled | memory pressure (no new streams), too many DNS lookups in flight, an upload past its credit and the cap, or a held upload past its hold (20.27) |
| 0x04, 0xc0-0xc2 | (connection level, stream 0) incompatible version, bad password, bad signature, auth required |
WebSocket close codes: 1000 normal (client closed, target of a wsproxy connection ended, handshake refusal), 1001 going
away (shutdown), 1002 protocol error (unmasked or bad frame, bad fragmentation), 1009 message too big, 1013 try again
later (memory level 3, ws:// only, best effort before a reset). Dead peers and memory-pressure sheds get a TCP reset. A TLS
1.3 KeyUpdate on a kernel < 6.14 closes the connection (close_notify) and logs one line per 60 s (60.12).

## Bandwidth caps (60.30 C10a: --download-rate, --upload-rate-per-stream)
Both are kernel TCP pacing (SO_MAX_PACING_RATE): the kernel spaces the packets of one socket, so no per-byte work and
no timers in finalwisp. No fq qdisc and no sysctl is needed (TCP paces itself since Linux 4.13; under fq, fq does it).
- `--download-rate RATE`: per client connection (all its streams share it). Set on each listener before `listen()`; every
  accepted socket inherits it (also `--balance` hand-offs). At startup a loopback self-check confirms that the kernel
  passes it on, else finalwisp refuses to start. A download cap also turns splice off (with splice on, a 10 Mbit/s cap
  split 4 wss streams 0.24-0.43 min/max; off: 0.93) and lowers the client lowat to max(16 KiB, RATE/8), about 125 ms of
  queued data at the cap (a queue bound, not a latency bound): a small reply behind a bulk download at 1 Mbit/s waited
  1.2 s with the 128 KiB default, 0.33 s with it (60.26).
- `--upload-rate-per-stream RATE`: per TCP target (each stream on its own). Set when the target connects, with a target
  lowat of max(16 KiB, RATE/8) so the backlog waits in finalwisp's queue (where the Wisp credit sees it), not ~4 MiB in
  the kernel. With a future upstream proxy (C6) the cap is set before the proxy handshake, so it counts those bytes too.
- Unit: TCP payload bytes per second (Wisp, WebSocket and TLS framing count; TCP/IP headers do not). RATE takes K/M/G =
  KiB/MiB/GiB: 1M = 8.4 Mbit/s, 10M = 84 Mbit/s, 100M = 839 Mbit/s. Range 16K..4095M.
- Precision (60.26, netns + veth): 0.96-1.02 of the cap at 10 and 100 Mbit/s, 0.92-1.05 at 1 Mbit/s over a few seconds.
Limits (what the caps do NOT do):
- UDP upload (U4): not capped. Pacing works on UDP sockets only under an fq qdisc, which is host-dependent; UDP download
  is capped (it leaves on the client's TCP socket). `--upload-rate` (60.25 C10b, section "Upload caps") covers UDP.
- Per IP (U5): there is no per-IP total. "About --max-conns-per-ip x --download-rate per client IP" is a steady-state
  approximation for tracked connections only, not a guarantee: untracked keys (a full table shard fails open), a
  trusted proxy's client without the header (not charged) and the unpaced start of every connection exceed it.
- Start of a connection (U6): the first 10 TCP segments are not paced (about 14 KB on a 1500-byte link; up to 640 KB
  over loopback to a local reverse proxy, which then forwards them at its own speed).
- Upload under a download cap (U8): CONTINUE and the credit pings travel on the paced client socket behind data
  already queued, so the same connection's upload slows down too (measured 10-27x the download cap at 1 and 10
  Mbit/s; nothing stalls). A remedy would have to send control frames between data frames sooner or shrink frames.
- Close tail at low rates: data still queued when a client closes drains at the cap; at 16K-64K the tail can outlast the
  10 s kTLS linger and is then cut, as for any slow client.
- Memory: a capped client is a slow reader; its data waits in the targets' sockets and the output queue up to the stage
  limits, as for a slow link. The memory budget (above) bounds it.
- Behind nginx/Caddy (TLS at the proxy): the cap applies to the proxy -> finalwisp socket of each WebSocket, so it still
  caps each client; through a local proxy the loopback MTU makes pacing coarse (64 KiB steps).
- Unix-socket clients (C7, later): pacing has no effect on unix sockets.
- CPU: TCP internal pacing uses one high-resolution timer per paced packet; with many capped connections an fq qdisc on
  the egress device batches this (optional, the server never changes qdiscs).

## Upstream proxy (60.32 C6: --upstream, --upstream-trust-dns)
Every TCP stream goes through one SOCKS5 (RFC 1928, RFC 1929 user/pass) or HTTP CONNECT proxy; flag details 40.03
"Upstream proxy". The parity reference is wispurr's `proxy` key (60.27).
- What still runs locally: DNS for target names, the destination policy and the address rules (60.21), the stream caps
  and memory admission. Only an allowed IP literal goes to the proxy. `socks5h://` (with the required
  `--upstream-trust-dns`) lets the proxy resolve names: the address rules then cannot see where a name points
  (startup warning). Use it only when the proxy must resolve (a Tor-like or split-DNS proxy).
- The proxy's own address: a name is resolved at startup (getaddrinfo, with the resolver's search list, so a Docker
  service name works) and every 30 s on the `upstream-dns` thread; a failed refresh keeps the last list. There is never a
  fallback to direct egress. The proxy address itself is not checked by the address rules: it is the operator's choice
  (a proxy on 127.0.0.1 works without --allow-loopback).
- Credentials: put the URL in a `--config` file with mode 0600 (a group/world readable file that holds it gets the C8
  warning; on the command line it is visible in /proc/PID/cmdline, a warning too). Both SOCKS and HTTP Basic send them in
  clear text to the proxy (a warning at startup). Logs and errors show the URL as `scheme://***@host:port`.
- Not over the proxy: UDP (CLOSE 0x48, the UDP extension is not advertised), TFO, TLS to the proxy (`https://` is
  refused at startup). The handshake shares the stream's --connect-timeout (proxy connect + handshake + the proxy's
  connect to the target + retries); a stalled proxy ends the stream with 0x43.
- Data path: after the reply the stream is a plain target socket (splice, kTLS on the client, upload batching and
  `--upload-rate-per-stream` on the proxy socket, applied before the handshake). Measured: a 32 MiB download through
  each proxy type uses splice (60.27 evidence).
- Metrics: `upstream_ok` (handshakes completed), `upstream_fail` (the proxy itself failed: unreachable, closed, broken
  reply, auth refused, deadline; a refusal about the target, e.g. SOCKS REP 05, is not counted). Close reasons:
  40.03 "Upstream proxy".
- Tested proxies (60.32, Debian 13): microsocks 1.0.5 (with and without auth), OpenSSH 10.0 `ssh -D`, tinyproxy 1.11.2
  (Basic auth), squid 6.13.

### Tor upstream (tested: the base-6 RC2 fix build, Tor 0.4.9.15, Debian 13, 2026-11-03)
```
apt install tor                      # SocksPort 127.0.0.1:9050 by default
finalwisp 6001 --upstream socks5h://127.0.0.1:9050 --upstream-trust-dns --connect-timeout 30
```
- `socks5h://` + `--upstream-trust-dns`: Tor resolves every name at the exit, and finalwisp makes no DNS query at all
  (strace -f -e trace=network and tcpdump port 53: 0 calls, 0 packets for http and https streams). IP literals and
  loopback names are still refused locally (0x48). A name the exit cannot resolve gets 0x42.
- `socks5://127.0.0.1:9050` also works, but DNS then goes out from this host (seen in tcpdump): the resolver sees
  every target name. Use socks5h for Tor.
- `.onion` works with socks5h (http://<56 chars>.onion, 200 OK through Tor): the name goes without the absolute-form dot
  (Tor refuses `x.onion.`; base-6-rc1 had that bug: 0x42 for every onion service, fixed in RC2, 60.32 #9). With
  socks5:// a .onion fails (no local address, 0x42).
- `--connect-timeout 30` (default 10): the timeout covers proxy connect + Tor's whole circuit and target connect.
  Measured first-stream times: after `systemctl restart tor` 0.2-1.4 s, once 6.7 s; a .onion's first connect
  2.3-8.8 s; with an empty DataDirectory, streams sent 1 s after Tor started: at most 3.1 s (Tor holds them until it
  has bootstrapped). Tor retries a stalled stream on a new circuit after 10-15 s, and some sites are slow over Tor (one
  site: 20-52 s, and 0x43 at the 10 s default): 10 s ends a stream before Tor's first retry.
- Tor stopped: new streams get 0x44 at once (connection refused, `upstream_fail` counts each), open streams end with
  0x02, finalwisp keeps running; the first stream after `systemctl start tor` (cached state) worked 0.8 s later, and a
  stream right after `systemctl restart tor` worked. No finalwisp restart is needed.
- UDP: CLOSE 0x48 (Tor carries no UDP; the UDP extension is not advertised).
- All Wisp clients share Tor's circuits: Tor isolates streams by SOCKS credentials (IsolateSOCKSAuth) and finalwisp
  sends one set (none here).


## Upload caps (60.25 C10b: --upload-rate, --upload-rate-per-ip)
finalwisp stops reading a client that is over its allowance; the client's TCP receive window closes and its sender
waits. No sysctl, no qdisc, nothing dropped or refused.
- `--upload-rate R[/B]`: per client connection (all its streams: TCP, UDP, wsproxy). Counted: every byte read from the
  client socket after the TLS handshake (WebSocket and Wisp framing included). Burst B (default max(R, 16K)) is what an
  idle connection may send at once; B >= R/10 because a paused client is resumed on the 100 ms timer tick.
- `--upload-rate-per-ip R[/B]`: shared by one client key (IPv4 /32, IPv6 /64). Each connection leases a share of the
  key's bucket (50 ms of R divided by the key's connections); while any connection of the key waits, the bucket serves
  them in order (a starved-first queue: none can be starved by a busier sibling; shares are rough, not equal:
  connections of one key on different threads split 0.25-0.5 / 0.5-0.75 on loopback). Behind a reverse proxy this needs
  `--trusted-proxy` (or `--listen-unix`), else all clients share the proxy's key; bytes read before the client's header
  is known are charged to its key once it is. A full table shard (IPv6 /64 rotation) leaves new keys untracked: no
  per-IP cap for them (fail open, 60.18 #17); `--upload-rate` and `--max-conns` still apply.
- Metrics: `rx_bytes` (always counted: bytes read from clients), `upl_pauses` (times a client was paused),
  `upl_ip_waits` (of those, because of the per-IP bucket or queue).
What to expect:
- All streams of a limited connection wait together: a small request behind a bulk upload on the same connection waits
  for the bytes ahead (head-of-line, as on a slow link). Downloads are not affected (see --download-rate).
- A credit-v2 pong queued behind upload waits too: at low rates the credit window falls back to the base rule for a
  while (no error).
- A limited client that hangs up is still read at its rate until EOF (the cap adds no input drop); at EOF the
  connection closes as without a cap.
- The stall shed at memory level 2+ (70.08) skips a client the cap paused in that interval; the holder rule and level
  3 still bound memory.
- The handshake deadline (8-10 s) applies to limited clients too; B >= 16K lets an upgrade through at once.
- Cost: none measurable with both flags off (60.25 A/B). With a cap set, per-connection: none measurable; per-IP:
  none measurable after the lease top-up (60.25 "Merged A/B": the merged build lost 13% of upload 10x10 to reads
  split at the lease edge; the top-up gives back 1.15x, 2 vCPU). A connection may hold up to 512 KiB of its key's
  bucket while nobody waits on the key.

## Memory: cgroup and budget (20.26, 60.17)
Budget (startup, the capability line shows it):
- In a cgroup with a memory limit (systemd MemoryMax=, docker --memory, a pod limit) the budget is that limit; usage =
  memory.current - inactive_file (v2) or memory.usage_in_bytes - total_inactive_file (v1). Nothing to configure.
- No limit: budget = MemTotal/2. --mem-budget BYTES sets the budget (the usage source stays); `--mem-budget 0` = off.
  Usage without a limit (Host mode) = our heap plus socket memory:
  - **HostSock (60.17, the usual case):** our own cgroup v2 `memory.stat` line `sock` (every socket this process owns,
    TCP and UDP), read at most every 5 ms, above an idle baseline. Needs cgroup v2 with the memory controller on our
    cgroup (memory.current exists there; not the root cgroup), socket accounting on (not `cgroup.memory=nosocket`) and a
    readable /proc/cmdline (unreadable = Host mode: the server cannot tell that accounting is on).
    Capability line: `usage = heap + our socket memory, <dir>/memory.stat sock`.
  - **Host (fallback):** the host-wide TCP memory (/proc/net/sockstat) above its level at startup / while idle. Every
    TCP-heavy process on the host then counts.
- **Run finalwisp in its own cgroup** (a systemd unit or `systemd-run --scope`, its own container) to get the HostSock
  benefit: with a neighbour filling ~120 MiB of host TCP memory (200M budget, upload 10x10), the server in its own
  scope stayed at level 1 (its floor) with 0-24 MiB used; counting host-wide it reached level 2 in 3 of 4 runs with
  87-130 MiB (60.17 P3 (a), VPS1 and VPS2). In a cgroup shared with
  other processes (an ssh session scope, a container with sidecars) `sock` holds their TCP and UDP sockets too (not
  other cgroups'): with the bench in the same session scope it tracked the host-wide count within a few MiB (60.17).
- **CPU fair share:** when the cpu controller is on for the parent cgroup, a cgroup of its own also gets its own CPU
  share (cgroup v2 cpu.weight, default 100) next to its sibling cgroups, instead of sharing one with the processes it
  was started with. Under CPU contention the split changes: 60.17 saw VPS2 loopback upload 10x10 (256M) at 1498-1715
  MiB/s with the server in its own scope vs 1596-1771 for the same build in the bench's session scope (1736-1845 for
  the old build there; n=4, not a gate; VPS1 equal). Set CPUWeight= if the server needs a bigger share.
- Not counted: the host's own TCP memory pressure (net.ipv4.tcp_mem is one counter for all sockets): that is opt-in
  --tcpmem-adapt (20.31 B3). With cgroup v1 (no socket accounting by default) Host mode stays host-wide. Sockets created
  before the process moved cgroups stay with the old cgroup; connections waiting in the listen backlog are charged when
  accepted.

Levels (per mille of the budget; up at once, down after a dwell):
| level | enter / exit | what changes |
|---|---|---|
| 0 | - | normal |
| 1 | 500 / 400 | smaller queues and credit; socket buffer requests capped (setsockopt sizes; the kernel doubles them): 32 KiB, target send 40 KiB, client receive 32 KiB or 128-256 KiB and client send 64 or 128 KiB by the per-worker budget |
| 2 | 700 / 600 | tighter queues; no new connections or streams (0x49, accept paused); client receive 32 KiB |
| 3 | 850 / 750 | clients with an upload backlog are not read; streams holding over 1 MiB of unsent upload are shed; with no progress for 2 sweeps the clients holding the most memory are closed (ws:// gets 1013 when nothing is queued, then a reset) |
It sheds instead of meeting the OOM killer.
- Small budgets: below 256 MiB (SMALL_BUDGET) the server starts and stays at least at level 1 ("small: level 1 from the
  start"): at level 0 a download burst grows memory from 1 to 32 MiB in ~25 ms, faster than any sampler (20.26). A
  128 MiB level-0 start was tried in base-4 and rejected: on a 1-vCPU VM it refused up to 300 streams and reached level
  3 (60.17 P2). In base-4 an upload at level 1 is much faster than before: target send buffer 40 KiB at level 1 (200M
  budget, upload 1x1 x4.92 on VPS1 / x2.99 on VPS2, 10x10 x1.58 / x1.73; 128M 10x10 x1.08 / x1.23; 60.17 step B and
  merge-gate fix). 40 KiB keeps a level-1 stream at 144 KiB of kernel memory: a 32 MiB worker still admits 113 streams.
- Flap damping (60.17 Dwell): a level steps down 250 ms after the last change. A step back up within 2 s of a step down
  from that level is a flap and doubles the wait before the next step down from it, up to 4 s; 10 s of calm resets it.
  1-vCPU VM at 128M (a test build that started 128M at level 0, rejected as P2), upload 10x10: 107-113 level changes
  -> 17; a noisy neighbour around the level-1 exit (unit test, 30 s): 185 -> 21. A neighbour in the same cgroup still moves the levels; damping only slows the flapping.
- Set MemoryMax= (or --mem-budget) to what the server may use. Memory per idle connection (70.25 own buffer allocator, the
  default build): ~1-3 KiB userspace (0.9-1.2 on servers from 2000 to 100k connections, 3.1 on a 16-thread laptop at
  2000 where the per-thread fixed part is a bigger share; the old glibc build: 4.7-4.9 at 2000 and 5-60 at 40k-100k)
  + ~8 KiB kernel; per busy stream up to its socket buffers (tcp_rmem/tcp_wmem).
- Own allocator notes (70.25): VSZ is 35-40% higher than the glibc build (4 MiB chunks; address space only, not RSS):
  with RLIMIT_AS (ulimit -v) size it from VSZ, the pool takes at most 1/16 of it and glibc serves beyond. After a big
  connect or data burst RSS can stay up to +20-50% above the glibc build for ~10 s, so the VmHWM peak is that much
  higher (it does not fall back): freed buffers wait in the per-worker dirty set and are released in bounded batches (8 MiB per loop turn) so no client sees a long stall.
  There is no build without it since 60.18 #11 (base-4's `NOFEAT=1` build was the last; tag base-4).

## Reverse proxy (TLS at the proxy, ws:// to finalwisp on 127.0.0.1)
Use this when the kernel has no kTLS, for KeyUpdate on kernels < 6.14, or to share port 443. Cost: the proxy copies
every byte through userspace (finalwisp's own kTLS + splice path is faster).
Idle timeouts: finalwisp itself never closes an idle Wisp connection (dead peers only, by TCP keepalive at ~180 s;
keepalive probes are not data, so a proxy does not see them) and sends no WebSocket pings. Proxies have their own
timers: nginx closes the connection after proxy_read_timeout (default 60 s) with no data from finalwisp, even while the
client keeps sending; Caddy sets none by default; Cloudflare is commonly reported to close idle WebSockets after
~100 s (community reports; its docs give no number). Raise the proxy timeout, or have clients send traffic.

nginx (tested in 40.02):
```nginx
map $http_upgrade $connection_upgrade { default upgrade; '' close; }
server {
    listen 443 ssl;
    server_name wisp.example.com;
    ssl_certificate     /etc/letsencrypt/live/wisp.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/wisp.example.com/privkey.pem;
    location / {
        proxy_pass http://127.0.0.1:6001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;   # default 60 s cuts idle Wisp connections
        proxy_send_timeout 3600s;
        proxy_buffering off;
    }
}
```
Caddy (tested in 40.02): `wisp.example.com { reverse_proxy 127.0.0.1:6001 }`. Caddy proxies WebSocket upgrades and
sets no idle timeout. On a config reload Caddy closes proxied WebSockets (1001); `stream_close_delay` keeps them open that much longer:
```caddy
wisp.example.com {
    reverse_proxy 127.0.0.1:6001 {
        stream_close_delay 5m
    }
}
```
Cloudflare: WebSockets are proxied; see the idle note above.

Client IP behind the proxy (60.20 C2, 60.22): without it every client is the proxy's address, so per-IP limits
(--max-conns-per-ip, --stream-rate-per-ip) would lock everyone out together; do not use per-IP limits behind a proxy
without it. Start finalwisp with `--trusted-proxy 127.0.0.1` (the proxy's address as finalwisp sees it; a list of
CIDRs). Only a peer in that list may name the client; from any other peer the header is ignored. Every address inside
--trusted-proxy may name any client, so list only the proxies (not a range that also holds clients). One header is read:
X-Forwarded-For by default, walked right to left (trusted hops skipped; the first other entry is the client, so an
entry the client wrote itself on the left does not count). nginx: add
`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` (appends the peer), or
`proxy_set_header X-Real-IP $remote_addr;` with `--real-ip-header x-real-ip` (one value; several lines of it count as
unparsable). Caddy sets X-Forwarded-For itself. RFC 7239 `Forwarded` is not supported (nginx and Caddy both send XFF).
An unparsable header makes the last trusted hop the client (metric realip_bad: those clients share one key); no header
means no per-IP limit for that connection (realip_missing). A proxy's connection is counted only after its HTTP
request; before that only --max-conns and the handshake timeouts bound it. Over --max-conns-per-ip a proxied client gets
`429 Too Many Requests`; a direct client is reset at accept.

Unix socket between the proxy and finalwisp (60.31 C7): `--listen-unix /run/finalwisp/wisp.sock` adds a second
listener on that path (the TCP one stays; bind it to 127.0.0.1 or a port nobody reaches if only the proxy should
talk to finalwisp). No TCP port to guard, and no loopback TCP in between. The socket is always plain ws://.
- Who may connect = who may write the socket file: mode 660 by default (`--unix-mode`). finalwisp has no group flag:
  give the directory the proxy's group. systemd: `RuntimeDirectory=finalwisp`, `RuntimeDirectoryMode=2750` and
  `Group=www-data` (the service runs with that group, the directory is setgid, so the socket gets the group and mode
  660 lets the proxy in). Without systemd: `install -d -m 2750 -o finalwisp -g www-data /run/finalwisp`.
- Its clients are trusted like a --trusted-proxy without listing anything: their X-Forwarded-For (or --real-ip-header)
  is the client IP (`ip=1.2.3.4 via=unix` in --log-conns); no header = the client is `unix` (not limited per IP).
  So only a proxy that sets the header itself may reach the socket (nginx `$proxy_add_x_forwarded_for`, Caddy by default).
- Startup: `PATH.lock` beside the socket is flocked (a second finalwisp on that path exits 1); a leftover socket that
  nobody listens on (a crash) is replaced; a live one or a non-socket is refused. A clean shutdown removes the socket
  (not the .lock file). Give it a path no other program uses: a socket another program bound but did not listen on yet
  counts as leftover.
- Not on unix clients (no TCP): --download-rate (startup warning), dead-peer detection and the stall shed (a local
  proxy that dies closes its socket), kTLS. New connections on it go to the least loaded thread always (one shared
  socket: the kernel does not spread them like SO_REUSEPORT).

nginx: `proxy_pass http://unix:/run/finalwisp/wisp.sock;` (the rest of the block as above). Caddy (tested in
tests/compat/unix.py): `wisp.example.com { reverse_proxy unix//run/finalwisp/wisp.sock }`.

PROXY protocol behind a TCP load balancer (60.34): an L4 balancer (AWS NLB, HAProxy in `mode tcp`, a TCP-passthrough
nginx `stream {}`) can put the client's address in a PROXY protocol header in front of the connection. Turn it on per
listener: `--proxy-protocol tcp --proxy-protocol-from 10.0.0.0/16` (the balancers' addresses), or `--proxy-protocol
unix` (HAProxy `server fw unix@/run/finalwisp/wisp.sock send-proxy-v2`). Then:
- Every connection on that listener must start with the header (v1 or v2, at most 4096 bytes, within 4-6 s); without
  it the connection is reset. So turn it on only where every client comes through the balancer, and turn it on at the
  balancer at the same time (AWS NLB: target group attribute `proxy_protocol_v2.enabled`; HAProxy `send-proxy-v2`;
  nginx stream `proxy_protocol on`).
- Only peers in --proxy-protocol-from may send it on TCP (others: reset at accept). List only the balancers, not a range
  that also holds clients: anyone in it can claim any client address. An NLB with client-IP preservation connects from
  the client's own address; there the list must be 0.0.0.0/0,::/0 (a startup warning) and the security group is the
  guard: let nothing but the NLB reach the port.
- The header's source is the client: per-IP limits are charged after the header, --log-conns shows it. TLS still ends
  in finalwisp (the header comes before the ClientHello). Health checks: a LOCAL header (NLB, HAProxy `check-send-proxy`)
  or a plain TCP connect-and-close both work (the first is the balancer itself, the second gives no log line).
- With a CDN or an HTTP proxy in front of the balancer, also list that hop in --trusted-proxy: its X-Forwarded-For then
  names the client (PROXY decides who the peer is, X-Forwarded-For refines it only for a trusted peer).
