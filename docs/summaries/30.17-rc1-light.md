### Heap check follow-up: no leak (2026-11-01; branch archive/leak-dhat 1220e8d, not merged)
- mmapped row = glibc 2.43 statistics drift, not memory. 2.43's `mremap_chunk` adds `new_size - size - offset` to
  `mp_.mmapped_mem`, but its new mmap layout makes chunksize = mmap size - offset - 16 (`mmap_set_chunk`), so every
  mremap of an mmapped chunk counts +16 B that munmap never subtracts (still so in glibc master). Our M_MMAP_THRESHOLD is
  16 KiB (mem.rs `MMAP_THRESHOLD`; the ">= 128 KiB class" above is wrong), so every System Vec growing past 16 KiB is a
  realloc -> mremap. Checks: all 28 per-cycle mmapped deltas of A and of B are multiples of 16 (never whole pages,
  though mmapped chunks are pages); a static C test against 2.43 (40 realloc growths, then free) leaves hblks 0 but
  hblkhd 640 = 40 x 16. A +720 B/cycle = ~45 mremaps per cycle. Upstream bug note: later, not public without the maintainer.
- Heap profile (feature dhat-heap: Counting's System path through dhat::Alloc, pool path unchanged; VPS1, cycle.py,
  profile from the floor of cycle 3 to the floor of cycle 13; run clean). Blocks allocated in cycles 4-13 and still
  live at floor 13: A 9,774 B in 27 blocks, B 9,106 B in 23 blocks (whole window, not per cycle). Every site is
  peak-concurrency capacity of a long-lived worker container (doublings): dns_cache HashMap + keys (capped 4096),
  the connecting / ready / dirty / dead Vecs, the Slab free list (worker/mod.rs Slab::remove), the std DnsReq channel
  block, one mpmc context per DNS thread. No site grows by a cumulative count.
- tcache test (release fw 6b7a1c30, `GLIBC_TUNABLES=glibc.malloc.tcache_count=0`, cycle.py 14 cycles + malloc_info;
  run clean): arena in-use flat.

| KiB (Theil-Sen per cycle, c2-14) | A heap1 | A tcache 0 | B heap1 | B tcache 0 |
|---|---|---|---|---|
| arenas in use / cycle | +3.99 | +0.42 | +5.62 | +0.78 |
| arenas in use, floor 3 -> 13 | +41.1 | +4.7 | +57.2 | +12.2 |
| arenas in use, floor 13 -> 14 | +0.2 | +0.1 | +4.1 | +0.2 |
| arenas free / cycle | +3.66 | +2.62 | +1.11 | +3.11 |
| arenas system / cycle | +7.71 | +3.0 | +8.50 | +4.0 |
| cgroup anon at the floor / cycle | +18.6 | +16.0 | +16.2 | +12.0 |

- Verdict: no leak. The arena in-use growth was freed chunks held in the worker threads' tcache (malloc_info counts
  them as in use); without tcache the residual (A 4.7, B 12.2 KiB over 10 cycles, ~0 by cycle 14) matches dhat's
  ~10 KiB of live peak capacity. The mmapped growth is the 2.43 counter drift (it stays with tcache off: +723 / +339
  B/cycle). Not closed by this: the early cgroup-anon slope (+12-16 KiB/cycle in cycles 2-14) is the same with tcache
  off, so it is not allocator in-use; heap1 / LIGHT 1 show it falling later (c15-28 +5.7 / +6.0). 14 cycles cannot show
  its plateau.
