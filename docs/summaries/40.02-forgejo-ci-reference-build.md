## Does a CI build lose "system-level optimization"? No: it is the same binary, byte for byte
- The release has no host-specific codegen: no target-cpu=native, no RUSTFLAGS from the environment (release.sh ignores
  them on purpose), generic x86-64, fat LTO + codegen-units 1 from Cargo.toml. So where it is compiled cannot change the
  machine code; only the inputs can: source, toolchain (pinned, rust-toolchain.toml), and the build image's gcc / binutils /
  glibc static archive (recorded in BUILDINFO: cc, ld, glibc).
- Before 40.02 the binary also embedded build PATHS (repo dir, ~/.cargo, sysroot: 434 strings, panic locations + debug info),
  so two hosts gave different md5s for the same commit. release.sh now remaps them (/finalwisp, /cargo, /rust) and
  rust-toolchain.toml installs rust-src everywhere (with rust-src rustc rewrites std's /rustc/<hash>/ paths to the sysroot,
  without it it does not: the first container build differed in .data.rel.ro + debug info for that reason only; .text size
  was already identical).
- Proof (df40938): laptop (Ubuntu 26.04, ~/..., CARGO_BUILD_BUILD_DIR cache) and a fresh Incus ubuntu/26.04
  container on the build host (fresh rustup, user b, other paths): md5 a56e668e619592321cdc7ce66365edf1 both. Same bytes => same
  performance; no benchmark is needed to compare them. Third check: the first fast-lane CI run
  (ab86faf, task 21: fmt, clippy, 68/68 tests, job succeeded) printed md5 a56e668e too. A different glibc/gcc in the build image WOULD change the bytes:
  BUILDINFO shows it, and the release lane pins ubuntu:26.04.

## Lanes
- `ci.yml`, fast lane (`runs-on: docker`, container ubuntu:26.04, rustup + cargo in /ci-cache/finalwisp): every push:
  cargo fmt --check, clippy -D warnings, cargo test --release, bench/release.sh (prints the md5 + BUILDINFO). From 70.25
  round 5 to base-4 clippy and cargo test also ran with --no-default-features (the old allocator path); 60.18 #11 removed
  that path and lane, and added clippy --features pooltest (test-only, so mem::pt cannot bitrot; 60.16 S15).
  Not in CI: wst compat (kTLS, netns, root, docker-in-docker, real-client node tests), fuzz campaigns, any timing. A red run
  alerts #buildbox-reporting (r7alert), so only stable steps belong here.
- `release.yml`, clean lane (`runs-on: clean`, fresh VM per job, no caches): on tags base-* / v* and by hand: the independent
  reference build + artifact (finalwisp + BUILDINFO). Before publishing a release: its md5 must equal the laptop's
  release.sh md5 of the same commit; a mismatch must be explained (build image drift) first.
- Found by the first container run: dns::tests::files_reload_on_change wrote a same-size file within one mtime tick
  (not detected on the container fs); test fixed (5b655c9). Product note: change detection is mtime/inode/size, editors
  replace files (new inode), so real edits are seen.

### Tarball + SHA256SUMS on a draft Forgejo release (release.yml, clean lane, tags base-* / v*)
- After the reference build, `bench/package.sh VER pkg` packs `finalwisp-VER-x86_64-linux.tar.gz`. It has one top
  directory with `finalwisp`, `BUILDINFO`, `README.md` and `LICENSE*`/`COPYING*` (the repo has none today).
  `SHA256SUMS` lists the tarball and the binary at its path inside the tarball. `sha256sum -c SHA256SUMS
  --ignore-missing` checks a download; after `tar xf`, plain `sha256sum -c SHA256SUMS` checks the binary too.
- package.sh refuses a build that does not match the checkout: the BUILDINFO md5 must be the binary's, the git commit
  must be HEAD, and the build must not be dirty. The tar has sorted names, owner 0:0 and the commit time as mtime, and
  it is compressed with `gzip -n`. Because BUILDINFO holds the build date, two builds of one commit give two different
  tarballs, but the binary inside has the same md5.
- `bench/forgejo_release.sh TAG pkg BUILDINFO` uses the job token (`secrets.GITHUB_TOKEN`, enough for releases and
  assets; it cannot write packages). It creates a DRAFT release named "finalwisp TAG", with BUILDINFO in the body and
  a note to check the md5 before publishing. Then it uploads the two assets. A rerun reuses the DRAFT of the tag,
  replaces assets with the same name and refreshes the body. A published release is never changed (exit 1). The
  release search follows pagination. Not serialized: two runs for one tag at the same time could mix assets (a tag is
  pushed once). Publishing stays a hand step: the binary's md5 must equal the laptop's
  `bench/release.sh` md5 of the same commit (section "Lanes").
- Workflow-dispatch runs (no tag) build and package, named `g<commit>`, but create no release.
- Tested 2026-11-03 on a throwaway branch and tag (pkg-test1, v0.0.0-pkgtest1, both deleted after, and the release
  too). Run 320 succeeded: it created draft 52 and uploaded the tarball (4257033 B) and SHA256SUMS (227 B). I pulled
  the stored attachment files from Forgejo's data dir: both SHA256SUMS checks pass, and the binary in the asset has
  md5 681fdd8e, the same as the laptop's release.sh for this source. Runs 314 and 317 failed (they were alerted to
  #buildbox-reporting) because the job token cannot download attachments: the web route `/attachments/<uuid>` and
  `/releases/download/...` return 404 for it in a private repo, even after the release is published. A check of
  uploaded assets must therefore run as a user (a PAT) or read Forgejo's storage, as here. After the reviewer B review,
  run 325 (throwaway pkg-test2 / v0.0.0-pkgtest2, deleted after) tested three paths: create the draft (53), a rerun
  that reused draft 53 (2 assets, not 4; body with the md5), and a rerun after publishing, which was refused (exit
  1). package.sh gave the same tarball md5 under umask 077 and 022.

### Container image (contrib/docker/Dockerfile; no image pushed anywhere)
- `FROM scratch`: the static binary (0555) and BUILDINFO, `USER 65532:65532` (numeric, because scratch has no
  /etc/passwd), `EXPOSE 6001`, `STOPSIGNAL SIGTERM`, `ENTRYPOINT ["/finalwisp"]`, `CMD ["--host", "0.0.0.0", "--port",
  "6001"]` (inside a container the default 127.0.0.1 is unreachable from a published port). No shell
  (`docker exec ... /bin/sh` fails: "no such file"). Image size 13.8 MB (the binary).
- Build context: the release tarball's top directory (or the release dir). Run:
  `docker run -d --name finalwisp -p 6001:6001 --stop-timeout 35 --memory 1g finalwisp:VER`.
  `--stop-timeout` must be longer than --drain-timeout + 2 s; the defaults are 30 s drain and 10 s docker stop.
  Passing arguments replaces CMD, so repeat `--host 0.0.0.0 --port 6001`.
- Nothing else is needed in the image. Hosts lookups use built-in files+dns, which read the /etc/hosts and
  /etc/resolv.conf that docker mounts. The memory budget reads the container's cgroup v2 limit: the capability line
  showed `memory budget 1024 MiB (cgroup limit /sys/fs/cgroup/)` with `--memory 1g`. wss:// needs `modprobe tls` on
  the host, and the cert pair must be mounted readable by uid 65532.
- Tested 2026-11-03 in the Coder workspace fwpkg on the build host (Debian 13, kernel 6.12, Docker; functional only, no
  timing):
  - the image runs as uid 65532;
  - wbench rr (4 conns x 4 streams) and echo through the published port to a target on the docker host: 0 errors;
  - `docker stop` with 2 busy downloads and `--drain-timeout 5` took 5.46 s: the clients got 1001 and the container
    exited 0.

### aarch64: feasibility only (not built)
- Code: one arch-specific path, ws.rs unmask, which has an AVX2 fast path behind `cfg(target_arch = "x86_64")` and
  falls back to the portable loop (autovectorised to NEON). The rest is libc and Linux syscalls through the `libc`
  crate (`TCP_INFO` offsets, `SO_*`, `splice`, `TCP_ULP` are the same numbers on arm64). Check: pool.rs assumes
  `PAGE = 4096`, and 16K or 64K page kernels exist (some Ampere/RHEL arm64 builds, Apple-silicon VMs). The pool
  already falls back to glibc on a page size other than 4096 (60.16), so it works there, only without the own
  allocator.
- Build: target `aarch64-unknown-linux-gnu` with `+crt-static`. Static glibc cross-builds need an aarch64 glibc
  >= 2.34 (static archive) and a cross gcc/binutils. On ubuntu:26.04: `gcc-aarch64-linux-gnu`,
  `libc6-dev-arm64-cross`, and `CARGO_TARGET_AARCH64_UNKNOWN_LINUX_GNU_LINKER`. release.sh needs a TARGET variable
  and the `CFLAGS_<target>` remap; BUILDINFO already records the target. Reproducibility then depends on the cross
  toolchain packages (recorded like cc/ld today). A native build on an arm64 host is simpler but needs that host.
- Kernel features: kTLS (TLS_TX/RX, AES-GCM and ChaCha20 have arm64 crypto acceleration), splice, TFO and
  SO_MAX_PACING_RATE are generic net code, so they are the same on arm64 at the same kernel versions. Graviton
  (AL2023 6.1, Ubuntu 24.04 6.8) and Ampere hosts run them. `tls` must be loadable, as on x86.
- Testing: no arm64 runner exists (the build host is x86_64). Unit tests could run under qemu-user (binfmt) in the clean
  lane, but kTLS, splice and the compat suite need a real arm64 kernel: a rented Graviton or Ampere VM for the compat
  run, and for any timing.
- Effort estimate: cross build + release.sh TARGET + package/Dockerfile per arch about 0.5-1 day; a qemu-user
  `cargo test` lane about 0.5 day; a compat run on a rented arm64 VM about 0.5 day (plus the rental). The pool on
  16K-page kernels (a `PAGE` from sysconf) is optional, about 1 day with an A/B. Total about 2-3 days, with low risk
  in the code itself.
