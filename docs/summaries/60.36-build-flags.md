# 60.36 Self-build optimization flags: measured, no gain (exact steps kept) (finalwisp base-6-rc1 f4202b2c, rustc 1.100.0-nightly f248f4038, LLVM 23.1.1)

Builds use bench/release.sh with one change: its RUSTFLAGS line gets `${BF_FLAGS:-}` appended
(`sed 's|RUSTFLAGS="-C target-feature=+crt-static $remap"|RUSTFLAGS="-C target-feature=+crt-static $remap ${BF_FLAGS:-}"|'`).
With BF_FLAGS empty the build is byte-identical to the release (md5 681fdd8e).

PGO:
1. `rustup component add llvm-tools` (inside server/, so the pinned toolchain gets it); llvm-profdata is then
   `$(rustc --print sysroot)/lib/rustlib/x86_64-unknown-linux-gnu/bin/llvm-profdata` (LLVM 23.1.1, matches rustc).
2. `BF_FLAGS='-Cprofile-generate=/tmp/fwpgo' bench/release-bf.sh` (static-pie; the profiler runtime is built in).
3. Training on the target box (pgo-train.py, ~2 min): `LLVM_PROFILE_FILE=<dir>/fw-%p-%m.profraw ./finalwisp
   --allow-loopback --port 6901` [plain, then again with --tls-cert/--tls-key], wbench 10x10 for 12 s each: rr, churn,
   connchurn, download, upload (plain); rr, connchurn, download, upload (wss). The server must exit normally (SIGTERM
   shutdown) for the .profraw to be written.
4. `llvm-profdata merge -o merged.profdata *.profraw`.
5. `BF_FLAGS='-Cprofile-use=/abs/path/merged.profdata' bench/release-bf.sh`.
The profile path is not remapped, and the profile itself is an input, so a PGO build is reproducible only with the
same .profdata file.

## Results (VPS2, AMD EPYC-Milan, 2 vCPU, 2026-11-02)
Counters: perf stat -p on the server, 5 s per run, 8 rounds × 3 tests × 5 variants, rotated order. Ratio = variant/base
per unit (connection, request, MiB), paired per round; median shown. Base per unit: connchurn user 21.3k / kernel 211k
instructions, cycles 430k; rr user 1.5k / kernel 21.6k; download user 4.4k / kernel 492k per MiB. The kernel does

NAT upload 10x10 (n=16 watch 0.962): n=32 0.999 tie. PGO+V3 echo 1x1 (n=16 watch 0.967): n=32 1.01 tie.

Verdict: none of them is worth a release or a recommendation. PGO cuts user instructions by 9-11 % (PGO+V3 by
11-12.5 %) on connection- and request-heavy work, but user code is only 1-9 % of the instructions, so cycles and
throughput do not move measurably on VPS2 (all ties after n=32). target-cpu=x86-64-v3 / znver3 save 1-4 % of user
instructions, nothing measurable either, and they would cost portability and the reproducible md5. One line in
40.01 ("self-builds: no measurable gain from target-cpu or PGO; the kernel does the work") would be enough.

Verdict (2026-11-02): none of V3, NAT, PGO, PGO+V3 is worth documenting as a gain. PGO cuts user instructions
9-12 % on connchurn/rr, but user code is 1-10 % of the work; cycles tie within the ±5 % spread and regress shows no
reproduced WIN. target-cpu also costs portability and the reproducible md5. The upload 10x10 PGO 'WIN' 1.07 at n=16
did not reproduce (n=32 0.999, swap 1.01, pooled 0.997). Pointers: 40.01 "Building it yourself", 40.02, 60.18 #18.
