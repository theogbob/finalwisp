# 30.11 Soak test: base-1.1, 12 h of mixed traffic on VPS3 (2026-10-24)

Pointers: 60.06 (base-1.1), 20.26 (memory budget), 30.10 (wst), code bench/soak/ (README below), data
raw data (not published) (analysis.md, soak.png, samples.csv.gz, probes/wbench/events, halfcost.jsonl, retain.jsonl).

## TLDR
- **Stable.** 12 h, 23.9 TiB through two instances: 0 crashes, 0 aborts, 0 OOM kills, memory level 0 the whole time,
  0 wbench errors in 5,503 runs, 1,439/1,440 probes OK (the 1 FAIL was a probe-script bug; see below).
- **Flat (no leak found; observed point slopes < 1 %/h, not a proven bound).** Quiet-window medians (no load besides the background clients), with the ESTAB
  count as covariate: RSS A -0.09 %/h, B +0.72 %/h; cgroup memory A +0.09 %/h, B +0.26 %/h. These are point estimates
  from 11 windows; their 95 % CIs are wide (B RSS [-1.8, +3.3]). The denser estimator (Theil-Sen on 22 half-hour
  minima) gives RSS A +0.19 [-0.02, +1.04], B +0.20 [+0.07, +0.82], cgroup A +0.51 [-0.58, +1.76], B +0.10
  [-0.60, +1.13] %/h: upper limits reach 1-1.8 %/h, so 12 h does not prove drift < 1 %/h. All include the deliberately held
  dead sockets (subtracting their measured cost makes every slope negative); fds follow the ESTAB sockets (fds - ESTAB: median
  31 / 21, min 17); pipe fds,
  threads (22), CLOSE_WAIT (0) flat; canary rr latency +0.2 %/h; probe time +0.06 / -0.65 %/h. After all clients
  stopped: fds 17 + exactly the half-open sockets, CPU 0.4 %.
- **Dead peers (the base-1.2 keepalive question):** a dead idle client costs **~13 KiB (plain) / ~19 KiB (TLS) + 1 fd**
  and is **never reaped** (the soak accumulated 720 at 60/h). A dead client with unread download data costs
  **~740 KiB + 2 fds** (cgroup) but the kernel reaped it after **~24 min** here (persist timer, tcp_retries2 = 15, kernel
  7.0); fds and socket memory are released, part of the heap stays with glibc for reuse (TLS 41 MiB after 200).
- **Watch (not a finding yet):** plain download runs with > 4 streams fell ~4 %/h under contention (z -4 after
  adjusting for concurrency; runs with <= 4 streams did not fall: 1686 -> 2081 -> 1800 MiB/s). Weaker and post hoc:
  canary rr p99 > 50 ms spikes under saturated CPU rose 3 -> 11 per ~110 runs per 4 h (20 events, z 2.2).
  Uncontended latency, upload, TLS download, solo-run peaks (3.5 GiB/s at 3 h and 9 h) did not move. Needs a
  controlled benchmark to settle (proposal at the end; needs a machine lock).

## Setup
- Box: VPS3, 4 vCPU, 7.5 GB, Ubuntu 26.04, kernel 7.0.0-27; nothing else running. Binary fw-base1.1 md5 b9036461.
- Server A: plain ws://127.0.0.1:7001, default flags + `--allow-loopback`. Server B: wss://127.0.0.1:7002,
  `--allow-loopback --allow-private`, certs raw data (not published) Each in its own user scope `MemoryMax=1G
  MemorySwapMax=0` (budget 1024 MiB from the cgroup, as the capability line shows). The driver raises its own
  RLIMIT_NOFILE soft limit to the hard limit (what systemd LimitNOFILE does; no sysctl touched).
- Targets: wbench echo/sink/source/reply/udp-echo + a Python pattern target (verifiable bytes).
- Load, all concurrent, random parameters and gaps (soak.py `WORKLOADS`): wbench download/upload (1-4 conns x 1-4
  streams, 5-30 s), rr, churn (half by name `localhost`, i.e. DNS), browse (pages of 4-20 streams, 30 % with an 8 MiB
  bulk stream), udp-rr; 75 % on A, 25 % on B. wbench SIGKILLed 0.8-8 s into a 60 s run (676 times). Idle holder: 300-3000
  connections (random walk, 2-8 % leave every 10 s by FIN, RST or stream CLOSE + FIN; 394k opened in total; each minute
  10 old ones must echo on a new stream). 12 slow readers (8-256 KiB/s, 16 KiB rcvbuf, end by CLOSE, RST or a 2-min
  stall). Half-open clients every 8-12 min: 10 idle + 10 with an unread download, alternately A and B; a root nft table
  drops every packet of the marked connection both ways (soak-nft.sh), so the server sees a peer vanish without
  FIN/RST. Abuse every ~30 min, alternating: 200 connections x a WS frame header claiming 10 MiB + 0-1 MiB of it,
  held 15-30 s (A); 3 x 100 CONNECTs to 10.255.255.1:80 (B, --allow-private). A 5-min quiet window each hour (only the
  idle/slow/half-open clients, the canary and the probes) gives the floor for the slopes.
- Probes, every minute per server, fresh client: 32 MiB pattern download checked chunk by chunk + CLOSE 0x02; 4 MiB
  upload through echo with credit respected, sha256 checked; 100 streams echo checked; refused port -> 0x44;
  `*.invalid` -> 0x42; 10.255.255.1 without --allow-private -> 0x48 (A); UDP echo.
- Sampler every 10 s (samples.csv, 125 columns): VmRSS/HWM/RssAnon, threads, CPU, fds by type, server TCP sockets by
  state + queues, cgroup memory.current/anon/sock/kernel/slab/peak/events, memory level (server log), half-open
  sockets, host sockstat/Slab/SUnreclaim/file-nr/load/CPU, workload counters and latencies.
- Pilot (20 min) and a 9-min check fixed the harness: TLS socket handle, half-open sockets must stay open (a close
  sends an unmarked RST), first-row columns, load lowered (host CPU 88 % -> 68 % mean).

## The one probe FAIL (harness, fixed)
17:27:04 EDT (min 379), A: `conn: TimeoutError: timed out` in streams100, after handshake, 32 MiB download and 4 MiB
upload had passed; during a partial-frame abuse burst (A CPU 0 -> 140 %, host 93 %). No RST/EOF/CLOSE, server at level
0, every later probe OK (340). Cause: wispc.recv_pkt left the socket timeout at the remaining time (<= 50 ms in the upload
loop), so the next sendall of 100 CONNECT+DATA timed out under CPU contention. Fix (commit 4339636): sends use a fixed
10 s timeout; deployed at min 401 (probe.py starts fresh each minute).

## Dead peers (half-open) - numbers for the base-1.2 keepalive decision
In the soak: 72 cycles; every dead idle connection stayed (360 on each server at the end, a straight staircase in
soak.png); the dead-download ones never exceeded 20 per server / 30 in total (each reaped by the kernel ~24 min after it died).
Controlled (halfcost.py, fresh server, 200 connections, fresh scope):
| per dead connection | plain | TLS |
|---|---|---|
| idle: RSS / cgroup (anon + kernel) / fds | 9.6 KiB / 13.4 KiB (8.1 + 3.7) / 1 | 17.5 KiB / 19.1 KiB (17.4 + 3.8) / 1 |
| idle: lifetime | forever (no timer runs: nothing in flight) | forever |
| unread download: RSS / cgroup / sock / fds | 326 KiB / 744 KiB / 412 KiB / 2 | 333 KiB / 740 KiB / 399 KiB / 2 |
| unread download: lifetime | 1441-1471 s (persist timer, zero-window probes, tcp_retries2 = 15) | same (7 of 200 at 360 s, unexplained) |
Healthy idle and dead idle cost the same; the difference is only that dead ones never leave. Sock = client send queue
(~92-123 KiB per socket, notsent-lowat) + the target socket's receive queue; anon = obuf/bulk lane.

All costs are deltas of the server's own scope (server only; targets and clients run outside it) divided by 200.
The ~24 min is an observation on kernel 7.0.0-27 with default sysctls (probe backoff to 120 s), not a constant; a
peer that is alive but answers every zero-window probe stays forever (that is an honest slow reader, by design).

What it means: at R dead clients per day a server holds 13-19 KiB x R x days and R x days fds until restart. Example:
1,000/day for 30 days = 30k fds and ~0.4-0.6 GiB, i.e. half of a 1 GiB budget, which then pushes the memory level up
and refuses honest streams. TCP keepalive on client sockets (SO_KEEPALIVE + TCP_KEEPIDLE/INTVL/CNT set per socket, no
sysctl) closes exactly this gap: idle sockets are the only ones the kernel never reaps today. A bare SO_KEEPALIVE is
not enough (tcp_keepalive_time defaults to 2 h). It does not change the dead-download case: Linux sends no keepalive
while data is unacknowledged or still queued (tcp_keepalive_timer); the persist/retransmit timers end it in ~24 min.
TCP_USER_TIMEOUT would shorten that, but must be checked against honest zero-window readers - not tested here.
Not covered by this soak: dead or stalled *target* sockets (only client-side peers were made half-open), real
network loss/mobile suspend (keepalive timing values). Cost when idle and healthy: one probe + ACK per idle interval.

## Memory after bursts (retain.py)
After 200 clients with unread downloads leave (RST), anon does not return to the start value; it plateaus:
TLS 0.6 -> 41 -> 51 -> 53 MiB after batches 1-3 (+40, +10, +2.4), plain 0.5 -> 21 -> 25 -> 26 MiB (+20, +4.4, +0.9),
unchanged 3-60 s later. Heap kept by glibc arenas (buffers < the 1 MiB mmap threshold) and reused by the next batch,
not a leak: in the soak 676 SIGKILLed mid-download clients and 12 abuse bursts took this path and the quiet RSS floor
stayed flat. In halfcost the plain server returned to 2.3 MiB after the timed-out batch; TLS kept 41 MiB. Watch item
only (idle RSS after a burst is ~25-55 MiB, not ~4).

## Watch: download throughput and tail latency under contention
- Plain download (A) per-run MiB/s, log-linear fit with log(conns x streams), log(concurrent streams) and the idle count:
  -4.1 %/h, z -4.1 (n = 344). By third, runs with > 4 streams: 1649 -> 1021 -> 843 MiB/s median. Not seen in TLS
  download (+0.8 %/h), upload (A -1.3 %/h z -1.3, B -0.2 %/h).
- Canary rr (1 conn, 1 stream, 5 s, every minute): spikes p99 > 50 ms only when the host CPU was 85-99 %; under
  >= 95 % host CPU: 3/132, 6/104, 11/109 per third; logistic fit with concurrent bulk: time z 2.25. Uncontended
  canary (host < 80 %): p50 109/104/108 us, p99 278/223/268 us per third. Other latency series (rr, churn, udp,
  browse p99 medians) fell slightly over time.
- Against a server-side drift: solo plain downloads (no other A traffic) reached 3505 MiB/s at 3.1 h and 3578 MiB/s at
  9.3 h; quiet-window values are flat; the server's CPU did not rise. For it: the effect survives the covariates I
  have. Confounders left: client-side helpers (host anon outside the servers grew 399 -> 436 MiB; per-process CPU was
  not sampled), the 12-h-old wbench source target (shared by download, slow readers and half-open downloads), host
  state. On a 4-vCPU box shared by clients and servers per-run throughput is a weak instrument.
- Proposal (needs a benchmark slot; not another mixed soak, which would confound the same way): age one server
  with the soak mix for several hours, then on a quiet box run the cell that moved (plain download, 3 x 3 and 4 x 4
  streams, short repeats, rotated) as a factorial {aged, fresh server} x {aged, fresh source target}, the fresh
  server started next to the aged one at the same time; clients and targets on CPUs apart from the servers (test-only
  pinning) or on another host. Drift in both aged-server cells and not in the fresh ones = the server. Canary under
  a fixed, reproduced saturation with a pre-set p99 threshold and enough repeats for a binomial CI.
