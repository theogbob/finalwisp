# 20.06 finalwisp performance findings (analysis)

Pointers: 20.01 server/ (finalwisp), 30.01 bench/ (wbench + run_matrix), 40.01-40.03 tests/compat/.

## Tricks in finalwisp and measured effect
| ID | Trick | Effect (this box, loopback) |
|---|---|---|
| T1 | Thread-per-core epoll loops, SO_REUSEPORT listener per worker, fds registered once (EPOLLET) | baseline architecture |
| T2 | Download zero-copy: target read() lands in client obuf behind a 9-byte WS+Wisp header gap | download 7.4-7.7 GiB/s vs epoxy 3.7-6.2, ~30% less CPU |
| T3 | One write() per client per loop turn, coalescing everything already queued (no added latency) | rr 10x10 306-409k rps vs epoxy 215-223k |
| T4 | Upload written straight from unmasked WS read buffer; copy only on EAGAIN | upload 1x1 1.1-1.4 GiB/s |
| T5 | CONTINUE in the same loop turn when credit <= N/2 and target backlog low | no stalls (epoxy stalls one-way upload without pings) |
| T7 | splice() download: target -> per-client pipe -> client socket, header via send(MSG_MORE); obuf marker keeps order (20.08) | download 1x1 1.9 -> 3.5 GiB/s, 10x10 8.7 -> 12.7 GiB/s on fewer cores; WispMark wisp-mux 5x10 4.6 -> 10.2 GiB/s; single-conn echo ~4% lower |
| T8 | Upload batching: consecutive DATA for one target staged as iovecs into rbuf, one writev (20.09) | upload 1x1 16K 2.5 -> 3.7 GiB/s, 1K 0.34 -> 2.5 GiB/s (5x7 interleaved medians) |
| T9 | Accept balancing to least-loaded worker, opt-in `--balance` (20.10) | bulk worst case 5.3 -> 6.7 GiB/s, but rr -10..25% (more half-idle threads = more wakeups); off by default |
| T6 | RST close (SO_LINGER 0) on client-initiated stream close when target spoke last, nothing unsent/unacked | churn 18k -> 119k streams/s, p99 39 ms -> 2.3 ms; TIME_WAIT 25k -> ~60 |

## Pitfalls found
- SO_REUSEPORT lets a stale instance silently share the port; finalwisp now probe-binds and refuses (20.07).
- background shell handles in the test driver must `exec` the server, or kill() only kills the wrapper shell.
- The bench echo target's single accept loop (backlog 1024) overflowed under churn (TcpExtListenOverflows) and
  added 1 s SYN-retransmit tails to every server; fixed with multi-acceptor reuseport + backlog 65535.
- epoxy-server queues per-stream CONTINUE without flushing; one-way upload stalls after 128 packets unless
  something else is written (bench gives epoxy/wisp-js/python --stall-ping-ms 1).
- Single 5 s runs vary up to ~40% (shared desktop, load avg ~8): use median of repeated runs.

## Known limits (deliberate, revisit later)
- UDP: implemented in 20.16 (see that section); no idle timeout, ICMP errors do not close the stream.
- 128 credits x 16 MiB frames could exceed the 64 MiB per-stream pending cap (real clients send <= 64 KiB).
- Port-ownership probe has a startup race if two instances start in the same instant.
- Close-reason UTF-8 not validated.
- Unread input at close (review r1, 2026-10-22; pointer 20.06/r1-close): a closing client is no longer read
  (read_client returns early once `closing`), so if it is still sending when the server closes (an upload after a
  protocol error, frames pipelined behind a bad one), close() finds unread data and TCP sends RST, dropping the
  unsent tail (plain and kTLS alike; for kTLS it also keeps the drain wait from reaching TCP-empty, so the 10 s
  linger cap closes it). Fix if it ever matters: read and discard input while closing/lingering (classic lingering
  close), then apply the same TCP-empty wait to plaintext. Rare with real clients; not fixed.
- kTLS close drain is a heuristic (review r1): the kernel exposes no "kTLS TX list empty", so a closing kTLS socket
  closes after close_notify is accepted and SIOCOUTQ == 0 on two samples >= 100 ms apart (cap 10 s). 0 failures in
  133 probes; a tx_work delay over 100 ms under heavy CPU contention could still cut the tail.

- Profile (perf, kernel symbols, 2026-10-21; supersedes the earlier "88% sys = copying" guess, which was unmeasured):
  bulk echo 5x10 (wisp-mux): _copy_to_iter 21.8% (socket reads), kernel_init_pages 15.4% (init_on_alloc zeroes
  every page tcp_sendmsg allocates: 12% from upload writev, 2.7% from send), unmask_avx2 10.8% (vectorised,
  memory-bound: 63% of samples on the first load), _copy_from_iter 10.5% (upload writev), netfilter ~3%, our other
  code <2%. rr 10x10: flat kernel TCP stack; process_backlog ~30% is the loopback PEER's receive path charged to
  us; netfilter (nft_do_chain+conntrack+defrag) ~7.5%, AppArmor ~1%, syscall entry ~1.3%, our code ~1-2%.
  Tried: capping read() size so unmask hits cache -> no gain (reverted).
- splice pitfalls fixed: park target in `blocked` when the client socket fills mid-splice (EPOLLET lost wakeup,
  repro'd by 40.03 frozen-reader test); short splice != drained (pipe slot limit); urgent data stops splice at the
  mark -> SIOCATMARK check, fall back to read().
- wispurr (formerly mrrowisp): baselines/wispurr/SOURCE.md — data-loss and credit-stall bugs; it wins WispMark
  wisp-mux 5x10 copy-path-vs-copy-path by spreading kernel copies over ~7 cores (goroutines per stream).

- 20.09 review (3 vendors agreed): staged iovecs must never point outside rbuf (fragmented messages are
  reassembled into a temp Vec -> flush before it drops + in_rbuf guard); a failed flush inside close_target
  re-entered it and panicked -> recheck liveness; flush before queuing a WS Close so no CONTINUE follows it.
  40.03 tests 11-12 reproduce both on the old build (0/20 intact; process died).

## 20.11 Idle memory (2026-10-21)
Probe: bench/idle_rss.py (2000 clients, each echoes 64 KiB once, then idle; server RSS after settle).
| server | KiB per idle connection |
|---|---|
| finalwisp before | 412 |
| **finalwisp 20.11** | **12-14** |
| epoxy | 116 |
How: rbuf starts at 16 KiB after the upgrade and doubles toward 256 KiB only when a read fills it (`rfull`);
per-worker idle sweep every 2 s frees rbuf/obuf of clients with no I/O for a whole period and nothing
buffered, plus empty target `pend`. Interleaved A/B (5-11 reps) on laptop and VPS: all cases within noise
(ratios 0.94-1.11, overlapping ranges). First version without `rfull` cost ~4-8% on echo on both machines.
Note: starting rbuf empty instead of 4 KiB raised idle RSS by ~5 KiB (allocator fragmentation): kept 4 KiB.
Test: 40.03 #13 (idle past two sweeps, then 60 KB + 200 KB echo).

### 20.11b Idle RSS regression in 20.26 and fix (branch idlefix, 2026-10-23)
20.26 (fcea270, first bad commit; every membudget/base1-rc build after it) raised the idle probe from ~15 to
90-130 KiB per connection. Not the budget (--mem-budget 0: same) and not the counting allocator (removed: same).
Live heap (mem::HEAP read from /proc/PID/mem) was 2.4 MiB of 175 MiB RSS: glibc kept the freed burst buffers.
Walking the worker arenas showed one live chunk just below `top` in each of them: the targets Slab slot array
(256 x 232-byte slots = 59408-byte chunk), grown by push during the burst, so heap_trim could not shrink the
~25 MiB below it. 20.26 grew a slot from 192 to 232 bytes; the old 49168-byte array still fitted a freed
16K+32K rbuf hole low in the heap, the new one did not (layout luck, not design).
Fix: Slab::new reserves >= 128 KiB of slots (SLAB_RESERVE), so the array is its own mmap from Worker::new on
and grows by mremap, never inside an arena (no RSS for untouched slots; +2 x 128 KiB per worker in heap_bytes).
**Regression check** (laptop, memory only; `bench/idle_rss.py PORT ECHO PID 2000 65536 5` against
`wbench target --mode echo`, default threads = 15): expected <= 20 KiB/conn. Measured (4 interleaved runs):
master 13.4-16.1, base1-rc 90-121, idlefix 17.4-17.7. 4000 x 16 KiB: master ~60, base1-rc ~57, idlefix 7-9.
Known limit (master too): with few workers (--threads 1/2) each arena holds many clients and small
long-lived allocations (64-byte chunks) or whole 64 MiB arena heaps stay pinned: --threads 2, 2000 x 64K
150-190 KiB/conn on master, base1-rc and idlefix; --threads 1, 1000 x 16K 26-55 (layout dependent).
malloc_trim(0) from the idle sweep after >= 4 MiB freed (experiment, not shipped) gives ~2 KiB/conn in all
three cases at 2-17 ms per call (it locks each arena in turn).

## 20.12 MSG_ZEROCOPY on upload writev (2026-10-21): REJECTED
Best-case-only experiment (no completion-driven buffer retention, never shippable): sendmsg(MSG_ZEROCOPY) for
upload batches >= 16 KiB, error queue drained every 8 sends. Interleaved A/B, MiB/s, median of 2-3:
| case | copy (writev) | zerocopy |
|---|---|---|
| laptop upload 1x1 | 1803 | 1261 |
| laptop upload 10x10 | 7557 | 1804 |
| VPS upload 1x1 | 1844 | 1428 |
| VPS upload 10x10 | 1962 | 1432 (678-2134) |
Loses everywhere: on loopback the kernel copies anyway and adds page pinning + completion notifications. A
real version would also need rbuf to stay pinned until completion (breaks in-place reuse) and only pays on
real NICs with large writes. The 15% `kernel_init_pages` cost is the host's init_on_alloc=1 default (zeroes
every page tcp_sendmsg allocates); removable only by the operator (boot param init_on_alloc=0, a hardening
trade-off), not by the server.

## 20.13 Built-in TLS via kTLS (2026-10-21)
`finalwisp --tls-cert cert.pem --tls-key key.pem` serves wss:// itself. rustls (ring) runs only the handshake,
in the epoll loop (new client state `Tls` before `Http`). Then the keys go into the kernel (TCP_ULP "tls",
TLS_TX + TLS_RX), and all later I/O, including the splice download path, is the same plain
read/writev/send/splice as for ws://. No userspace TLS data path. Code: server/src/tls.rs, worker.rs `tls_*`.
- Record at a time (not the rustls unbuffered API): read the 5-byte header, then exactly the body, feed that one
  record to rustls. The server never reads past the client's Finished, so records after it stay in the socket
  for kTLS RX. Same safety as the unbuffered API with less code: the buffered API plus an exact-length read.
  A bad header (type not 20..23, major version not 3, length > 18432) closes at once (plain HTTP, garbage).
- `send_tls13_tickets = 0`: no post-handshake records owed. TLS 1.2 session-id resumption still works.
- Order at the end: flush every rustls record, drain rustls plaintext (always empty, no 0-RTT), extract the
  secrets, install TX + RX, then read actively once (the edge for data after Finished may already be used up).
- Handshake timeout 10 s (FIFO deadline list, checked every loop turn; the 2 s idle-sweep wakeup bounds it).
- After kTLS, a non-data record (close_notify, alert, KeyUpdate) makes read() fail with EIO: client closed.
- Startup probe: TCP_ULP on a loopback pair, then TX+RX with dummy keys per (version, cipher); the offered
  suites are only the ones the kernel accepts. **The `tls` module autoloads only for CAP_NET_ADMIN**: an
  unprivileged server needs `sudo modprobe tls` (persist: /etc/modules-load.d/tls.conf). Error message says so.
- wbench: `--url wss://... --insecure` (userspace rustls on the client side, any server; no cert checks).
  `WBENCH_TLS_SUITES=TLS13_AES_128_GCM_SHA256` restricts the offered suites.

Tests (VPS, kernel 7.0.0-27, module loaded; the laptop had no `tls` module): tests/compat/run_tls.sh runs
wisp-js over wss (TLS 1.3 AES-256-GCM, TLS 1.2 AES-128-GCM, TLS 1.3 ChaCha20; 2x64 MiB pattern downloads,
splice confirmed with strace: 1288 splice calls), 40.03 adversarial.py --tls (all 15), and 40.04
tls_adversarial.py (plain HTTP, garbage, oversized record, alert on bad ClientHello, 60 mid-handshake closes
FIN/RST, TLS 1.1 + ALPN h2-only refused, Finished + request in one segment, close_notify -> close, 600
parallel handshakes, stalled handshakes closed at 10.0 s, no fd leak, s_client 1.2/1.3 x 3 ciphers, EC + RSA).

## 20.14 Happy eyeballs + 20.15 TCP Fast Open to targets (2026-10-21)
- 20.14: addresses keep getaddrinfo order (RFC 6724), families interleaved (RFC 8305 s4), deduped. Next
  address starts 250 ms (+ up to one 100 ms tick) after the last start, in parallel, max 4 in flight; a failed
  attempt starts the next one at once; first to connect wins, the rest close. Before: IPv4 first, serial.
- 20.15: IP-literal / DNS-cache-hit targets start connecting at the end of the input batch, so DATA from the
  same read is queued. An attempt with no other attempt carrying SYN data sends the first TLS ClientHello
  record (0x16 0x03xx, handshake type 1; only that record, never 0-RTT data behind it) via sendto(MSG_FASTOPEN).
  Bytes stay queued until that socket wins. Plain-text first bytes never ride the SYN (replay). `--no-tfo`.
- Review (3 vendors): loser hangup events could mark the winner rdhup (disabling the RST close) -> confirm on
  the real fd; one poll per connect; attempt cap.

## 20.16 UDP streams (2026-10-22)
What: CONNECT stream type 0x02 opens one UDP socket per stream, connected to the resolved address, so the
kernel delivers only datagrams from that address and port. Each DATA payload = one datagram, each datagram
received = one DATA packet (0-byte datagrams are valid both ways). The server never sends CONTINUE on UDP streams.
UDP is available in v1. In v2 the server INFO gets the extension record `01 00000000`. `--no-udp` removes the
record and answers UDP CONNECTs with CLOSE 0x41 (as before).
How (server/src/worker.rs "20.16" region, net.rs udp_connect/udp_soft_error):
- The `Target` struct gets a `udp` flag. UDP streams share the slab, tokens, DNS path + cache, SSRF filter,
  connect-time CLOSE reasons (0x41/0x42/0x48/0x49) and close path with TCP. For UDP, connect() sends nothing,
  so there are no happy eyeballs: the first allowed address (resolver order, interleaved) whose connect() works.
  Epoxy, wisp-js and wispurr also use one address.
- Upload: send(MSG_DONTWAIT) per DATA, no staging, no credit. If the socket buffer is full (EAGAIN), the datagram
  is dropped. Payloads > 65507 are dropped. DATA that arrives while the name resolves is queued
  ([u16 len][bytes] records, 256 KiB cap, excess dropped) and sent when the socket opens.
- Download: recvmmsg up to 8 datagrams into one per-worker 8 x 64 KiB scratch buffer (allocated on first use),
  then a copy into obuf as DATA frames. A short batch means drained (no EAGAIN syscall), except when an
  EPOLLERR is pending: then read until EAGAIN, because recvmmsg stores a mid-batch error again without a new
  edge. Same BUDGET + OUT_HIGH back-pressure as TCP: a stalled client parks the stream, and the kernel drops what
  overflows the socket receive buffer.
- ICMP errors (ECONNREFUSED, host/net unreachable, EMSGSIZE, ENOBUFS, EPERM...) are soft: the error is
  consumed, the datagram is lost, and the stream stays open. A pending error eats the next send(), so the send
  is retried once. **Deliberate deviation:** epoxy closes the stream (CLOSE 0x03) and wisp-js closes it (0x02)
  on the first refusal. Measured with tests/compat/udp.py --ref: a stream to a not-yet-open port dies there.
  An ICMP error is advisory for UDP (DNS/QUIC/game clients retry), it can be forged by anyone who knows the
  4-tuple, and the client can close the stream itself. To match the references, `read_udp` would call
  target_eof(0x03) on a soft error (one line).
- Idle timeout: none. epoxy, wisp-js and wispurr have none, and the client owns the stream's lifetime (CLOSE or
  WS close frees the socket). The cost of an idle stream is one fd + one slab slot.
- A v2 client that did not list 0x01 can still open UDP streams (epoxy, wisp-js and wispurr accept this too).
Tests:
- tests/compat/udp.py PORT [--no-udp-port P] [--ref] (40.06, raw v1+v2): datagram boundaries, empty datagram,
  no CONTINUE, 65507 round trip, 65508 dropped, DATA before DNS, closed port then reopened, 0x48/0x42/0x41,
  a 200k-datagram flood with a stalled client (RSS +1 MiB), 1000 streams then CLOSE (fds released),
  v2 without the extension, --no-udp. Master binary: 21 FAILED; this branch: ALL PASS.
- tests/compat/wispjs_udp.mjs URL [NO_UDP_URL] (40.07, real wisp-js client, v1+v2). Master: v2 refuses UDP
  ("udp is not enabled": no 0x01 in INFO), v1 gets 0x41. This branch: ALL PASS. Note: the target socket needs
  a big SO_RCVBUF; with the default 208 KiB a client burst of 300 datagrams loses ~60% at the target, for every
  server.
- net.rs unit test: ICMP refusal is soft, the socket works after the port opens, a connected socket ignores
  datagrams from other peers.
- simple-wisp-client `-u` cannot test UDP: it only lists (and in v2 requires) extension 0x01, and its streams
  are always TCP. Its `--wisp-v2` sends no Sec-WebSocket-Protocol header, so every server that follows the spec

## 20.17 TLS extras: SNI, SIGHUP reload, close_notify, KeyUpdate, cipher order (2026-10-22)
Code: server/src/tls.rs (`Certs`, `pick`, `hs_step`, `send_record`/`recv_record`, `rekey`), worker.rs
(`TlsHs`, `tls_drive`, `tls_read_records`, `tls_finish`, `tls_control`, `Client::flush`/`tx_count`/`key_update`,
`read_client` EIO branch, `close_client`), main.rs flags + `reload_loop`. Tests: 40.09 tests/compat/tls_extras.py
(run by run_tls.sh on PORT+1..PORT+3), cipher A/B: bench/tls_cipher.py.
- **SNI**: `--tls-cert/--tls-key` repeat (pairs in order). Own `ResolvesServerCert` (`tls::Certs`): the first
  pair whose end-entity cert is valid for the SNI name (`rustls::client::verify_server_name`: SAN DNS names,
  wildcards, case-insensitive), else the first pair (no SNI, IP literal, no match). One pair = no parsing per
  handshake. Startup error (exit 1) if any pair does not load or cert/key do not match; exit 2 if the counts differ.
- **SIGHUP reload**: main blocks SIGHUP before any thread exists; after startup the main thread sits in
  `sigwait` and calls `Certs::reload` (re-reads all pairs, all or nothing) and swaps a `Mutex<Arc<Vec<..>>>`.
  Handshakes take the lock once (in rustls' resolve call) and clone the Arc; the event loops never wait on file
  I/O. Live connections are untouched (their keys are in the kernel). A bad file logs
  `SIGHUP: reload failed, keeping the current certificates: ...` and keeps the old set. Without TLS, SIGHUP
  is blocked too and only logs `SIGHUP: no TLS certificates, nothing to reload` (60.04 F7; before that it ended
  the server).
- **close_notify**: `close_client` on a kTLS socket sends an alert record [1, 0] via `sendmsg` + cmsg
  SOL_TLS/TLS_SET_RECORD_TYPE=21, MSG_DONTWAIT (best effort, never delays the close; the kernel closes an
  open record first). Not sent after a fatal alert from the peer. Incoming: read() EIO -> `recvmsg` with
  TLS_GET_RECORD_TYPE: close_notify -> close (and answer with ours), other alert -> close silently.
- **KeyUpdate (TLS 1.3)**: kernel 7.0 supports rekey (setsockopt TLS_RX/TLS_TX again on a 1.3 socket, Linux
  6.14+: after a KeyUpdate record RX returns EKEYEXPIRED and polls not-readable until the new RX key is set;
  /proc/net/tls_stat TlsRxRekeyOk/TlsTxRekeyOk). rustls 0.23.46 `KernelConnection` gives the next secrets
  (`update_rx_secret`/`update_tx_secret`), but only from `UnbufferedServerConnection::dangerous_into_kernel_connection`,
  so the handshake now runs on the **unbuffered rustls API** (`tls::hs_step`), still one record per read:
  rustls may keep a partial handshake message in rbuf[..kept] (a message spanning records), the next record is
  read after it, and `discard` is honoured. At the end rbuf must be empty (nothing after Finished is in rustls).
  Per TLS 1.3 client the `KernelConnection` (key schedule) stays in the Client. Received KeyUpdate
  (`[24,0,0,1,req]`): new RX key; if update_requested, our KeyUpdate (update_not_requested) is queued and sent
  at the top of the next `flush` (sendmsg type 22 under the old key, then the new TX key; stream bytes are
  unaffected, records are independent of Wisp framing, also mid-splice).
  Proactive: `--tls-rekey-records N` (default 2^23, 0 = off, >= 2^24 = off): after N records under one TX key
  the server sends a KeyUpdate; after N records received it sends update_requested (once until the client
  answers). The 2^24 close budget stays as the fallback (TLS 1.2, a client that ignores update_requested).
  TLS 1.2 is unchanged (no `KernelConnection` kept; set_raw's TLS 1.2 GCM nonce fix untouched; tls_nonce.py passes).
  Other handshake records after kTLS (TLS 1.2 renegotiation, malformed) close the connection.
- **`--tls-cipher-order client|server`** (default client = before). server = `ignore_client_order` with
  ChaCha20 sorted last (stable: AES-256-GCM, AES-128-GCM, ChaCha20, TLS 1.3 before 1.2).

client the kept `KernelConnection` (key schedule, ~hundreds of bytes) adds memory. No unit test of
`hs_step` against an in-memory rustls client (covered by the compat suites).

**KeyUpdate right behind application data (fixed 2026-10-23, branch ku).** Records [data][KeyUpdate] in one read:
kTLS read() stops at the type change and returns the data short, but the KeyUpdate is already decrypted (moved to
rx_list) and `key_update_pending` is set (tls_rx_one_record -> tls_check_pending_rekey), so from then on
tls_sk_poll masks EPOLLIN until the new RX key is set (Linux 6.14+). Our EPOLLET reader took the short read as
"drained": the KeyUpdate was never read, every later read event masked, the connection stalled for good (master:
[ping][KeyUpdate][ping] in one segment, pong 2 never came, RX rekeys +0, 3/3 runs). Fix (worker.rs `dispatch`):
on EPOLLOUT without EPOLLIN for a TLS 1.3 kTLS client that is not readable, try one read (EIO -> tls_control).
Why that event always comes: the KeyUpdate can only be decrypted after the strparser marked it ready, and the
strparser marks the next record ready only after the previous one was consumed, i.e. inside one of our reads
(tls_strp_msg_done -> tls_strp_check_rcv -> tls_strp_read_sock sets msg_ready and calls tls_rx_msg_ready ->
saved_data_ready). That wakeup puts the epitem back on the ready list after our epoll_wait; the next epoll_wait
polls it with EPOLLIN masked, so it reports EPOLLOUT alone (if the socket is not writable then, tcp_poll sets
SOCK_NOSPACE and the later write-space wakeup reports EPOLLOUT). Cost: one read per EPOLLOUT-only event on TLS 1.3
clients (they follow a full send buffer), none per data read. Test: 40.09 tls_extras.py `HoldProxy` holds
s_client's records and sends [ping][KeyUpdate][ping] in ONE send (deterministic by record count, no timing), plus
[ping][KeyUpdate] then a later ping (master fails both, permanently: later data does not help).
Kernel dependency (review, verified in source): Linux 7.2 ("tls: Suppress spurious saved_data_ready", msg_announced)
wakes at reader exit only for a record parsed but not yet read. With a record behind the KeyUpdate the wakeup still
comes (probe works); with a lone [data][KeyUpdate] there is no wakeup until the client's next segment, which then
arrives as EPOLLOUT-only and the probe reads the KeyUpdate. So on 7.2+ no application data is ever held back, but
the rekey (and our answer to update_requested) waits for the client's next segment. If that ever matters: read
once more after every short read on TLS 1.3 kTLS clients (kernel-independent, +1 syscall per short read).
**Kernels without kTLS rekey (< 6.14, e.g. Ubuntu 24.04's 6.8).** In-kernel rekey arrived in Linux 6.14 (v6.13
net/tls/tls_main.c do_tls_setsockopt_conf still says "we don't support set crypto info more than one time" ->
EBUSY; v6.14 adds the TLS 1.3 update path, key_update_pending and TlsRx/TxRekey* stats). Before this fix master did
not check: a proactive server KeyUpdate (after --tls-rekey-records, default 2^23) went out, then the TX rekey
failed and the connection closed, the client (already on the new key) saw bad record mac (6.8 box: rekey-64 test
broke after 62 pings). Now a startup probe (tls.rs `probe_rekey`: TLS_TX twice on a TLS 1.3 loopback socket; EBUSY
= no rekey, any other error also = no rekey, logged, never fatal) sets tls_rekey = 0 and logs one line: no
KeyUpdate from us, TLS 1.3 then closes at the 2^24 record limit like TLS 1.2. Known limit: a client KeyUpdate on
such a kernel closes the connection (our close_notify under the old key, clean; checked with s_client -msg on 6.8).
On 6.8 tls_sk_poll has no rekey mask, so there is no stall there either. tls_extras.py checks the counters only
when /proc/net/tls_stat has them, else this documented behaviour.

## 30.09 Idle splice-pipe reclaim (2026-10-22)
Problem: a client whose target download went through splice() keeps its pipe (2 fds, resized to 256 KiB = 64
pages) until it disconnects. Linux gives each user fs.pipe-user-pages-soft = 16384 pages by default, so 256 such
pipes use the whole quota. Past it the kernel refuses F_SETPIPE_SZ (EPERM) and new pipes hold only 2 pages, and
other processes of the same user cannot get a 256 KiB pipe either.

Fix (server/src/worker.rs, branch pipes 8a0b008, merged 0606e2e):
- `idle_sweep` closes a client's pipe when it is empty and nothing is in flight (`splice_at == NO_MARK`,
  `splice_pending == 0`). A pipe that still holds data is never closed.
- If F_SETPIPE_SZ fails, the new small pipe is closed and the worker uses the copy path for 1 s (`pipe_retry_at`,
  `PIPE_RETRY`), then tries again. Splice is never switched off for good.

Measured with bench/pipe_probe.py (N clients each download once through splice, then stay idle):
| 400 idle clients after one bulk download each | before | after |
|---|---|---|
| server fds | 1204 | 448 |
| this user can still get a 256 KiB pipe | no | yes |
Adversarial test 14 (40.03) downloads 8 MiB, lets the sweep release the pipe, downloads 8 MiB again and checks
every byte. wisp-js 0.5.0, adversarial, run_tls.sh (7 parts) and udp.py pass.

Speed: neutral. Laptop interleaved A/B: every case within noise (churn read 0.90 once, 0.99 at 9 reps). VPS
download 10x10, final check with rotated order (16 reps, patched vps_ab.py, md5 verified on the VPS): pipes /
base = **0.998** (medians 3000 vs 3006 MiB/s), pipes faster in 8 of 16 paired reps, Wilcoxon p = 0.90. Earlier
VPS reads of 0.93 and 0.95 came from the old fixed-order script (base always first); the 1.06 "rotated" recheck
predates the patched script reaching the VPS, so it is not counted. Active downloads keep their pipe because the
sweep skips them, so no effect was expected. Not measured: the cost of re-creating a pipe (pipe2 + fcntl) on the
next bulk read of a client that went idle in between.

## 20.18 Wisp v2 extensions: password auth, key auth, MOTD (2026-10-22)
Code: server/src/ext.rs (INFO builder + client INFO check, 22 unit tests), handshake in worker.rs. Test:
tests/compat/v2ext.py (40.11, starts its own servers). Built by the v2ext-builder helper (aborted before it
finished its tests); the lead ported it onto master, added the UDP record, finished and ran the tests.

Flags (all off by default; with none set the INFO bytes are unchanged: `02 00 01 00000000`, or `02 00` with --no-udp):
- `--auth-file FILE`: one `user:password` per line (split at the first ':', '#' comments). Plaintext like epoxy;
  the server warns when the file is group/other readable. Stored as SHA-256 of the wire credential
  (u8 user_len | user | password); the check hashes the client's credential once and compares it with every
  entry without early exit (handshake medians 8-12 us for right / wrong last byte / unknown user / long password).
- `--cert-auth-key FILE` (repeatable): ed25519 public keys, PEM "PUBLIC KEY" blocks (`openssl pkey -pubout`).
  Each connection gets a fresh 64-byte challenge in record 0x03. Accepted: epoxy's form (alg | SHA-256(key) |
  signature) and the spec form with a username in front. Keys are not bound to users (as in epoxy).
- `--motd TEXT`: record 0x04.
INFO records go in id order: 0x01 UDP, 0x02 password (required = 1), 0x03 key auth (per connection), 0x04 MOTD.
Every configured method is required; one verified method is enough, a wrong one that was offered fails.

With auth on: header-less clients also get the v2 handshake (as epoxy-server; simple-wisp-client sends no
header); v1 traffic gets CLOSE 0xc2; wsproxy paths get 403 (no way to carry credentials). CLOSE reasons: 0xc0
bad password, 0xc1 bad signature, 0xc2 auth required, 0x04 malformed records or wrong major version. Without
auth the client's records are not parsed (pre-20.18 behaviour).

Interop with epoxy's simple-wisp-client (`--wisp-v2 --auth`, `--certauth`, `--motd`): connects, not downgraded,
extensions [2, 4] / [3], MOTD received; wrong password, wrong key and no credentials are refused. v2ext.py: 53
checks incl. malformed records, a 1 MiB unknown record, INFO split over WS continuation frames, a second INFO
ignored, brute force (15,000 wrong guesses/s all rejected while an authenticated stream keeps answering, p99
40 ms). Side fix found by it: a frame header declaring more than MAX_FRAME (16 MiB) now closes with 1009 (was
1002), like the reassembly path.

## 20.21 adaptive TCP_NOTSENT_LOWAT for kTLS clients (2026-10-22)
Every client starts with --notsent-lowat (128K), so a slow link gets the HOL win from the first byte. For kTLS
clients, flush_dirty reads TCP_INFO once per 4 MiB sent (RATE_CHECK_BYTES, counted in tx_count). A delivery
rate >= 1 GiB/s (LOWAT_FAST; accepted when app-limited, since that is a lower bound) sets lowat to i32::MAX
(0 would mean the host sysctl); a non-app-limited sample < 256 MiB/s (LOWAT_SLOW) puts 128K back. Plain ws is
unchanged (lowat costs it nothing). Code: net.rs delivery_rate (raw TCP_INFO: u64 at offset 160, app-limited bit
in byte 7, endian-aware; kernel < 4.9 returns a short struct and sampling stops), worker.rs adapt_lowat.
Results (raw data (not published)):
- Laptop wss download 10x10, 12 rotated reps vs lowat 0: lowat128k 0.902 (p = 0.001), adaptive 0.967 (p = 0.15).
  A first 9-rep run (noisy, load 16): 0.929 / 1.002 (adapt-tls-dl.json, adapt-tls-dl2.json).
- VPS netns 100 Mbit / 10 ms, wss browse, 8 reps: request p50 lowat128k 179 ms, adaptive 202 ms (p = 0.25, noise),
  lowat0 600 ms (hol-tls-adapt.jsonl). The link rate (~12 MB/s) never reaches the lift threshold.
- VPS no-regression vs 8d15875, 16 rotated reps (vps-adapt.jsonl): wss download/rr/churn 1.003/1.015/1.004;
  plain download 1.060 (p = 0.004; the code is not reachable for plain sockets: layout noise), plain rr 0.973.
- strace: each fast connection goes 131072 -> 2147483647 once; a rare flap back under load.
Review (3 vendors, no P0/P1): applied the endian-safe flag mask and the latch when TCP_INFO has no rate.
Known limits: a splice-fed client is sampled only after a short write (enough: a client that slows down fills
the socket). The kernel rate is packets x MSS / interval and keeps the highest app-limited sample, so a bursty
client on a >= 10G path (or a TCP proxy peer) can be lifted wrongly; it self-corrects at the next real sample,
costing at most one sndbuf of HOL for <= 4 MiB. With a large tcp_wmem[2] a lifted client can hold more queue.

## 20.23 negative DNS cache, 20.24 Happy Eyeballs memory (2026-10-22)
From the "which knobs can become dynamic" design review (recap 2026-10-22). Both are automatic, with no flags.
**20.23 negative DNS cache.** net::lookup is a raw getaddrinfo (same hints as std: AF_UNSPEC, SOCK_STREAM) that
keeps the error kind. Only EAI_NONAME (NXDOMAIN) is cached: an empty per-worker cache entry, answered with CLOSE 0x42
at once for DNS_NEG_TTL = 5 s. Never cached: EAI_AGAIN (timeout/SERVFAIL), EAI_FAIL, EAI_SYSTEM, EAI_NODATA (glibc
can report NODATA when the parallel AAAA query SERVFAILed), names with NUL. A negative answer never replaces a fresh

## 20.25 copy-path stall at a TCP urgent mark (pre-existing; found via the 20.22 gates) (2026-10-22)
The adversarial "target urgent/OOB data" check failed now and then (3 sightings before, more often with the lane
on). Two causes:
1. Server bug. read_target took a read() shorter than CHUNK for "drained" and waited for the next EPOLLET edge,
   but Linux tcp_recvmsg stops short at the urgent mark even with ordinary data queued behind it. If the target had
   nothing more to send (or a full window), no edge came and the stream stalled until the FIN. The splice path
   already handled the mark (at_mark after splice 0/EAGAIN). The lane made it more frequent because splice runs
   only when both lanes are empty, so more data took the copy path. Fix: targets register EPOLLPRI (EV_TARGET); PRI
   sets a sticky Target::urg; a short read returns only if !(urg && at_mark) (SIOCATMARK). The common short read
   stays syscall-free. Known gap (review): a pointer that stays TCP_URG_NOTYET with data queued (RFC 793 senders,
   urgent byte out of order) raises no PRI; only a misbehaving target hits it, stalling only its own stream.
2. Test too strict. TCP keeps one urgent pointer (RFC 6093): when the next mark arrives before the reader reaches
   the current one, that urgent byte becomes ordinary data (8,388,609 bytes). The check now accepts an earlier
   urgent byte inline; the last one never.
New check urgent_behind_bulk (adversarial.py): a 16 MiB download to a client frozen for 1 s fills the connection's
output; stream 2's target sends 32 KiB, an urgent byte, 32 KiB and stays open until the client is done. Old binary:
stream 2 stops at 32,768 bytes (8/8 runs, lane on and off); fixed: 65,536 intact at once (8/8).
VPS no-regression, 16 rotated reps (vps-urg.jsonl): rr 10x10 0.993, download 10x10 1.017, churn 10x10 0.993
(p >= 0.30). Gates: adversarial (lane on/off), run_tls, wisp-js, udp, v2ext.
Open (review notes, not verified): splice_target pays SIOCATMARK on every EAGAIN (could use the same urg gate);
Reviewer B flagged a possible short-read-as-drained case on the kTLS client read path when a KeyUpdate record sits
behind application data (tls_sk_poll suppresses EPOLLIN during a pending rekey): confirmed and fixed, see 20.17
"KeyUpdate right behind application data".
splice at_mark gate: 0.1 ioctl/GiB, P3 TCP_URG_NOTYET risk, not done (perf2 6363b6b).

## oh256 lane-aware output cap (2026-10-23; branch oh256; pointer 20.06/oh256)
Problem: the client output cap (OUT_HIGH 1 MiB / OUT_LOW 256 KiB) is a big per-connection FIFO for downloads. A plain
256K/64K cap: download 10x10 +16% (wss +17%), peak RSS 21.6 -> 8.6 MiB, CPU -20% (VPS3, 16 rotated reps); but
it failed the 100 Mbit page test (page p50 197 -> 431 ms, 512K: 312 ms; monotonic). Cause: one cap shared by both
lanes; the bulk stream (8 reads x 64 KiB per turn) refills a 192 KiB gap at once, so the small streams park again.
Change (--prio only; --no-prio, wsproxy and UDP unchanged): a target whose next read goes to the bulk lane parks at
out_pending (obuf + lane + splice) >= OUT_HIGH_BULK 256K in Client::blocked_bulk, resumed below OUT_LOW_BULK 64K;
obuf-lane targets keep 1M/256K in `blocked`. Worst case per client stays master's OUT_HIGH + CHUNK.
Order inside blocked_bulk decides fairness (the gap is ~3 reads, so the first resumed stream refills it): targets that
parked without reading since their last park (Target::lane_read) keep FIFO order at the front (Client::bulk_waiting),
readers go to the back. Rejected on the way (adversarial #18 / review): FIFO (one stream took ~90% of the lane; page
p50 +16-25%), insert(0) for non-readers (reversed the list, 2 of 6 streams got 0 bytes; review P0), rotate_left(1)
at the drain (starves one of two streams when no-read rounds alternate; review P1), "no read in this call" (misses
reads before a BUDGET requeue; review r3). New adversarial #18: 6 endless downloads on one throttled connection, every
stream must advance (min >= 0.05 x mean; master's spread 0.3-0.9, final 0.75-0.98).

  page p50 0.875 (p=0.092), page p99 0.630 (p=0.000). Bulk 0.982 (p=0.002) (plain): the link total
  (bulk + responses) is unchanged at 11.4 MiB/s, the pages take the share.
- Loopback: download 10x10 1.105 (p=0.002), wss download 10x10 1.166 (p=0.000); download 1x1
