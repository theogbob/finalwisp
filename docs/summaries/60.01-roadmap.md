# 60.01 Roadmap: stable fast base, then production features (2026-10-23)

Pointers: 20.06 (performance findings), 20.26 (memory budget), 20.27 (upload backlog credit), 50.xx (competitors).

## Principle
1. Finish a minimal, stable, ultra-fast base first. Freeze it as a tagged baseline binary.
2. Add each feature on top of that baseline, one at a time. Every feature gets a regression A/B against the baseline:
   - feature OFF: must tie the baseline on every case (zero cost when unused);
   - feature ON: cost measured and written down (a feature may cost something only while it is in use);
   - the fast path (splice, kTLS, batching, two lanes) must keep working with the feature on, unless documented.
3. A regression found later can then be bisected against the baseline instead of guessed.

## Phase A: base (in progress)
- Merge 20.26 memory budget (c3 or round 5), the oh256 lane-aware output cap (bulk -1.8% under pages: accepted
  by the maintainer), and 20.27 echo candidate (b) only if its real-box test passes.
- Startup capability line (threads, memory budget + source, kTLS ciphers, rekey, splice, TFO, host TCP buffer
  maximums) and low-limit warnings (e.g. tcp_wmem max caps a long-RTT single stream at ~X MiB/s). Warn only,
  never change sysctls.
- Post-merge gates on laptop + VPS3 + VPS1/VPS2, then tag `base-1` and keep its binaries.

## Phase B: regression harness (before any feature)
- One command that runs the fixed case set against `base-1`: loopback 8 cases (plain + wss), page test on a
  100 Mbit/20 ms netns link, 1 Gbit/40 ms link, potato curve (16-128 MiB), idle memory per connection, peak RSS.
- Rotated, paired, medians, Wilcoxon; non-inferiority bound 0.95 (n >= 16 when close). Output: one table vs base.

## Phase C: production features (priority order; each OFF by default unless noted)
| # | Feature | Where it costs | Notes |
|---|---|---|---|
| C1 | Destination policy: host allow/block lists (TCP and UDP), port ranges, block direct-IP targets, IPv6 targets on/off | CONNECT only | wisp-js, epoxy, mrrowisp have it; check after DNS too (private/loopback rules already do) |
| C2 | Real client IP from X-Forwarded-For / X-Real-IP, trusted proxies only | upgrade only | needed for per-IP limits and logs |
| C3 | Limits: streams per connection, total connections, connections per IP, new connections per IP per second | accept / CONNECT | policy limits, separate from the memory budget |
| C4 | Log levels + structured connection log (open/close, client IP, target, bytes, close reason) | per connection, not per packet | default level: info without per-stream lines |
| C5 | Metrics: per-worker counters (connections, streams, bytes, refusals, pressure level, splice/kTLS use), summed on demand; periodic metrics line in the log and an optional text endpoint (Prometheus format) | counters are thread-local plain adds | no atomics on the data path; read by the sampler or on request |
| C6 | Upstream proxy for outgoing connections: SOCKS5 (incl. remote DNS, auth) and HTTP CONNECT | connect handshake | used in production setups (user); bulk data path stays splice/zero-copy after the handshake |
| C7 | Unix socket listener (behind nginx/Caddy on the same host) | none | |
| C8 | Config file: the CLI flags in a file (`flag value` per line, `#` comments, repeated key = list); no new dependency (user, 2026-10-24); CLI overrides file | startup | a richer format later, once the base is stable |
| C9 | Custom DNS servers / result order | DNS pool | low; system resolver + cache + Happy Eyeballs already |
| C10 | Bandwidth limit per IP / per connection (opt-in) | data path while on | must document interaction with splice |

Not planned: static file serving, WebSocket compression (breaks zero-copy, TLS payloads barely compress), TWisp
(remote terminal; risky on a public server), Wispnet, length-prefixed/file transports, reputation scoring.

## Update 2026-10-25: musl track (decision)
- Phase A ends with base-1.2 = glibc build, declared stable (keepalive, honest-uploader fix, cleanup, fuzz fixes, + the
  allocator fix if it ties).
- Then, BEFORE the deeper Phase C features: "base-2" makes the static musl build the standard download, if it checks out:
  (1) allocator: musl-like memory return without musl's global malloc lock (mimalloc / jemalloc / own buffer pool; the alloc work),
  (2) own DNS resolver (C9 pulled forward): musl's getaddrinfo waits the full resolv.conf timeout (5 s) on SERVFAIL and fails a
      name when only its A query fails; own resolver also caps glibc's 10 s never-answering case and makes lookups cancellable,
  (3) gates + regress (laptop, VPS1, VPS2, cross-host) + re-fuzz + soak on the musl binary.
  Measured so far (60.07, bench-suite musl report): idle 0.8 vs 171 KiB/conn at 2 threads; RSS ~2 MiB vs 62-225 after a burst;
  laptop throughput within noise. Open: burst peak (HWM up to 1.8 GiB musl vs 1.1 glibc, one laptop run), multi-core alloc load.

## Update 2026-10-27: base-2 tagged (static glibc, not musl)
- base-1.2 was not tagged on its own; it became base-2 = tag base-2 (4ce741e): ONE build, statically linked glibc
  (bench/release.sh). musl was dropped as the standard: no throughput edge, more CPU per new connection, ~1,100 extra lines
  (own resolver + mapping guard). The 16 KiB mmap threshold + per-worker block cache gives glibc 4.7 KiB/conn idle.
  Parked: musl build, vma-guard (e00ba6e), dns-own (91d2024, -> C9). Details and measurements: 60.10.
- Next: backlog in 60.10 (upload credit redesign, obuf > out_high at L2, --tls-userspace, B3, C9 + 70.10, browser
  backpressure, rr ~2%), then Phase C with C3 + C8 first.
